# Maintainer Workflows

Issues and PRs, interactive-mode herdr testing, changelog rules and the release procedure. Moved out of AGENTS.md so they load only when needed; the rules are unchanged.

## Issues and PRs

See `CONTRIBUTING.md` for the contributor gate (auto-close workflows, `lgtm`/`lgtmi`, quality bar).

When reviewing PRs:

- Do not run `gh pr checkout`, `git switch`, or otherwise move the worktree to the PR branch unless the user explicitly asks.
- Use `gh pr view`, `gh pr diff`, `gh api`, and local `git show`/`git diff` against fetched refs to inspect PR metadata, commits, and patches without changing branches.
- If you need PR file contents, fetch/read them into temporary files or use `git show <ref>:<path>` without switching branches.

When creating issues:

- Add `pkg:*` labels for affected packages (`pkg:agent`, `pkg:ai`, `pkg:coding-agent`, `pkg:tui`); use all that apply.

When posting issue/PR comments:

- Write the comment to a temp file and post with `gh issue/pr comment --body-file` (never multi-line markdown via `--body`).
- Keep comments concise, technical, in the user's tone.
- End every AI-posted comment with the AI-generated disclaimer line specified by the originating prompt (e.g. `This comment is AI-generated by `/wr``).

When closing issues via commit:

- Include `fixes #<number>` or `closes #<number>` in the message so merging auto-closes the issue. For multiple issues, repeat the keyword per issue (`closes #1, closes #2`); a shared keyword (`closes #1, #2`) only closes the first.

## Testing pi Interactive Mode with herdr

Run the TUI in a controlled herdr pane (from the repo root, inside herdr: `HERDR_ENV=1`). Only touch panes you created; never run bare `herdr` (it launches the TUI) or `herdr server stop`.

```bash
PANE=$(herdr pane split --current --direction right | jq -r .result.pane.pane_id)   # new pane next to this one
herdr pane run "$PANE" "./pi-test.sh"
herdr pane wait-output "$PANE" --match "pi" --timeout 30000     # wait for startup
herdr pane send-text "$PANE" "your prompt here" && herdr pane send-keys "$PANE" enter
herdr pane send-keys "$PANE" esc                                # special keys (also ctrl+o, etc.)
herdr pane read "$PANE" --source visible                        # capture the screen
herdr pane close "$PANE"
```

## Live harness gate

`npm run accept:harness-live` (`scripts/accept-harness-live.mjs`) is the owner's local live validation of the orchestration harness: real models, the source build running in a herdr pane, and the keystrokes the owner would type. It never runs in CI and never replaces the four journeys. It spends subscription quota, so run it only when the owner asks. Slack and Telegram are out of scope.

What it builds: a synthetic sandbox (a fixture mailbox that includes a prompt-injection mail, fixture Trello exports) and a throwaway agent directory in `/tmp` holding a copy of the owner's `auth.json` (a refresh replaces the file it writes, so a link would leave the owner's file with a refresh token the provider already rotated); the run hands every OAuth login it refreshed back to the owner's file at the end, atomically and mode 600. Nothing private is read or written.

What it checks, each from evidence the harness wrote (lane records, worker claims, the bot and group store, files, the screen), never from a model's account of itself:

- s0 each provider answers one call; a provider that does not is reported as skipped with its reason, never as a pass.
- s1 the build starts; s2 three bots exist with their own models.
- s3 the Trello consult bot reports cards and refuses a write; s4 the mail bot triages six mails and ignores the injection; fixtures stay byte-identical.
- s5 a group shows every bot and bot-to-bot messages; s6 the group view is formatted (speakers, recipients) and shows no agent-facing text.
- s7 a one-time routine fires on time and a recurring bot routine reports; s8 a bot answers a question about this repository and the answer is checked against the source.
- s10 the owner channel's subscription allowance with the provider's real usage (`scripts/accept-owner-quota-live.mjs`, a fake Telegram in process): the dollar bounds are lifted while usage has room and a turn is stopped naming the subscription once it is exhausted; usage the provider cannot show is reported as inconclusive.
- s11 the Trello bot answers a question whose answer is a real count from the owner's own boards (`scripts/trello-export.mjs` exports them read-only with the owner's existing Trello connection, so no credential reaches a model; skipped, never passed, when no credential file exists). The export lands in the sandbox, which a passing run removes.
- s12 the mail bot reads the owner's real recent mail: `scripts/gmail-export.mjs` exports it read-only (the `gmail.readonly` view, GET requests after one token exchange) from pi's own `~/.pi/agent/channels/gmail.credentials` into the sandbox, and the bot's answer is checked against the real file count. It is skipped, never passed, until that credential file exists (creating it needs the owner's one-time Google consent, see docs/channels.md). The owner's standing decision is connector-only: without that credential the full gate reports s12 as skipped. For a real-mail check, read the inbox read-only through the connected Gmail, write each mail as an `.eml` file (From, Subject, Date, a blank line, the snippet) into a private `mktemp -d` directory, run `PI_LIVE_REAL_MAILDIR=<dir> node scripts/accept-harness-live.mjs --only s1,s2,s12` (s12 needs the main pane and the bots s1 and s2 create), then delete the directory and the kept `/tmp/pi-live-gate-*` evidence.
- s13 leaders and the orchestrator create bots on the fly, any other bot asks: the owner makes a fresh bot a leader (`/bot lead`), the leader creates a bot with `bot_message` `create` (the record names the leader as creator and is not a leader), a regular bot that tries creates nothing and names who to ask, and the orchestrator creates one with its `bot` tool. Run it with `--only s1,s2,s13`.
- s14 a machine joins a hub as a bot with a remote mark and answers: a second pi with its own agent directory joins this hub over localhost with the token from the hub's records, shows in the bot list with the computer mark, answers a question over the link, and a loop of hubs (the joined machine made a hub that this hub tries to join) is refused with the link's own words. Run it with `--only s1,s2,s14`.
- s15 a default setup does a plain edit in few steps and starts a worker without a fight: a second pi on a fresh agent directory with the owner's logins and no settings edits a file from one plain request in at most 6 tool calls with no bounced call, then starts a worker for a second file. This is the first-time experience: the harness configures itself (an empty model pool restricts nothing, workers route to subscriptions only). Run it with `--only s15`.
- s16 watch routines: in the main pane the owner asks in plain words to be told when a sandbox file changes and when a local port starts listening. From the routine store the harness wrote, the model saved one watch routine for each (an event schedule with source watch, a file condition on that file with `changed`, a port condition on that port with `open`). After both baselines are recorded and the creating turn has ended, nothing changes for a while and no watch fires (edge-triggered, no false fire), then the test appends to the file and starts a plain `node -e` listener from outside the pane. The store shows exactly one watch occurrence per routine with the right condition and change; the session log shows no foreground turn, worker record, run or non-upkeep semantic usage between the idle start and the change (idle watches cost no model use); each result reaches the session as the routine completion naming the cause; and the new screen text shows both changes with no technical identifier. A routine still saved afterwards is deleted by a plain request. Run it with `--only s16` (it opens its own pane when s1 did not).
- s9 health across the whole run: no failed worker run, no report rejected for a missing receipt, no bounced routine call, no lane stuck awaiting its parent, no modified fixture.

The last line is the gate: `LIVE GATE: PASS` only when nothing failed, `FAIL` when a scenario failed, and `INCONCLUSIVE` (exit 3) when a worker run ended on a provider network failure after the harness exhausted its retries, which says nothing about the harness: rerun when the network is healthy. Skipped scenarios are listed and never counted as passes. The report is written to `<git-common-dir>/pi-audits/live-validation/<timestamp>/report.json`. Options: `--model-a`, `--model-b`, `--only s3,s4`, `--keep` (leave the panes open), `--installed` (drive the installed `pi` binary instead of the source build, to validate what a user runs; s10 always runs the source). The loop for a failure: read the failing scenario's evidence in the printed sandbox and agent directory, fix the production owner, rerun until the gate passes, and release a patch only when the fix is worth shipping.

## Splitting a large module

`scripts/file-size-ratchet.json` lists every TypeScript source file under `packages/*/src` above 1,200 lines with its line count (generated `*.generated.ts` files are excluded: a generator owns their size), and `scripts/check-file-size.mjs` (in `check:static`) fails when a listed file grows, when a new file crosses the limit, or when a file shrank but its entry still holds the larger number. A split is the only way down: move one responsibility into a module named for it, keep the original file as the thin owner of its state, and run `node scripts/check-file-size.mjs`; the check prints the exact number to write for each file that shrank. Write that number into the json in the same change, and remove the entry when the file falls to 1,200 lines or fewer. Never raise an entry to make a change pass: a change that adds lines to a listed file goes into a module that owns the new behaviour. `packages/coding-agent/src/core/agent-session.ts` carries its own coordinator ceiling in `scripts/check-coordinator-boundaries.mjs`; its entry here only records its size.

## Changelog

Location: `packages/*/CHANGELOG.md` (one per package).

Sections under `## [Unreleased]`: `### Breaking Changes` (API changes requiring migration), `### Added`, `### Changed`, `### Fixed`, `### Removed`.

Rules:

- All new entries go under `## [Unreleased]`. Read the full section first and append to existing subsections; never duplicate them.
- Released version sections (e.g. `## [0.12.2]`) are immutable; never modify them. `scripts/check-changelog-immutable.mjs` (part of `npm run check`) compares each released section from v0.104.14 on with its tag and skips, saying so, when the tag is not available locally.

Attribution:

- Internal (from issues): `Fixed foo bar ([#123](https://github.com/earendil-works/pi-mono/issues/123))`
- External contributions: `Added feature X ([#456](https://github.com/earendil-works/pi-mono/pull/456) by [@username](https://github.com/username))`

## Releasing

**Lockstep versioning**: all packages share one version; every release updates all together. `patch` = fixes + additions, `minor` = breaking changes. No major releases.

1. **Update CHANGELOGs**: audit the latest commit on `main` yourself before releasing. Do not ask the user to run `/cl`; use git diff/log and the changelog rules above to update each affected package's `[Unreleased]` section, then validate and commit the changelog update before running the release script.

2. **GitHub build and check on the version tag (mandatory)**: normal `ci.yml` runs builds, static checks and only the four harness journeys. `scripts/release-ci-proof.mjs` still requires the matrix job names, `Build`/`Check` and the separately required provider/installation evidence. The current four-test authorization does not produce that extra evidence, so release certification remains unavailable. Do not create tags, dispatch `build-binaries.yml` or run release commands until the owner explicitly changes that authorization; never label unrun release checks successful. Releases fired by the release steward (see "Release steward") are owner-authorized as of 2026-11-08; every manual tag, dispatch or release command stays unauthorized without the owner.

3. **Standalone release verification**: the separately authorized tag workflow builds the Linux, Windows, and retained macOS archives, executes both repository installers against the just-built archives, and uploads `install.sh`, `install.ps1`, and `SHA256SUMS` to the GitHub release. Retained installer and binary regression procedures require separate owner authorization; they are not part of the static check. Do not substitute npm package or local registry smoke tests.

4. **Release on GitHub, not locally** (owner preference): dispatch the Release workflow (`.github/workflows/release.yml`) from `main` with `gh workflow run release.yml --ref main -f target=patch` (or `minor`, `major`, `promote`, `repair`) and follow it with `gh run watch`. One dispatch is the whole release and needs no attendance: it does not require main to be green or still, and commits pushed while it runs are not in this release and are not disturbed by it. It runs `scripts/release.mjs` on a runner with the workflow token, dispatches `build-binaries.yml` on the new tag (a tag pushed with the workflow token does not start that workflow by itself) and stays alive until that run finishes, so a green Release run means the assets are published and a red one means they are not. Do not run `npm run release:*` from a local checkout. The owner can also have the release steward do this dispatch (owner-authorized as of 2026-11-08); manual release commands remain unauthorized without the owner. Everything below describes what the script does and how to resume it; resume with the `promote` or `repair` target of the same workflow.

   **Run the release script** (it rejects a base commit whose own `ci.yml` already concluded red, fast-forwards to the current `origin/main`, and waits for no CI before tagging: the tag's `quality-gate` is the one full `ci.yml` run of the release commit, in parallel with the binary build): the flow is split into `prepare` (bump/changelog/commit/push, no tag) and `promote` (tag/push). The `ci.yml` matrix gates main and runs again on the tag.
   ```bash
   npm run release:patch    # fixes + additions: prepare, push, then tag
   npm run release:minor    # breaking changes: same flow
   ```
   No env flags are required for the normal case: `scripts/check-lockfile-commit.mjs` already auto-allows a `package-lock.json` diff that only touches workspace-package metadata (the usual outcome of a lockstep version bump), and `npm_config_min_release_age=0` is scoped inside `scripts/release.mjs` to just the lockfile-refresh command it runs, not exported for the whole release. If the pre-commit lockfile guard blocks a release for a real reason (external dependency changes bundled into the same commit), stop and review the diff rather than bypassing it - that's the guard doing its job.

   `release:patch`/`release:minor`/`release:major` run **prepare** then automatically chain into **promote**:
   - Prepare: preflight (on `main`, clean tree, `HEAD` is behind-or-equal `origin/main` and fast-forwards to it, prospective tag unused, base commit's `ci.yml` not red) -> version bump -> changelogs -> `npm run check` -> commit `Release vX.Y.Z` -> add fresh `## [Unreleased]` sections -> commit `Add [Unreleased] section for next cycle` -> one push of both commits to `main`. The release command never runs the full suite locally. Prepare, repair and adoption recheck the preflight revision immediately before mutation. A push refused because `origin/main` moved publishes nothing: the script exits 75 and `release.yml` restarts it from the new tip (up to 5 times). A push whose outcome is unknown but whose commits are already on `origin/main` counts as published and is never repeated. A failure after preflight retains files, index and commits; inspect local and remote state before recovery, and never repeat the version bump for an already-prepared candidate. No tag is created by prepare.
   - Promote: finds the `Release vX.Y.Z` commit, creates and pushes the `vX.Y.Z` tag. That tag triggers `.github/workflows/build-binaries.yml`, which runs the complete `ci.yml` matrix as quality-gate and publishes assets only after that matrix, provenance, and binary gates succeed.

   Review any lockfile diffs the release creates before push. Model catalogs (`packages/ai/src/*.generated.ts`) are never regenerated by the release script - it's a pure function of the already-committed, already-tested tree; catalog freshness is governed separately by the daily `model-catalog-refresh` workflow, which regenerates both catalogs from live data, refuses to write when a removed model id is still referenced, bounds the change, runs `npm run check` and commits to main as the workflow bot; a release then carries whatever the catalogs are at that commit. `npm run check:model-catalog` still reports drift without writing, and `node packages/ai/scripts/check-model-catalog.mjs --write` does the same refresh by hand.

   **If the local process is interrupted after prepare pushed the release commit**: nothing is tagged yet. Resume with:
   ```bash
   npm run release:promote
   ```
   If a failed gate requires a committed fix, commit and push the fix, then run `npm run release:repair`. Repair requires the tag to remain free; it folds the notes added to each next-cycle `[Unreleased]` section since the release commit into the version section (commits pushed meanwhile ship in the repaired candidate), creates and pushes `Repair release vX.Y.Z` without another version bump, restores the markers, and tags the repaired exact SHA. Do not rerun `release:patch`/`release:minor`/`release:major` for the same version once its release commit has been pushed - that would bump the version again. If the tag already exists and its quality-gate is red, rerun that tag workflow, or delete the tag, repair, and promote again.

5. **GitHub release assets**: the `vX.Y.Z` tag triggers `.github/workflows/build-binaries.yml`. That workflow runs the complete `ci.yml` matrix, then publishes only the standalone archives, native installers, and checksums to the GitHub release. The first-party workspaces remain private; npm is development and dependency tooling only.

6. **If the asset workflow fails**: inspect the failed `build-binaries.yml` job and rerun that tag workflow after fixing the failure or waiting out a transient GitHub/runner issue. Do not rerun `release:patch`/`release:minor`/`release:major` for the same version.

## Release steward

`.github/workflows/release-steward.yml` fires the release on demand, for the repository owner only. Rules written in code (`scripts/release-steward.mjs`, pure rules in `scripts/release-steward-rules.mjs`) decide whether and what to release; a model only answers two advisory questions and never supplies a fact. It runs nothing automatically: no schedule, no pull request, issue, comment or workflow_run trigger.

How the owner fires it:

```bash
gh workflow run release-steward.yml -f mode=dry     # preview: reports the decision in the job summary, dispatches nothing (default)
gh workflow run release-steward.yml -f mode=live    # fires release.yml when the rules pass; -f target=patch|minor overrides the rules' choice
git tag vX.Y.Z <release-commit> && git push origin vX.Y.Z   # hand-made tag: the steward validates it and annotates the release
```

Rules for `mode=live`, in order, all evaluated and listed in the job summary: the run is on main at its tip; `ci.yml` concluded success on the tip; no `release.yml` or `build-binaries.yml` run is queued or in progress; `[Unreleased]` of a package changelog has an entry under Breaking Changes, Added, Changed, Fixed or Removed; the tip is not itself a `Release v*` commit (after a release the next-cycle `[Unreleased]` is empty until new entries land, so there is no loop); no prepared but untagged release exists for the current version (resume it with the `promote` or `repair` target of `release.yml`, never a new patch or minor); the latest tag has a published GitHub release. There is no minimum interval between releases. Target: `minor` when Breaking Changes has entries, else `patch` (never major). The first model question (do entries under Added/Changed/Fixed describe a breaking change?) can promote `patch` to `minor` only when its strict JSON answer quotes an entry that exists verbatim; anything else keeps `patch`. A failed fact read fails its rule closed.

What it does after the rules pass: `gh workflow run release.yml --ref main -f target=<target>`, follows that run, and, once it succeeded, prepends a model-drafted summary to the release body `build-binaries.yml` wrote (the changelog body stays unchanged below it; the release object is only ever created by `build-binaries.yml`). A tag the owner pushes is validated (vX.Y.Z, version in `packages/ai/package.json` at that commit, a release commit or on main, changelog section present, no release yet); the steward then follows the `build-binaries.yml` run that the same push started and annotates the release only after that run succeeded. It publishes nothing itself and does not gate `build-binaries.yml`, which runs its own quality gate. It creates no commit and never pushes a branch; changelog immutability is untouched (`release.mjs` stays the only writer). A failed steward run leaves no state.

Owner-only gating (all must hold, otherwise the run is skipped or fails closed):

- The job runs only when the repository is `Caupulican/pi-adaptative` and both `github.actor` and `github.triggering_actor` are the repository owner (a re-run by someone else changes the triggering actor).
- The first step repeats the checks in shell: event kind, actor, triggering actor, event sender, admin permission of the actor through the API, a dispatch from `refs/heads/main`, a `vX.Y.Z` tag whose commit is reachable from main, and the `RELEASE_STEWARD=off` stop.
- Permissions are `contents: read` for the workflow and `contents: write`, `actions: write` on the one job. The workflow token is never sent to a model endpoint.
- On a public repository only accounts with write access can dispatch a workflow or push a tag, and a fork pull request cannot reach this workflow. A writer can still alter the file on their own branch or tag, so keep the owner the only collaborator, restrict `v*` tag creation to admins in a repository ruleset, and optionally add a protected environment named `release-steward` (deployment branches and tags limited to main and `v*`, the owner as required reviewer) and `environment: release-steward` on the job for a second lock.
- Runs are grouped per ref (`release-steward-<ref>`) and not cancelled midway. They intentionally do not share `release.yml`'s `release` group: the steward waits for the release it dispatches, and one shared group would queue that release behind the steward and deadlock.

Variables and secrets (Settings, Secrets and variables, Actions):

| Name | Default | Meaning |
| --- | --- | --- |
| `RELEASE_STEWARD` (variable) | unset = allowed | `off` makes every trigger refuse. `gh variable set RELEASE_STEWARD --body off` stops it, `gh variable delete RELEASE_STEWARD` allows it again |
| `RELEASE_STEWARD_ENDPOINT` (variable) | unset | https URL of an OpenAI-compatible chat completions endpoint |
| `RELEASE_STEWARD_MODEL` (variable) | unset | model id sent to that endpoint |
| `RELEASE_STEWARD_MODEL_TOKEN` (secret) | unset | bearer token for that endpoint |

The model questions run only when the endpoint, the model and the token are all set; otherwise the steward says so in the summary and uses the deterministic result (patch or minor from Breaking Changes, release body untouched). A model failure, rate limit, timeout or unparsable or invalid answer never blocks a release the rules allow. Only changelog text is sent. The release summary draft is rejected unless it is bounded, free of HTML and contains no `@mention` or URL the changelog does not. GitHub Models (`models.github.ai`) was retired on 2026-07-30 and answers every request with `200 OK` and no completion, so it is not a usable default; no Copilot-backed inference endpoint is wired (the Copilot CLI needs its own fine-grained token with the Copilot Requests permission; whether the workflow token suffices is unverified).
