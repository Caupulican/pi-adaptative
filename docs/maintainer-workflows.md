# Maintainer Workflows

Issues and PRs, interactive-mode herdr testing, changelog rules and the release procedure. Moved out of AGENTS.md so they load only when needed; the rules are unchanged.

## Issues and PRs

See `CONTRIBUTING.md` for the contributor gate (auto-close workflows, `lgtm`/`lgtmi`, quality bar).

When reviewing PRs:

- Do not run `gh pr checkout`, `git switch`, or otherwise move the worktree to the PR branch unless the user explicitly asks.
- Use `gh pr view`, `gh pr diff`, `gh api`, and local `git show`/`git diff` against fetched refs to inspect PR metadata, commits, and patches without changing branches.
- If you need PR file contents, fetch/read them into temporary files or use `git show <ref>:<path>` without switching branches.

When creating issues:

- Add `pkg:*` labels for affected packages (`pkg:agent`, `pkg:ai`, `pkg:coding-agent`, `pkg:tui`); use all that apply.

When posting issue/PR comments:

- Write the comment to a temp file and post with `gh issue/pr comment --body-file` (never multi-line markdown via `--body`).
- Keep comments concise, technical, in the user's tone.
- End every AI-posted comment with the AI-generated disclaimer line specified by the originating prompt (e.g. `This comment is AI-generated by `/wr``).

When closing issues via commit:

- Include `fixes #<number>` or `closes #<number>` in the message so merging auto-closes the issue. For multiple issues, repeat the keyword per issue (`closes #1, closes #2`); a shared keyword (`closes #1, #2`) only closes the first.

## Testing pi Interactive Mode with herdr

Run the TUI in a controlled herdr pane (from the repo root, inside herdr: `HERDR_ENV=1`). Only touch panes you created; never run bare `herdr` (it launches the TUI) or `herdr server stop`.

```bash
PANE=$(herdr pane split --current --direction right | jq -r .result.pane.pane_id)   # new pane next to this one
herdr pane run "$PANE" "./pi-test.sh"
herdr pane wait-output "$PANE" --match "pi" --timeout 30000     # wait for startup
herdr pane send-text "$PANE" "your prompt here" && herdr pane send-keys "$PANE" enter
herdr pane send-keys "$PANE" esc                                # special keys (also ctrl+o, etc.)
herdr pane read "$PANE" --source visible                        # capture the screen
herdr pane close "$PANE"
```

## Live harness gate

`npm run accept:harness-live` (`scripts/accept-harness-live.mjs`) is the owner's local live validation of the orchestration harness: real models, the source build running in a herdr pane, and the keystrokes the owner would type. It never runs in CI and never replaces the four journeys. It spends subscription quota, so run it only when the owner asks. Slack and Telegram are out of scope.

What it builds: a synthetic sandbox (a fixture mailbox that includes a prompt-injection mail, fixture Trello exports) and a throwaway agent directory in `/tmp` whose `auth.json` links to the owner's logins, so token refreshes stay consistent. Nothing private is read or written.

What it checks, each from evidence the harness wrote (lane records, worker claims, the bot and group store, files, the screen), never from a model's account of itself:

- s0 each provider answers one call; a provider that does not is reported as skipped with its reason, never as a pass.
- s1 the build starts; s2 three bots exist with their own models.
- s3 the Trello consult bot reports cards and refuses a write; s4 the mail bot triages six mails and ignores the injection; fixtures stay byte-identical.
- s5 a group shows every bot and bot-to-bot messages; s6 the group view is formatted (speakers, recipients) and shows no agent-facing text.
- s7 a one-time routine fires on time and a recurring bot routine reports; s8 a bot answers a question about this repository and the answer is checked against the source.
- s9 health across the whole run: no failed worker run, no report rejected for a missing receipt, no bounced routine call, no lane stuck awaiting its parent, no modified fixture.

The last line is the gate: `LIVE GATE: PASS` only when nothing failed, and skipped scenarios are listed. The report is written to `<git-common-dir>/pi-audits/live-validation/<timestamp>/report.json`. Options: `--model-a`, `--model-b`, `--only s3,s4`, `--keep` (leave the panes open). The loop for a failure: read the failing scenario's evidence in the printed sandbox and agent directory, fix the production owner, rerun until the gate passes, and release a patch only when the fix is worth shipping.

## Changelog

Location: `packages/*/CHANGELOG.md` (one per package).

Sections under `## [Unreleased]`: `### Breaking Changes` (API changes requiring migration), `### Added`, `### Changed`, `### Fixed`, `### Removed`.

Rules:

- All new entries go under `## [Unreleased]`. Read the full section first and append to existing subsections; never duplicate them.
- Released version sections (e.g. `## [0.12.2]`) are immutable; never modify them. `scripts/check-changelog-immutable.mjs` (part of `npm run check`) compares each released section from v0.104.14 on with its tag and skips, saying so, when the tag is not available locally.

Attribution:

- Internal (from issues): `Fixed foo bar ([#123](https://github.com/earendil-works/pi-mono/issues/123))`
- External contributions: `Added feature X ([#456](https://github.com/earendil-works/pi-mono/pull/456) by [@username](https://github.com/username))`

## Releasing

**Lockstep versioning**: all packages share one version; every release updates all together. `patch` = fixes + additions, `minor` = breaking changes. No major releases.

1. **Update CHANGELOGs**: audit the latest commit on `main` yourself before releasing. Do not ask the user to run `/cl`; use git diff/log and the changelog rules above to update each affected package's `[Unreleased]` section, then validate and commit the changelog update before running the release script.

2. **GitHub build and check on the version tag (mandatory)**: normal `ci.yml` runs builds, static checks and only the four harness journeys. `scripts/release-ci-proof.mjs` still requires the matrix job names, `Build`/`Check` and the separately required provider/installation evidence. The current four-test authorization does not produce that extra evidence, so release certification remains unavailable. Do not create tags, dispatch `build-binaries.yml` or run release commands until the owner explicitly changes that authorization; never label unrun release checks successful.

3. **Standalone release verification**: the separately authorized tag workflow builds the Linux, Windows, and retained macOS archives, executes both repository installers against the just-built archives, and uploads `install.sh`, `install.ps1`, and `SHA256SUMS` to the GitHub release. Retained installer and binary regression procedures require separate owner authorization; they are not part of the static check. Do not substitute npm package or local registry smoke tests.

4. **Release on GitHub, not locally** (owner preference): dispatch the Release workflow (`.github/workflows/release.yml`) from `main` with `gh workflow run release.yml --ref main -f target=patch` (or `minor`, `major`, `promote`, `repair`) and follow it with `gh run watch`. One dispatch is the whole release and needs no attendance: it does not require main to be green or still, and commits pushed while it runs are not in this release and are not disturbed by it. It runs `scripts/release.mjs` on a runner with the workflow token, dispatches `build-binaries.yml` on the new tag (a tag pushed with the workflow token does not start that workflow by itself) and stays alive until that run finishes, so a green Release run means the assets are published and a red one means they are not. Do not run `npm run release:*` from a local checkout. Everything below describes what the script does and how to resume it; resume with the `promote` or `repair` target of the same workflow.

   **Run the release script** (it rejects a base commit whose own `ci.yml` already concluded red, fast-forwards to the current `origin/main`, and waits for no CI before tagging: the tag's `quality-gate` is the one full `ci.yml` run of the release commit, in parallel with the binary build): the flow is split into `prepare` (bump/changelog/commit/push, no tag) and `promote` (tag/push). The `ci.yml` matrix gates main and runs again on the tag.
   ```bash
   npm run release:patch    # fixes + additions: prepare, push, then tag
   npm run release:minor    # breaking changes: same flow
   ```
   No env flags are required for the normal case: `scripts/check-lockfile-commit.mjs` already auto-allows a `package-lock.json` diff that only touches workspace-package metadata (the usual outcome of a lockstep version bump), and `npm_config_min_release_age=0` is scoped inside `scripts/release.mjs` to just the lockfile-refresh command it runs, not exported for the whole release. If the pre-commit lockfile guard blocks a release for a real reason (external dependency changes bundled into the same commit), stop and review the diff rather than bypassing it - that's the guard doing its job.

   `release:patch`/`release:minor`/`release:major` run **prepare** then automatically chain into **promote**:
   - Prepare: preflight (on `main`, clean tree, `HEAD` is behind-or-equal `origin/main` and fast-forwards to it, prospective tag unused, base commit's `ci.yml` not red) -> version bump -> changelogs -> `npm run check` -> commit `Release vX.Y.Z` -> add fresh `## [Unreleased]` sections -> commit `Add [Unreleased] section for next cycle` -> one push of both commits to `main`. The release command never runs the full suite locally. Prepare, repair and adoption recheck the preflight revision immediately before mutation. A push refused because `origin/main` moved publishes nothing: the script exits 75 and `release.yml` restarts it from the new tip (up to 5 times). A push whose outcome is unknown but whose commits are already on `origin/main` counts as published and is never repeated. A failure after preflight retains files, index and commits; inspect local and remote state before recovery, and never repeat the version bump for an already-prepared candidate. No tag is created by prepare.
   - Promote: finds the `Release vX.Y.Z` commit, creates and pushes the `vX.Y.Z` tag. That tag triggers `.github/workflows/build-binaries.yml`, which runs the complete `ci.yml` matrix as quality-gate and publishes assets only after that matrix, provenance, and binary gates succeed.

   Review any lockfile diffs the release creates before push. Model catalogs (`packages/ai/src/*.generated.ts`) are never regenerated by the release script - it's a pure function of the already-committed, already-tested tree; catalog freshness is governed separately by the weekly `check:model-catalog` workflow.

   **If the local process is interrupted after prepare pushed the release commit**: nothing is tagged yet. Resume with:
   ```bash
   npm run release:promote
   ```
   If a failed gate requires a committed fix, commit and push the fix, then run `npm run release:repair`. Repair requires the tag to remain free; it folds the notes added to each next-cycle `[Unreleased]` section since the release commit into the version section (commits pushed meanwhile ship in the repaired candidate), creates and pushes `Repair release vX.Y.Z` without another version bump, restores the markers, and tags the repaired exact SHA. Do not rerun `release:patch`/`release:minor`/`release:major` for the same version once its release commit has been pushed - that would bump the version again. If the tag already exists and its quality-gate is red, rerun that tag workflow, or delete the tag, repair, and promote again.

5. **GitHub release assets**: the `vX.Y.Z` tag triggers `.github/workflows/build-binaries.yml`. That workflow runs the complete `ci.yml` matrix, then publishes only the standalone archives, native installers, and checksums to the GitHub release. The first-party workspaces remain private; npm is development and dependency tooling only.

6. **If the asset workflow fails**: inspect the failed `build-binaries.yml` job and rerun that tag workflow after fixing the failure or waiting out a transient GitHub/runner issue. Do not rerun `release:patch`/`release:minor`/`release:major` for the same version.
