# System Knowledge

Long-term reference for how this system works: invariants the code relies on and sharp edges that are
not obvious from reading it. Entries are short, present-tense, and topical — no dates, authors,
incident narratives, or progress notes. New durable facts go directly into the fitting section;
anything fully encoded in code, tests, or docs does not belong here.

## Delegation and Orchestration

- Worker execution reads its parent only through `ParentExecutionContext` (`core/delegation/parent-execution-context.ts`): environment, policy and judges, foreground-state readers, parent writes. `AgentSession`'s background-lane wiring is the foreground composition, and every member stays a lazy closure because the session swaps its manager, settings and resources on resume and reload and builds memory, the model router and tool performance after that wiring. The context's `getSessionManager()` is a read-only `ParentSessionReader`; every parent transcript append goes through `ParentWritePort` (claim and lane snapshots, notices, terminal reports, task profiles, receipt-origin anchors). The foreground port is `AgentSession`'s wiring plus the transcript writes the background-lane controller builds once (`createForegroundTranscriptWrites`), so foreground effects are the existing appends.
- A host that is not the parent records its parent writes in the attempt's outbox (`AttemptRuntimeState.parentWrites`, bound 16, events `attempt.parent_write_recorded`/`attempt.parent_write_imported`). The parent imports them when its worker lifecycle opens and on each recovery pass: per attempt in ledger order, stopping at the first write that has not landed, under the parent's session-file mutation lock. An import appends only when no entry carries the write's marker (`parentWriteId` on claims and notices, the attempt id on terminal reports) and acknowledges only after the entry is persisted, so a stop between append and acknowledgement never duplicates. A write the parent can never land (invalid record, no notice or report owner) is refused once with a warning and acknowledged, never held. A terminal is not published while its attempt still holds writes, so the claim lands before the completion it explains. Foreground attempts never record writes, so these paths find nothing there.
- Every worker-reachable policy member is composed by a factory over readers, and the foreground passes its existing stateful instances into it (never a second custody, gate, queue or vault): `createWorkerSkillAccess` (any vault that serves reads; exclusions need the vault's `appendPolicyEntry` writer), `createWorkerRequestPlanner` (`CacheLaneGuard` owns custody, knowledge and the worker early-compaction verdicts; brain-curation appends take a per-call writer and are root-only), `createWorkerSettlementPolicy` (`SettlementJudges` over System One and the expensive-tier consult; unsettled worker items go through `ParentWritePort.recordUnsettledForOwner`, which a non-parent host must record, never drop) and `createWorkerEdgePolicy` (`sessionEdgeGrants` over `edgeRecordsOnBranch`, `createSessionOperationGate`, `ModelPoolPolicyView` over `branchPoolPolicyReader`). A worker is refused by the operation gate, never asked, so owner-word settling and `askOperator` are foreground-only. `localCommitBranch` and handoff are in-memory owner-word state never restored from the branch: a host without the owner must take the delivery binding from the routine's saved intent.
- Workers are persistent specialists: conversations are keyed by `(parentSessionId, logicalAgentId)` and survive across tasks. `delegate start` with `agentId` dispatches onto an idle worker's transcript and keeps its admitted grant (`authority`/`profileId` are rejected on reuse); `list` reports per-agent `activity`. `start` must never silently ignore `agentId`.
- Clean worker-owner shutdown reserves suspended project contexts in `handoff`, including owed mailbox messages. This is same-parent continuation authority, not fleet-wide idle availability; acquisition consumes the reservation under a new generation. Goal cancellation can change task status without settling those obligations, so reclamation must not depend on still being suspended. Unsafe crash snapshots remain busy and require their original recovery proof.
- Session-bundle deletion has one token-owned remover and a durable retention/permanent policy. Refused admission never publishes new destructive intent. Explicit deletion validates the foreground header and acquires ownership before removing history or usage journals; busy worker artifacts may remain as a reported partial outcome. Its exact reservation guards the later worker eligibility inspection. Failed or uncertain removal keeps the permanent barrier; strict foreground absence can retry an already permanent deletion. Only a settled local operation or proven-dead same-host owner can be reclaimed. Partial retention cleanup bypasses age checks only when the existing retention marker is confirmed again under lock. Admission can retire a settled retention marker after strict bundle absence; permanent and legacy ownership-free markers never reopen this way.
- Persisted SDK sessions acquire a bundle lifetime lease before asynchronous startup and session-bound recovery. Direct `AgentSession` construction requires an exact unclaimed lease from `acquireSessionBundleLease`; transfer revokes the caller's release capability. Deletion and lease admission share one lock. Replacement holds both predecessor and target through retirement, activation and rollback; admission failure cleans the candidate while preserving the active predecessor. Lease registries are bounded to 64 holders and prune only proven-dead same-host processes. In-memory sessions create no lease files.
- Worker retry is host-owned and evidence-gated, built on suspend/resume — there is no parallel re-dispatch path. Retries require a classified-transient failure detail (`classifyFailure`; missing or `unknown` never retries); `maxAttempts: 1` never ladders. Retry count and not-before are persisted atomically with the fenced suspension, restart recovery retains both, and terminal transitions clear the durable ladder while terminal publication clears its process timer.
- A retained retry owns its exact attempt, pending entry and alarm generation. Timer allocation failure keeps the original deadline or failure backoff and is retried on the next recovery/capacity event, including after ordinary queue recovery is complete. Queue-full retries use capacity events. Removing or replacing an entry invalidates its callback before best-effort timer cleanup; one failed clear cannot block terminal publication or the rest of shutdown. Recovery stops between callback-bearing phases when disposed.
- Token budgets charge `budgetedTokens()` — cache reads at `CACHE_READ_BUDGET_WEIGHT` — in both the capability gateway and the worker-tree coordinator; face-value cache-read counting turns `maxTokens` into a request counter. Grants below `MIN_VIABLE_WORKER_TOKEN_BUDGET` reject at admission; bounded failures carry `detail`; worker provider calls retry transient transport failures with jittered backoff.
- Background workers notify the foreground root by lane record plus a bounded completion event; root output is retrieved explicitly via `delegate` action `status`. Late worker output never enters an active foreground transcript — it races the foreground model.
- A blocked worker-wait restore is woken by write-reservation availability (`subscribeReservationAvailability` → `notifyAvailability`), not `subscribeStateChanges` and not a 1s poll. The 300s restore bound is a watchdog only; a reservation release must resume the waiter on the event.
- Delegated memory is a bounded query capability, not delegated file access: granted per call and by the lane profile, delivered source-labeled via `memory_read`; raw memory/state/auth paths stay denied; the mutation tool is never exposed to workers.
- The worker claim envelope is authoritative, but non-JSON reports are retained as bounded plain text with disclosure, never rejected outright. Worker tool loops resolve tool-call protocol from the lane model, never the foreground model. Concurrency admission counts running workers only; durable fleet admission separately caps depth, direct children, persistent identities, and queued dispatches, while ordinary starts and persistent-agent turns reserve mandatory-verifier headroom before durable mutation.
- Omitted `forkTurns` is `none` even for same-provider/model root workers. Explicit `all` or a turn count remains available only inside the exact provider/model boundary. Worker terminals that need parent review wake the parent through the terminal handoff; they must not queue Review now / Keep blocked, because that latch blocks automatic parent wake. Workers never spawn: `delegate` is in `WORKER_TOOL_ADAPTER_FORBIDDEN_NAMES` and a worker authority naming it is rejected at admission, so only the root starts, steers and cancels workers. A worker token/cost/wall/tool budget denial terminals the lane; it is not a per-call block the model can retry around.
- Native workers communicate through `bot_message` when their immutable grant includes `workflow.message` and that tool. It uses the existing parent mailbox, current bot bindings and captured sender attempt; idle peers wake through the ordinary scheduler. Replies infer their destination from the delivered request. Messaging grants no spawning or peer access, and explicit profiles remain restrictive.
- Worker task fitness is checked at execution admission, including explicit model pins and reused mailbox turns. The complete task, actual model and effort determine the judgment; model availability and a role named worker do not establish suitability. Unconfirmed lightweight classification never counts as strong. Explicit System One disablement keeps the deterministic admission path without claiming semantic validation.
- An uncertain task-fit result names its evaluation and a fingerprint of the exact instructions, objective, model, effort and role. After an additional reasoning round, the root can record `workerTaskFit: adequate` or `inadequate` through `systemone resolve_uncertainty`. Only an explicit affirmative decision for the pending evaluation/question admits an unchanged retry; generic dispositions, other sessions and stale evaluation completions cannot. This never resolves independent verification obligations or grants execution capabilities.
- Managed and native worker profiles share `lendableToolSurface`: a parent holding bash may lend the catalogued read-only search, listing and repository tools. Explicit worker requests still intersect the worker ceiling, and a single approved route needs no model-selection request.
- Worker usage receipts carry the originating durable goal identity when available and the worker binding as provenance. Their cumulative usage can include descendants or other model calls, so binding metadata never justifies repricing the aggregate; missing historical origin stays unassigned.
- Queued worker admission keeps asynchronous directory and fitness work in the scheduler's owned preflight. Dispatch rechecks exact current fitness inputs and capacity before the synchronous execution-lease transition; a stale approval returns to preflight while retaining queue ownership.
- `delegate interrupt` is a halt, never a silent stop: `WorkerAgentControlCoordinator.interruptWorkerAgent` records one `WorkerLaneHalts` entry per running lane and the worker loop takes it once at its next request boundary (`AgentLoopConfig.getHaltRequest`, polled before every provider request). The loop then injects the halt message and spends one tool-free request on the model's own report; `runWorker` turns that report into a `blocked` / `worker_interrupted` claim with `parentReviewRequired` whatever status the report claims, so a halt can never read as completion, and the controller never retries a delivered halt. The terminal handoff is the only wake path, so a worker that reaches no boundary within `haltReportDeadlineMs` (120 s) is cancelled and the cancellation is what the parent hears. The halt is `delivered` when the loop takes it; one the run finishes before reaching is moot and the ordinary handoff stands. `force` keeps the old suspend-and-abort for System One's steer-and-resume (`agent-session.ts` worker control) and is not model-facing. The worker stays an idle persistent agent: a blocked/review-pending latest result with no newer task is `awaitingParent` in `list`, and the parent answers with `follow_up` on the same agentId.
- `ForegroundTerminalHandoffController.flushProviderBoundary` (`agent.beforeSteeringPoll`) folds a terminal into a request only when its known `ownerEpoch` equals the current foreground submission epoch. Unknown or different ownership takes the idle-delivery path. `WorkerNotificationCoordinator.noteAttemptOwnerEpoch` captures ownership once by exact attempt ID at fresh native dispatch, managed dispatch, or mailbox-turn creation. Names and lane IDs can repeat across execution kinds and generations; they cannot key this ownership. A refreshed pending notification retains its captured epoch. Mailbox turns capture only when the ledger returns `created: true`; replay never borrows the current epoch. Epochs stay process-local and are not written into the durable orchestration contract.
- Terminal observation acknowledges delivery, not mutation review. Bounded `delegate list` and `tasks` results carry their exact attempt IDs; only items retained in the serialized result can be observed. Waits capture `terminalAttemptIds` with their result; `terminalLaneIds` are display metadata only. Coarse activity reads and arbitrary transcript pages do not establish terminal exposure. Native agent ordering excludes managed-process attempts even when their display names collide.
- Terminal publication and recovery retain the captured attempt identity. A terminal lane record is reprojected only from its matching task/attempt, with parent routing from that same snapshot; missing or contradictory identities remain unresolved. Notification acknowledgement, publication fences and retry-alarm cleanup use that exact attempt. A newer attempt on the same lane cannot inherit an older terminal or lose its retry alarm to that terminal's replay.
- Worker receipt origin belongs to each dispatch, not a persistent specialist's birth context. New root work confirms its parent branch anchor on disk before durable admission; an empty or buffered session prefix is flushed through the session owner. Live navigation fences survive admission waits and callback boundaries but are never serialized. Mailbox replay, child dispatch and verifier recovery retain their original origin; missing historical origin is never inferred from the currently open branch. Capturing origin alone does not publish or accept worker evidence.
- Native worker results freeze receipt facts from their exact terminal transcript slice before awaited review. Receipt eligibility is recorded after host findings and before independent verification changes the public outcome; reviewing a partial, blocked or inconclusive claim cannot make those facts accepted. Invalid or oversized facts remain explicitly unavailable, with no truncation or reconstruction from retained transcript pages. Result status and review acknowledgement alone do not authorize receipt publication.
- Worker receipt publication is an attempt-owned obligation, independent of terminal notification and usage delivery. Required parent review binds the exact attempt, result and facts digest; required verification binds its exact verifier attempt. Startup and result, verification, review, branch and persistence events retry publication even when delegation is disabled. Parent history is checked under the existing bundle/transcript lock before append; only confirmed physical publication permits the separate runtime acknowledgement. Conflicting or duplicate publications, uncertain history, and histories beyond 64 MiB or 100,000 entries remain pending with diagnostics. In-memory publication receives no physical acknowledgement. Legacy receipts without final acceptance identity cannot establish accepted worker evidence.
- Automatic bundle retention checks pending worker content and usage receipts under its exact deletion reservation before expiring mailboxes or removing files. Unreadable projection evidence defers deletion; a fresh reservation is released so recovery remains possible. Task cancellation does not retire unpaid usage or an older result's potentially publishable facts. Exact receipt acknowledgement or immutable negative verification settles content custody. In-memory content receipts have no physical acknowledgement and therefore retain their bundle; permanent user-requested deletion remains a separate policy. Retention and runtime share projection replay, but only runtime requests compaction.
- Worker notification timers are auxiliary to delivery: an unavailable watchdog never prevents a handoff, and failed timer cleanup never reclassifies an accepted handoff. Alarm tokens invalidate before adapter cleanup, including disposal and reentrant allocation. Failed retry allocation retains outstanding records with a warning and waits for the next notification event or recovery; it cannot reject the serial delivery tail. Callback boundaries recheck disposal before further durable writes or outbox publication.
- Root and worker mailbox reads distinguish initial file absence from unavailable or malformed storage. Only initial `ENOENT` means an empty mailbox; permission/layout errors and files disappearing during a bounded read remain errors. A project mailbox frame must contain its payload, and binding may initialize missing storage but must reject a null payload. Read failures flow to existing wait/reconciliation errors rather than implying that no replies or obligations exist.
- Native attempt membership is resolved by `nativeAgentIdForAttempt`: managed execution has no native owner; a bound native `agentId` takes precedence over its queued `logicalLaneId`. Tree attempt budgets, retirement blockers, queued-context recovery and native turn sequencing use this rule. Managed attempts cannot lease a native binding. Uncorrelated native turn tasks use a separate hashed namespace from managed turn tasks; correlated mailbox task identities retain their original stable hash.
- `agentLoop`'s `runLoop` return value (`newMessages`, seen by callers as `loop.result()`) has always silently disagreed with that same run's own `message_end` event stream about what it added: a message committed only into `sourceContext.messages` (the kernel's `provider-request-planner.ts`, transient records included) was invisible to `newMessages` while fully visible via emitted events. Harmless until something compared the two - `worker-attempt-executor.ts`'s `onMessage` builds its own `durableCallbackMessages` from every `message_end` (a generic catch-all, any role), then `callbackEvidencedCompletion` (same file) asserts `isDeepStrictEqual(result.messages.slice(historyLength), durableCallbackMessages)`, where `result.messages` traces to `newMessages` via `reflection-controller.ts:889`. Once the kernel's transient-record host-gap hook started emitting `message_start`/`message_end` for a committed record (turn-economics remediation, step 3), it showed up in one side and not the other, throwing `WorkerCompletionProtocolError("...suffix without exact callback evidence.")`. Fixed at the root in `agent-loop.ts`: the hook's closure now also does `newMessages.push(message)` alongside its emit calls, so the return value matches the event stream it already produces - a general agentLoop correctness fix, not a worker special case.

- FOLLOW-UP, same day: the fix above closed the actual bug but left the underlying hazard alive - committing a transient record into `sourceContext.messages` and recording it (for a host's own persistence to see) were still two separate statements in `provider-request-planner.ts`, which a future edit could pull apart or a new call site could add without knowing it needed both. - A persistent bot's soul (`PersistentBotRecord.soul`, no size limit of its own, threat-scanned at write by `normalizeBotSoul` and again by `bindBotSoul`, which refuses at admission only past `MAX_WORKER_SOUL_LENGTH` or the model's `systemPromptMaxChars`) is host-owned `WorkerDelegationRequest.botSoul`; admission places it before the profile soul in the NEW worker's execution contract, so mailbox reuse, queued dispatch, retry and restart recovery inherit it from the pinned contract and never re-read the bot record. A live worker keeps the soul it started with, so editing a soul or grant requires `/bot retire` first.
- Root-worker messages are canonical records first; the text a model reads is one rendering of them. `details.v` versions the `delegate` result and the terminal handoff (`details.records[].h` carries each lane's state codes); a refusal is a `CommsErrRecord` (`core/comms/comms-records.ts`) in `details.err` with a tagged content view, built from `skipReason` by `tools/delegate-rejections.ts`. Nothing in the harness reads a rendering back: a decision reads the record, and `scripts/check-comms-text-parsing.mjs` (in `npm run check`) fails when a listed comms file parses a value named for message text. A line that must read foreign text carries `comms-legacy-decoder: <reason>`.
- Host injections are canonical records with a tagged model view too: the tool-failure ledger (`ToolFailureLedgerRecord`, `kernel/tool-failure-ledger-record.ts`, built by `sanitizeToolFailureContext`, rendered by `renderToolFailureLedger` in the planner), the authority context, the task-directory context and the path-alias legend (`AuthorityContextRecord`, `TaskDirectoryContextRecord`, `PathAliasLegendRecord` with their renderers in `core/comms/host-injection-records.ts`). A transient slot (or a host transient's `details.record`) carries the record, and `reconcileTransientRecords` writes it into the durable record's `details.record` beside the `cumulative` / `pointer` / `transientCleared` markers, which stay top level; pointer and cleared records carry none. Append-on-change still compares rendered text, so every view is a total function of its record (a tag omitted when equal to another, such as `kind_mistakes` equal to `occ`, is still derivable). The view is a header line, then one line per item: identifiers bare when they are plain tokens, every free-text value one JSON string escaped for `& < >`. A trailing slot supplies its header line in `TransientRecordSlot.header` (`renderToolFailureLedgerHeader`, `VERIFICATION_OBLIGATIONS_HEADER`), and a pointer record that reclaims the tail repeats it, bounded to 80 characters; it is never read back from the content. The legend's committed ids are read from `details.record.entries` (`PathAliasRuntime.durableLegendIds`); a legend record persisted before the record existed is read by its `<id>=<path>` lines (a marked legacy decoder). Compaction carries whole session entries, so `details.record` survives the cut. All four views are tail records: a renderer change affects only records appended after it, and an existing session pays one tail re-append per non-cumulative kind on its first request after the upgrade (the old text differs), never a prefix break. The per-call `[harness] {json}` failure envelope keeps its JSON view: `buildFailureContextAnalysis` re-renders bounded replacements of already-sent failure results from their record on every fold, so changing that renderer would rewrite cached prefix bytes in every resumed session. Its readers decide by `details`: a refused replay carries `details.piToolFailureReplay` (`readToolFailureReplay`, read by the recovery gate's `replayRefused`; a result persisted before the marker falls back to `readVisibleToolFailureCode`, marked legacy), and `toolResultBatchSignature` compares a failure result by `stableToolFailureIdentity(details)` (the visible record without `occurrence` / `kindMistakes` / `state`). The goal context keeps its view: a tagged rendering measured 2% smaller (median 789 to 772 B), which does not repay the one re-append of the whole record (about 790 B) each session with an active goal would pay after the upgrade. A discarded attempt's directive details (`piToolFailureDirective`) now also carry the `evidence` its visible result shows, so the record holds everything the text does. `task_steps_context` was already a header plus one line per step. A plain transient record carries `details.superseding: true` beside its superseding note; `classifyTransientRecord` (the compaction carry) and the reconciler's content index read the marker, and only a record persisted before it existed is recognized by the note suffix (marked legacy). The failure fold classifies a tool result as a harness failure by `isError`; the `[harness]` notices an engine result may append (cleanup, after-hook, progress) are recorded in its receipt's `postprocessingFailures` and never make a successful result a failure, and the `[harness] ` text prefix is read only for a result without an engine receipt (marked legacy). A background task's summary reads the completion's failure record (`readToolFailureTelemetry`), not its output text; a restored task keeps its stored summary. The path-alias legend carries the aliases visible on the request's wire minus committed ones (`PathAliasSyncResult.legendFor`): ids referenced by the rendered messages (text, thinking, tool-call arguments, custom records other than the legend), the transients placed before the legend, and `AgentContextPlanRequest.wire` (`AgentContextWire`: `texts`, the failure ledger and verification obligation the kernel planner sends at the tail, scanned on every request because they change; `messages`, the continuous-chat view and state frame the ICM projection prepends, the same objects for every request of a turn and state, so their references are read once through the runtime's per-message memo; the frame is never aliased, but its summaries can quote model-written alias tokens), each token also counting every alias id that prefixes it. The old rule (every id ever rendered by the runtime, which root and its workers share) re-sent the full session legend each ICM turn, because the base plan sees only the running turn. An alias the model can no longer see gets no new line; a tool argument naming it still expands, since `wrapToolWithPathAliasExpansion` resolves against the full table, so visibility is a model concern only. The legend itself is recomputed on every call against the synced table and committed lines, never cached. `getAliasEconomics` prices the legend by the characters of every distinct legend record seen in a synced history (one object per conversation it was sent in), so a re-send to another conversation, after a compaction or in a continuous-chat turn is paid again; the savings side still counts mentions of rendered ids. Context GC classifies the task-steps page by `customType === "task_steps_context"` (`isTaskStepsContextMessage`); the page has carried that type since it first existed, so no persisted page needs its `<task_steps_context` text. The pipeline page keeps its marker because `pipeline` tool results carry the same text. The session census scripts read refusals through `toolFailureOf` (`scripts/session-stats-common.mjs`): details first, the `[harness] {json}` text only for a result with neither failure details nor an engine receipt (marked legacy).
- State codes, error classes and hint codes have one definition, `COMMS_STATE_GLOSSARY` / `COMMS_ERR_GLOSSARY` / `COMMS_HINT_CODES` in `provider-prompt-contracts.ts`, rendered once into `ROOT_DIRECTOR_ROLE_PROMPT` (about 290 tokens: one line per state class, err classes in one line, hints as bare names because they are self-describing; a text holds no semicolon, the prompt joins a line's codes with one). It is in the cached prefix, not a rule hook, because a hook only appends to tool results and cannot reach a wake message, and under the default memory system a rule delivered in an earlier turn is not on the wire. A caller without the director prompt (a worker using `wait` or `follow_up`, a child session) reads the same codes without the glossary; the class and hint names are self-describing and `m` states the reason. Non-full capability classes cannot call `delegate`.
- Reading mode follows the host verdict (`workerReportSufficesForAcceptance`): an `accepted` code verdict with no missing proof, no parent review pending and the judge's `allRequirementsCovered` fact is `READ_REPORT` (the report is the evidence, transcript ranges on demand); every other case, including a task with no required ids and a claim whose verdict lacks the fact, is `READ_ALL`. The judge covers a requirement only through its own receipts and recorded changes (a failed cited receipt is contradicted, `not_applicable` is never covered), not through the worker's `checks` list. A claim holds the host's own observations in typed `hostFindings` and its wait for an independent verifier in `pending`; the blocker lines beside them are display and no gate reads them.
- A structured `delegate start` (`goal`, `note`, `refs`, `evid`, `out`; budgets, enums and renderers in `core/comms/comms-records.ts`) is rendered into the worker's task text at admission and stored as the dispatch `instructions`; the `TaskBrief` is stored beside it as `brief`, and a dispatch without one is legacy free text. `TaskBrief.v` selects the renderer and a renderer is frozen once a record carries its version (version 1 is not injective and stays readable; new briefs are version 2: one-line goal, one `Ref:` line per ref, `Evidence:`/`Output:` line, note last). The dispatch decoder rejects a brief whose renderer does not reproduce the stored text, and replay identity compares `brief` field for field beside the text. The decoder also rejects unknown fields, so a binary older than the `brief` field cannot read such a session.
- A host-written worker message (a mailbox control message, or the attempt's task prompt) carries a typed identity, `WorkerControlRecord` (`kernel/worker-control-stamp.ts`): a non-enumerable stamp on the message object, like the owner-input stamp, written on its session entry as `workerControl` ahead of `message` (so a bounded prefix read of an oversized entry reaches it) and re-stamped when a context is rebuilt from entries. Its `body` range is where the sender's words sit inside the rendered text. The mailbox acknowledgement, transcript reconciliation (including the cold-prefix lookup), the context-fork sanitizer, the lane's last words (bounded by the newest attempt boundary, not the TASK frame) and the bot chat read it first. The rendered text is unchanged (`[Worker control <id> ...]`, the TASK frame) because the model needs the id to reply, so a message that lost its stamp (a copy, or an entry persisted before entries carried it) is still recognized by the marked `comms-legacy-decoder:` readers in `worker-agent-control-coordinator.ts`, `worker-conversation-store.ts`, `sanitized-context-fork.ts`, `worker-runner.ts` (`isWorkerTaskPrompt`, used only for a conversation without attempt boundaries) and `persistent-bot-team-store.ts`. Two text readers remain by design: the host's own memory-block separator cut of a bot's task words, and the text-envelope reply (`botReplyText`), which is the declared fallback of the report tool.
- A mailbox message written by a build that knows envelopes carries `env: {v:1,k}`; addressing stays in its typed fields. `env` selects the intent digest: a keyed message's replay receipt carries `digestVersion: 2` (digest over the message id and the canonical fields, label `pi-worker-agent-control-intent-v2`); a legacy message or receipt (no `env`, no `digestVersion`) is judged by the frozen version 1 digest. A replayed key is judged under the version its stored message or receipt carries, so an identity first accepted by an older build still replays, and a differing replay is a `WorkerControlIdentityConflictError` (`E_DUP` at the `delegate` tool). A mailbox holding a version 2 receipt is rejected by a build older than the field, as for any additive record.
- `submit_report` is the structured write path of a worker (the schema refuses unknown properties). The JSON text envelope is parsed only where no report tool is offered or a model answers in text, and carries no structure promise.
- Agent messaging is durable records plus advisory wakes, and the address decides what can be durable. The worker mailbox, the session-root inbox and the collaboration job queue address stable identities (parent session, agent id, job member) and keep records with their own admission and bounds proofs; a notification only wakes a reader, who re-reads the record (`subscribe`/`waitFor`), so a lost wake never loses a message. pi-chat (`core/chat/mesh.ts`) addresses the pi session: its mesh id is `session-<session id>` and its credential is kept in `sessions/local/credentials/`, so a resumed or restarted session is the same peer and the broker adopts its credential for an id it does not know. A send to a peer that is not on the mesh becomes mail in that peer's inbox (`core/messaging/inbox.ts`: 32 messages, 256 KiB, 24 h, receipts for 24 h; a settled message drops its body), woken in-process and by a directory watcher, and collected by the recipient at join and on every inbox change through the same `receive` path as a live message (one delivery per sender and id, also across a restart, through the receipt). Standing of held mail is an HMAC under the machine session secret, never the file's claim. The cold protocols are not interchangeable shapes, so none is re-hosted on `MessageInbox`, which forgets receipts after 24 h or 128, expires held mail after 24 h and refuses a changed body under a known id. The collaboration peer queue lives in the job record because enqueue authenticates the member token and checks the recipient's state, and `reservePeerTurn` turns the message into a turn reservation, all in one job-file transaction; its messages have no expiry and its 128 receipts refuse rather than forget. Collaboration control-failure notices (`control-handoffs.ts`) are one latest notice per source in the job's metadata, replaced by a newer turn and deleted by `clear`, and follow the job when another session adopts it. The worker terminal handoff outbox is process-local and rebuilt by `rehydrate` from the orchestration state, which is its truth, and a newer projection of the same attempt replaces the waiting payload. The session-root reply mailbox and the worker mailbox write under session-bundle admission, expire through bundle retention with attributed evidence, and bound replay receipts with `replay-safe-mailbox-bounds.ts`, which refuses instead of forgetting; a session-root reply settles in two phases (source reconciled, then acknowledged with its `ackToken`). What they share is the wake: the pi-chat inbox and the session-root mailbox notify through one `KeyedSignal` per file path (`util/keyed-signal.ts`), whose listeners are `waitFor` checks or async drains that never throw.
- Routine calendar schedules (`core/routines/calendar-schedule.ts`) are owned by one pure module: five-field cron, IANA zone through `Intl.DateTimeFormat`, no dependency. Wall slots map monotonically to instants: a repeated wall time runs once at its first instant, a skipped one at the transition instant, and slots collapsing onto one instant run once. The cursor stores the next slot computed at claim (`{kind:"calendar", nextAt}`); stored state and occurrence validation never re-derive slots from zone data, which may change between runtimes. A stored zone is checked for shape only (`isCalendarTimeZoneName`), never support or canonical spelling, so a zone a runtime lacks makes that routine unschedulable there (`routineZoneUnsupported`: the claim records one cancelled notice for `cursor.nextAt`, marked by `lastRunAt >= nextAt`, and leaves the cursor; the scheduler's alarm includes it only while that notice is owed), never the store unreadable. Saving still refuses it, except an upsert resubmitting the stored schedule unchanged (pause, resume, prompt edit), which keeps it as saved; the comparison side of `scheduleChanged` is re-canonicalized when supported. An update without a zone keeps the saved one (`RoutineSessionController.persist`). The claim isolates each clock routine (`admitClockRoutine`); one that throws is returned in `unschedulable` and warned once by the scheduler. The day-field rule is classic cron: a field starting with `*` (`*/2` included) is unrestricted, and OR applies only when neither starts with `*`. The forward search spans one Gregorian cycle (146,097 days, after which dates and weekdays repeat), so a satisfiable rule always finds its next slot, however sparse (29 February on a given weekday can recur decades apart), and a rule matching no date is refused at save; `nextAt: null` arises only when no representable instant remains. Start windows (`once.notAfter`, calendar `maxLatenessMs`) are excluded from slot identity (`routineSlotRule`), so editing one neither replays a consumed one-off nor moves a slot; a late calendar slot is passed over into `cursor.skipped`, which the next run's `missedCount` absorbs (`routineParentInput` states a nonzero `missedCount` in the delivered text and details, as "at least" with `missedCountIsLowerBound` at the calendar or event saturation bound; the event worker brief keeps the exact count text because `RoutineWorkerExecutor` matches attempts by it); the first late slot of a streak (`skipped` undefined) is also recorded as a cancelled notice occurrence, which needs journal room like a run, and later ones only count, and an undispatched occurrence past its window is cancelled at the next claim pass, not at the deadline. A stored calendar schedule makes the store unreadable to builds without it.
- The routine scheduler (`routine-scheduler-controller.ts`) never lets one failure stop a session's routines. A pass delivers pending results first (an acknowledged terminal entry is what the journal can prune), then reconciles, claims and dispatches; the claim and each occurrence's reconciliation, dispatch and delivery are isolated, a failing unit warns once per reason (`faults`) and the pass ends with a `RETRY_DELAY_MS` retry. The 256-entry occurrence journal is shared by every session of the agent dir and uncertain entries are never prunable: without room the claim returns `journalFull` and leaves due slots and event attempts unconsumed instead of throwing, and the scheduler warns once per streak and leaves due routines out of its alarm, since only a store change (which wakes it) can make room. Alarms use `alarmAt`, which re-reads the port clock at least every `WALL_ALARM_RECHECK_MS`, because platform timers stop during suspend and do not follow wall steps. Clock faults: nothing is claimable while the clock reads before the routine's `updatedAt` (an occurrence is validated as never older than its definition, so claiming it would make the store unreadable); a manual run refuses with that reason. A cursor whose previous slot is later than now (a forward clock fault later corrected) is rebased from max(anchor, now) at claim (`rebasedRoutineCursor`), and the scheduler arms its alarm on the same rebased slot; a rebased cursor reaching a slot that already has its occurrence consumes it without a second run.
- Quiet routine outcomes travel as one typed field, never text: `submit_report.ownerUpdate` -> `WorkerSubmittedReport.ownerUpdate` -> `WorkerResultContract.ownerUpdate`, which `createWorkerResultContract` stamps only for a `completed` result with no blockers, inconclusive findings or parent review and a host verdict of `accepted` (a recovered claim has no verdict and wakes) -> `RoutineResult.ownerUpdate` (succeeded only; a resolved uncertainty always wakes). `routineParentInput` derives `mode: "next-owner-turn"` from the persisted result alone, so a redelivery after restart keeps its identity; the field joins `routineResultDigest` only when present, so older results keep their digest. Pending `next-owner-turn` inputs share the 256-input parent ledger with wakes, so a routine carries at most one quiet input: a later quiet result is acknowledged against the still-pending one (`findCarriedQuietResult`), so the carry holds the first quiet result, not the latest, and later ones are recorded in the routine store but not delivered (no tool surfaces occurrence outcomes yet). Builds without the field reject a task ledger or routine store holding it.
- Event routines (`schedule.kind: "event"`, session targets only) never copy event custody: `routineHostEventFeed` projects retained `hostEvents` with `ready` (`HostEventRuntime.isSourceReady`, process-local), `current` (`hostEventIsCurrent`) and `rootApplicable` (current `registration.rootSubjects`, decided at use like `hostEventDeliveryEligible`, never stamped at accept), and `decideRoutineEvents` is the one decision used by both the scheduler's claim gate and the store. `acceptedOrdinal` is the shared orchestration ordinal (tasks and attempts advance it too) and one seal's snapshots share it, so ordering is `(acceptedOrdinal, sourceSequence, eventId)` and no gap can be inferred from ordinal holes; a replay gap is detected by a digest of all sources' `lastReplayGap`. Current seal observations are never pruned, so pruning cannot remove a fire-able attempt. The cursor stops before the first matching attempt whose source is not ready; a source that never becomes ready again (custody replaced) holds the cursor there, which only costs re-evaluation of at most 256 retained events per wake, with exactly-once kept by the attempt-keyed occurrence id plus `routineManualTombstones` (persisted key unchanged, now also holding `:event:` ids). Readiness can change without a ledger commit, so the lane controller forwards `HostEventRuntime.subscribe` to the scheduler once the lifecycle exists. The worker brief (`routineInstructions`) is derived only from the stored occurrence because `RoutineWorkerExecutor` matches attempts by exact instruction text. A store holding an event schedule or an `:event:` tombstone is unreadable to builds without them.
- Routine ends (`expiresAt` on interval, calendar and event schedules; event `stopAfterFirstRun` with cursor `spent`) are decided by one predicate, `routineEnded`, used by the store's claim (an ended routine takes no new slot or attempt; a waiting admitted occurrence or a manual run still dispatches, and retirement waits for it), the scheduler's claim gate and its alarm. An uncertain occurrence counts as settled, so an expiry notice can precede that run's confirmed outcome. `expiresAt` is excluded from `routineSlotRule`, so extending it keeps slots and cursor; `stopAfterFirstRun` is part of the event filter, so turning it off re-anchors instead of leaving a spent cursor that would never run or retire. `spent` is written in the same store write as the one run's occurrence. Removal is the scheduler's `retire` step (outside `canDispatch`, paused routines included) calling `retireEndedRoutines`, which rechecks under the lock that every occurrence of the incarnation is terminal or uncertain with no pending delivery (`routineOccurrencesSettled`); an expired routine's notice is a terminal cancelled occurrence with trigger `{kind:"expiry"}` written in the same write as the deletion, so a crash can neither lose nor repeat it, and `routineParentInput` renders it as host text with `next-owner-turn`. A spent routine leaves quietly. Once ended, a routine has no alarm: the settlement of its last run or delivery wakes the pass. Every worker brief ends with `ROUTINE_UNATTENDED_LINE`; because `RoutineWorkerExecutor` matches attempts by exact instruction text, an occurrence dispatched by a build without that line is not found after an upgrade and is reported uncertain. Builds without these keys reject the store.
- Routine provenance: the turn-origin signal is `OwnerEvidenceLedger`'s current-run set, filled where owner input is persisted (`noteOwnerInputPersisted`, owner path only, never extension, worker or host input) and cleared at every non-retry `agent_end` (`finishCurrentTurnCue`) and after a toolkit hit, which answers owner words without a run. `knowledge-admission` reads the same set. The `routine` tool's create, update, resume and run require a source in it (`RoutineSessionController.requireOwnerTurn`, read before admission awaits; a manual run spends a worker run whose result can open another parent turn, so a wake turn cannot loop itself); pause, delete, list and get do not. A save stamps `toolAuthoredThrough` with the first source of the run (`currentTurnOpeningSource`), never a later one, so words sent while it was admitted stay unread for intake. A run a wake opened that the owner then steers into counts as the owner's from that steer. `backgroundLanes.createRoutine` is the host's own entry and passes neither check nor stamp. A run that ends announcing a retry keeps the set, and the submission's `afterRun` clears it whatever ended the submission, so a retry the `agent_end` predicted and nothing started (an abort during the backoff, a runtime stop) leaves no owner words for a later wake-started run to read. The journeys do not witness that abandoned-retry path.
- A routine definition's `lastRunAt`/`lastStatus`/`lastSummary` is a cache of its most recently claimed occurrence: every claim (scheduled, manual, or an expired one-off recorded as cancelled) sets `lastRunAt` to the trigger instant (`routineTriggerAt`) and clears `lastSummary`, and `withResult` writes the outcome and summary only when the occurrence's trigger instant equals `lastRunAt` in the same incarnation, so an older run finishing late never overwrites a newer claim. Same-millisecond claims tie, and the last written result wins. It never changes `revision` or `updatedAt`.
- Routine intake (`core/routines/routine-intake.ts`, setting `routines.automaticIntake`, default on) keeps all its state in the routine store: `routineIntakeOrigins` (consumed request keys, which outlive deletion of their routine) and `routineIntakeSessions` per parent (`through`, the createdAt watermark of read owner sources; `toolAuthoredThrough`, stamped by every `routine` tool save with the first owner source of the run it answers; `batch`, the open pass with its operation id, accounting origin, source ids and extracted requests with `done` marks). A session first met by intake starts `through` at its newest source, so old words are never read as new; words written while intake is disabled are skipped, never read later. A source at or before `toolAuthoredThrough` was answered by the model and is passed over. A request key digests the session, source, digest and the grounded excerpt offsets from `locateOwnerQuote().start/end`, so a replayed pass meets its own consumed origin: a live routine is announced again under the same delivery id, a deleted one stays gone. The extractor returns timing slots only; `routine-intake-timing.ts` checks every slot value against `locateOwnerQuote(...).stated` of the `when` excerpt (shown and inline-code text excluded) and compiles the schedule, so the model never writes cron, epochs or zones. Its word tables are the only place number, weekday, part-of-day and CI-outcome words are recognized; the daypart hours and the weekdays-only default live there, and each host choice is stored as `defaults` on the retained request (the extractor's optional `lasts` adds a 14-day `expiresAt`, plus `stopAfterFirstRun` for a one-time CI watch, as a stated default; a cadence or default longer than 300 characters drops the request because the retained batch bounds them) (so a replayed notice keeps its payload digest) and on the routine origin. Intake never cancels on foreground activity (its notice delivery must not abort itself); it only waits for an idle foreground before a pass. Its timer owner `routine-intake` is virtual in the journeys, so a pass runs only where a journey advances it. Builds without these keys reject or drop them.
- Host-event worker copies (`worker-host-event-transport.ts`) belong to the exact execution in their binding (task, attempt, lease id, fencing token). `consume` receives the consuming `StartedDelegationAttempt` and never appends another execution's copy: it routes it to `reconcileInactive`, which settles every copy whose execution `hostEventExecutionSuperseded` (`host-event-reducer.ts`: attempt left `running`, another attempt selected, lease, fence, agent or conversation moved, task closed; lease time and source readiness are excluded because renewal and catch-up restore them). An attempt-window mismatch in `reconcileHostEvent` is a `stale_execution` fence. `deliver` returns `dormant` (stay pending) for every waiting state (no control surface, no selected attempt or agent, leased, suspended) and `unavailable` (hand back) only when the selected suspended or running execution's agent is retired, not `pi`, or has no session file; the session controller never hands back on `dormant`. Capacity (`host-event-capacity.ts`) reserves remaining growth, not a fixed ceiling: an open delivery its settlement, a bound unconsumed copy its exact receipt, so binding is an ordinary admission that may be refused while the delivery stays pending. `accept` and `beginCatchUp` prune settled history inside their own transaction. Task fan-out per CI subject is refused at subscription (`replaceHostEventSubscriptions`), so accepted membership never exceeds `MAX_HOST_EVENT_TARGETS`.
- Host-event binding validity is event currency (`hostEventDeliveryEligible`), not the seal: a binding's `sourceSealDigest`, `sourceGeneration` and `scopeVersion` are provenance, so a re-seal of the same current event keeps queued copies. Subscription replacement bumps only changed rows (the task revision is the max row revision); a wake-only change moves its open deliveries' `target.subscriptionRevision` with the row, so a binding's `subscriptionRevision` may trail its target (the codec allows `<=`). `HostEventSessionController` runs two `DeliveryLane`s: tasks under one runtime work lease, root without a lease (the parent-input foreground admits its own reader; a probe admission skips the pass while the runtime is replacing and the availability notification re-drives it). Custody history is positional, not per event: a completed seal observation carries its occurrence's `sourceSequence` (`HostEventSealObservation`; the CI source fills it from the run cursor at the seal boundary, its journal keeps plain `CiCurrentObservation`s), and `source.unaccepted` keeps the merged positions below `replayFloor` the consumer never accepted (before `registration.startingSequence`, which is fixed per epoch, and inside replay gaps, minus snapshots it accepted). A position `<= retiredThrough` outside `unaccepted` with no retained event is released history (`hostEventObservationIsHistory`): a seal observation or snapshot naming it is skipped, never failed or accepted again, and `acceptCanonicalHostEvent` refuses any position `<= acceptedThrough` outside `unaccepted`. Pruning therefore writes nothing to the source. Past `MAX_HOST_EVENT_UNACCEPTED_RANGES` the two lowest ranges coalesce, so the oldest accepted positions between them may be accepted again as snapshots (a duplicate delivery, never a lost event). `hostEventRetentionPressure` (three quarters of the event, delivery or byte bound) lets `pruneWithin` waive the recall window, recorded as `pressure: true` and revalidated in the fold. Root deliveries share `proactivity.maxTurnWakesPerDay` with proactive notes: `daily-usage.ts` counts `turn`-mode `host-event` parent inputs as `hostEventTurnWakes` (the async scan prefilter must admit that line type), `parentTurnWakes` sums both kinds, and past the bound the delivery is saved as `next-owner-turn`. The root delivery id is fixed and `appendParentInput` refuses replayed metadata that differs, so `admitRootDelivery` reuses the mode of an input already saved under that id (`SessionManager.getParentInput`) and measures only a new one.
- CI host-event source (`host/ci/`): one locked journal per repository, `<git-common-dir>/pi-ci/source/journal-v2.json` (`CiSourceStore`). A session consumer is parked on stop, never deleted: its acknowledged sequence and last sealed observations stay pins, so events retained while Pi is closed replay on resume. Every claim rebuilds the consumer's position, generation and scope from the session's durable checkpoint (a restored session that accepted less resumes from its own position or an explicit gap); only the parked observations carry over. A collection failure blocks the seal only for subjects a delivery can target (HEAD, subscriptions, unaccepted events); an unsettled watcher record's subject is sealed without observation and, once run-less past `CI_REGISTRATION_GRACE_MS` with its watcher gone, written `no_run`. Only expiry (`CI_PARKED_CONSUMER_TTL_MS`, 7 days) or capacity eviction of the oldest parked consumer retires one; that consumer later resumes through a `consumer_inactive` replay gap from its session checkpoint. Run cursors are dropped only under capacity, oldest unpinned first (no retained event and no consumer observation of that run), and `retiredRuns` records exactly the dropped run numbers, so queued, in-progress and never-seen runs stay admissible. When a subject's newest listed run is retired, the provider reports `predatesRetention` instead of selecting an older run; the subject is sealed without an observation. An own-version journal that cannot be read is renamed to `.unreadable` (one copy) and a new epoch starts; a newer version throws `CiSourceVersionError` and the source stays inactive; `change()` skips the write when the canonical encoding is unchanged. The reconcile (`ci-host-event-source.ts`) begins a catch-up generation only for a new activation, a scope change, a pending handshake or gap, or after collection when pending events or changed observations require one; a reconcile that observes nothing new makes no sink call. Filesystem events reconcile only when the local input fingerprint (HEAD, branch, ref directory, record identities, subscriptions) differs from the last reconcile's inputs plus its own record writes. `gh run watch` runs through `CiCommandPort.wait` (spawn, stdout ignored, bounded stderr tail); a monitor that ends while its run still looks pending re-arms after `CI_RUN_WATCH_RETRY_MS`. The footer reads `readCiStatusView` (local files only), independent of the source.

## TUI and Terminal

- Verification candidate capture uses `captureCandidateSnapshotAsync` on the per-tool-call path; the synchronous variant is for cold event boundaries. The bot roster is a cached projection in `BackgroundLaneController`, invalidated by bot-store, lane-tracker and orchestration events.
- Orderly and fatal interactive shutdown retain process error guards until exit. Fatal shutdown reports its original error before callback-bearing cleanup and discloses host-stop failures before exiting. Cleanup uses the same stop-once owner as normal shutdown, so a reentrant exception cannot repeat terminal teardown; late promise rejections are reported on stderr while shutdown continues.
- Agent-owned message arrays publish a shared revision through the kernel mutation methods. Context estimates, cached-token queries and verification-obligation views reuse that revision; arbitrary caller arrays without a revision are not memoized. In-place message changes must pass through the owner rather than relying on array length or trailing-message identity.
- Daily usage queries return the current projection and coalesce asynchronous refreshes. Pending totals remain explicitly pending; publication checks the original session and day window. Session-file reads retain canonical header, row-size and file-revision checks, and cached disk records contain usage rather than complete conversation payloads.
- Historical Antigravity response costs can be reconstructed only from an exact upstream catalog model match, including a supported preset suffix. These are API-equivalent estimates, not subscription bills. Cumulative worker reports may include descendant models and cannot be repriced as one model; recorded non-Antigravity zero costs remain zero. Task timing without a recorded execution clock is explicitly estimated.
- `pi accounting-reconcile` defaults to the current project's retained history; `--cwd`, `--session` and `--all` select mutually exclusive scopes. It creates accounting sidecars without model calls, execution recovery or transcript changes. Its JSON report separates recorded charges from API-equivalent estimates and reports per-source failures.
- Historical worker accounting decodes only validated archival metadata, independently of current execution-policy admission. Exact parent/attempt/receipt identity and complete token/raw-cost conservation authorize response expansion. Source revisions include orchestration cursor, events, snapshots and child transcripts; changes invalidate projections. Inherited receipts use their original parent's evidence without importing its unrelated pending charges. Headerless fragments have content-bound accounting identity only, never runnable session identity.
- Task call counts union lifecycle IDs with retained response identities; an incomplete lifecycle journal does not erase older calls. Tool active intervals end at the referenced real result timestamp, never a recovery publication timestamp; synthetic unknown outcomes remain unresolved. Identified worker-only tasks keep separate rows and cannot replace the selected foreground task.
- Compaction and branch-summary response components conserve every token category and recorded cost before per-model pricing. Journal-owned checkpoints carry reference-only usage; consumers charge their semantic receipts once, using the original response date. Historical maintenance lacking model provenance keeps its recorded amount and exposes incomplete API-equivalent coverage instead of borrowing the foreground model.
- Paid-request admission materializes the session through its canonical buffered-prefix writer and rechecks ownership after persistence callbacks. ICM jobs bind their original usage owner and retain one receipt per physical response across logical cancellation; aggregate completion results never add a second charge.
- East Asian ambiguous characters occupy 2 columns on CJK-codepage consoles; width mode is probed at startup (print `·`, DSR `6n`, read the CPR column) because locale sniffing cannot detect it. ## Compaction and Long Sessions

- Context-GC's already-sent freeze (`frozenBelow`, derived from `sentPrefixCount` via `context/prefix-stability.ts`'s `frozenPrefixLength`) and its recency window (`preserveRecentMessages`/`recentStart`) protect from opposite ends of the transcript. Both marks in `ProviderRequestPrefixState` (`sentPrefixCount` for packing, `sanitizerSentPrefixCount` for dedup-erasure) are session-scoped: `Agent` carries them across prompts and the planner's post-acceptance write is monotone (`Math.max`). Below the mark nothing changes spelling except as a context-GC grid-crossing batch; a message packed once stays packed while frozen. The marks drop only when the history they count is replaced: a compaction applied between runs resets them in `_refreshAfterCompaction` (every compaction path goes through `applyResult`), an admission `replan` inside a run lowers them to the prefix the new history shares with the old by reference (`lowerPrefixMarksToSharedPrefix`, which also drops the sanitizer's erasure memory), and reload/fork/branch switches call `resetSanitizerPrefixHorizon()` (`session-tree-navigator.ts`, `sdk.ts`, `agent-session.ts`). A stale mark after a replaced history freezes the whole new history (no packing, no dedup) until it regrows past the old count. Do not tune `preserveRecentMessages` or the pack stride to chase packing gaps; they are a separate, deliberate tradeoff.
- Transcript-recall observations (memory searches and the proactive review's memory evidence) go stale only on ingests that may change captured content: a `message` or `custom_message` entry, a branch switch, a rewrite or a first flush. `SessionEntriesPersistedEvent.leafAppend.types` marks a batch that only grew the last-entry lineage; bookkeeping entries appended that way (semantic usage receipts, labels, model changes) are capture-neutral, advance no content sequence and add no index revision. A review's own usage accounting must never stale the evidence it just read.
- Token measurement is a pure read: `TokenBudget.anchor()` anneals EWMA state per call, so it runs only from the per-turn pipeline on fresh persisted usage. The compaction loop's within-threshold skip runs on cycle 1 only, using the same `shouldCompact` predicate that triggers compaction.
- Gated facts are bounded and de-noised (verb+path, deduped, capped, harness plumbing excluded); the summary budget derives from that demand; verification failure details thread to warnings, never flattened to a bare cause. The open-error classifier is signal-first (`isError` → `exitCode` → bash-only anchored text), never whole-text keyword matching.
- Verification scores exact identities: read paths as recalled items, open errors weighting operation and error identity independently; failure breakdowns cross the retry boundary into the applied checkpoint; both verification loops share one implementation.
- Long-session performance: no quadratic prefix work (append then reverse once; retain stream fragments and join once at the delimiter; lazily serialize only the transport in use). Compacted-away payloads ≥ 16KiB become disk-backed getters, and provider session resources invalidate immediately after compaction applies. Retention and UI bounds are byte-based, never count-only.
- Field-acceptance replays copy the session file to a scratch id and resume with `--no-extensions`; live session files are never replayed, and `/compact` is never passed as a `-p` prompt with extensions active.

## Local Models and Reliability

- Pi-managed Ollama registrations set `supportsDeveloperRole: false` and `maxTokensField: "max_tokens"`: Ollama’s OpenAI adapter forwards role names to the renderer and reads `max_tokens` for generation limits. Re-registration retains other per-model compatibility settings.

- Native tool-calling is serving-stack-scoped, not a property of the weights: identical GGUF can have a working tool channel under one runtime and none under another. Probe verdicts are keyed by provider/model ref; the runtime is part of model identity.
- Local-class (loopback) providers emit nothing — headers included — until the first generated token, so prefill lands in the connect phase. The adaptive resolver treats local connect as the quiet bound and raises profiled `connectMs` from measured prefill throughput; remote providers keep the stock bound. A `text-protocol` demotion probed under starved transport (stock bounds, CPU serving) is invalid evidence — re-probe with adequate bounds.
- Ollama startup readiness is proven from the exact spawned child's post-bind `Listening on <ln.Addr()>` log, not by adopting any reachable server. The reader drains bounded stdout/stderr and unreferences the pipes; after the bind proof, `/api/tags` verifies the configured model and startup fails closed when it is absent. `OllamaRuntime` canonicalizes HTTP(S) `localhost` to `127.0.0.1` once in its constructor and reuses that URL for `OLLAMA_HOST`, readiness, health and API calls; readiness then requires the exact numeric host and port logged by the child.
- `LFM3_MODELS` owns the exact Ollama tags and declared modalities; `advertisedContext` keeps the library's rounded display label as text, never a fabricated token limit. `LFM3_MINIMUM_OLLAMA_VERSION` is the shared .40.13 floor for all variants.
- `pi lfm3 import-blob` checks the source size and digest, uploads a private staged copy through the Pi-owned Ollama listener, and verifies the actual cached blob because native Ollama pull skips cached-blob hash checks. This imports bytes only: setup still fetches official registry metadata and any remaining layers. Cached inference can be offline after complete setup, while System One coordination remains remote.
- `pi lfm3 setup` keeps inference/media on Pi-managed loopback Ollama but requires configured remote System One for readiness and modality judgments; only model-generated text evidence is sent for judgment. Speech and transcription fitness share one synthesized reference clip, so failed synthesis blocks dependent audio checks; round-trip judgments do not independently establish held-out recognition. Setup requires every selected model to pass its advertised media trials; fitness trials use a temporary in-memory enabled/favorites scope and do not change the persisted interactive pool.
- General-agent admission is separate: a model must pass every router/executor surface and task-grade tool calling. Activation needs at least one generally qualified model; its primary additionally passes compaction/digest fitness and the effective ICM summary thinking level (default medium). Activation enables only the qualified subset, ordered with that primary first, and sets it for compaction/history summaries and executor/learning; it turns on System One and automatic routing, clears tier pins, disables external summary-model egress while preserving remote System One admission, and makes fresh workers inherit the qualified foreground model while retaining worker provider-order preferences. These settings publish in one global write. Media-ready specialists that fail general-agent gates remain registered for native media commands.

## Providers

- `StreamOptions.requestGuard` is synchronous and request-local. It survives wrapper spreads and is consumed by `dispatchGuardedProviderRequest` after the session chain's admission/auth/redaction waits or at a raw `stream`/`streamSimple` handoff. No await separates guard and delegate; the callback is stripped before provider code sees options. Refusal is a zero-usage terminal stream, preserving error/abort semantics and releasing admission. Provider-internal work after handoff is outside this boundary.
- A successfully parsed provider stream is delivered even if the caller abort signal races the terminal push. Mid-stream abort is the transport's job (`terminateAssistantStreamWithError`); `completeAssistantStream` must not inspect `signal.aborted`. Responses `response.output` and `output_item.done` are authoritative when incremental `added`/`delta` events were skipped — fast or coalesced xAI/OpenAI streams otherwise land as empty assistant turns. Message, reasoning, and function-call ids are attached on `output_item.added`; `done`/`response.output` must reuse that block even after `currentBlock` has moved on. Creating a second text or tool-call block for the same item stores the status sentence or tool twice.
- Degenerate collapse drops later text that repeats an earlier block. Parallel tool calls with distinct ids are kept even when name and arguments match; the Responses assembler reuses a function-call block by item/call id so the same stream item is not stored twice.
- `EventStream.end()` must settle `result()`. Ending without a `done`/`error` event is an error, never an unresolved promise. `complete()` and the text-protocol wrapper consume that settlement; a hang here is a deadlock of the turn.
- Fugu/Sakana orchestration usage detail fields are categories already included in `total_tokens`: allocate them to normalized categories for cost, never add them to `totalTokens` again.
- The Codex Responses WebSocket reports its 60-minute connection lifetime as a nested `error.code: websocket_connection_limit_reached` before response output; the request replays once on a fresh socket, only before output starts.
- ChatGPT subscription meter headers (`x-codex-*`) are reset windows, not USD spend; they are recorded as redacted diagnostics and `(sub)` cost stays token accounting.
- Antigravity account discovery resolves prices through the shared model catalog, including long-context tiers. Unknown models remain unpriced; model-family guesses must not supply rates.

## Tooling, Shell, and Extensions

- `soul.md` in the agent directory is the agent's identity (the Hermes and OpenClaw persona-file pattern): the name opens the prompt and the body sits under it as standing text. The agent may write the file, so its body goes through `scanContextFileThreats` before it becomes instructions (a finding replaces it with a notice); it has no size limit by owner decision. Read once per builder for cache stability. The loader (`projectAgentIdentity`) screens the whole document once, name and body together (`scanContextFileThreats` plus the invisible-unicode strip), before either is read; a finding replaces the whole identity, default name included, with the notice. Writes to it are owned by `SoulController` (`core/soul/`), exposed as `session.soul`. Agent writes: `ToolGateController.beforeToolCall` calls the `checkSoulWrite` dep after the operation gate (YOLO does not skip it: it guards identity, not permission) for the root agent's `write` or `edit` whose realpath is `<agentDir>/soul.md` (case-insensitive for Windows and macOS; a missing file resolves through its real existing parent plus the name, so the creating write is gated). The candidate is the whole document the call leaves: a `write`'s inline `content`, or the current file with the `edit`'s edits applied by the edit tool's own planner (`planEditsToNormalizedContent`, `applyEditMatchPlanToSource`); a `contentRef` or `payloadRef` is refused (the `write` tool only creates files, so an update of an existing soul is an `edit`), and an edit that does not apply is left to the edit tool to fail. That exact text passes `checkSoulText`; then, only while System One is available (the session's recorded engine exists), the `soul-review` decision program (override, authority, covert, external required false; identity required true; `consequence: "high"`, 20 s deadline) runs through `DecisionEngineRouter.evaluateOrFallback`. All settled good allows; any adverse blocks with the decision codes in a reason under 240 characters; an unsettled band blocks with "simplify the text" and the same text is evaluated at most twice; an evaluation that fails or times out allows, warns the owner "soul written without Jev review" and records the write `unreviewed`. Evaluations run on the recording engine, so they land on the semantic evaluation ledger like every other judgment. Owner writes (`/soul`, `/soul restore`) pass the screen and skip the judgment. Any other writer (`bash`, `python`, a script, another tool, a second process) is caught after the fact, by revision evidence rather than time. `SoulWatch` holds the last accounted-for revision of the file: its text, the sha256 of that text and a stamp (mtime, ctime, size, inode, so a timestamp-preserving write still moves ctime); an unchanged file costs one `stat`. At admission of every root tool call (`SoulController.checkWrite`, first line) the file is reconciled with that revision: a difference found while no other call is running happened between calls, so it is adopted as the owner's (recorded `owner`/`unreviewed`, never judged, never reverted; a deletion between calls is adopted as absence). `SoulController.settleWrite`, called from `ToolGateController.afterToolCall`, reconciles again: a difference relative to the admission baseline happened while calls were running and is attributed to this call or to a parallel sibling (whichever settles first reports it, in its own result). It is judged on that exact revision like a gated write: the deterministic screen, then the soul review while System One is available. Accepted: recorded `agent` with reviewer `allow` or `unreviewed` (a failed or timed-out review accepts with a warning). Adverse, unsettled or failing the screen: the accounted-for text is written back (a file that did not exist is removed), a typed `reverted` entry is recorded, the owner is warned and the model gets a notice under 240 characters appended to the call's result; a deletion is put back as a typed `removed` entry; a gated write whose text another writer replaced is reverted to the reviewed text. A verdict is valid for one revision only: it is committed under the cross-process soul lock (`state/soul/write`, `withFileLockSync`) after the file is read again, and if the digest is no longer the observed one the verdict is discarded without writing or advancing the accounting; the new revision is reconciled the same way (judged again while other calls still run, at most 3 rounds, otherwise adopted with a warning; adopted as the owner's when none runs). Text, digest, stamp and history advance together for the same verified bytes. Owner saves and restores take the same lock and refuse to replace a file that is no longer the text the owner started from. Crash order of a revert: the text to restore is stored as a version, the file is replaced atomically, then the history entry is appended; a crash after the replace leaves the right file with no entry (the next write records it as a baseline), a crash before it leaves the offending file, which the next load screens and the next session starts from. A verdict the lock refuses (`withLock` returns `held: false` after its bounded retries) is not dropped: `SoulController` keeps it as a `DeferredSettlement` (the exact revision, the accounting digest it was made against, and the commit), and `resolveDeferred` runs first at every admission and settlement. While it is pending, the revision it owns is never adopted as the owner's and no new judgment starts. It is retried; it is dropped when the file is a newer revision or an owner save/restore advanced the accounting (the authority to restore is gone, owner priority); it expires after 5 retries or 10 minutes, adopting the current text with a warning and a typed `unresolved` history entry. A revert that completes at a later admission is told to the model in the next settled call's result. Every history read-modify-write and version prune takes the same soul lock (`recordAudit`; blocked attempts included; inside a locked operation they run directly, so the lock is never acquired twice), because the history file is rewritten whole; an entry the lock refuses is kept in a bounded queue (32) and written first by the next locked operation. Remaining gaps: the offending text is on disk from its write until the end of the call (for a background process, until a later call ends), so another session can load it in that window; an external editor that writes between the last digest check and the replacement is overwritten (the lock binds only harness actors; the window is a few microseconds); a change by the owner while a root tool call is running is indistinguishable from that call's and is judged as the call's; a root call blocked after admission never settles and its running entry is dropped after an hour; deferred records (verdict, history entries) live in the process, so a crash while the lock is contended loses them (the file keeps whatever text it had, and the next session starts from it). History: `state/soul/history.jsonl`, one JSON line `{at, sha256, author, reviewer, bytes}` per write, where `sha256` and `bytes` name the text the file actually held after the write and `versions/<sha256>.md` keeps it whole (a blocked attempt is a `block` entry that keeps no text); a file found with text no kept version holds is first recorded as an `owner` baseline. The record boundary is truthful: an allowed agent write is only held by the gate (keyed by its tool call); `SoulController.settleWrite`, called from `ToolGateController.afterToolCall` (`settleSoulWrite`), records it only when the tool call succeeded and from the file as it is then on disk. If that text differs from the reviewed text it is recorded `unreviewed`, run through the deterministic screen, and the owner is warned; a failed call records nothing. Owner saves and restores record after `writeFileAtomicSync`, from the file as written. Bounded to the last 20 entries and the versions they name; `/soul restore <n>` writes version n (newest first) back through the same screen. Residual gap: another writer that changes the file between the review and the tool's own read is detected after the fact, not prevented.

- `transient-records.ts`'s `lastDurableTransientContent` returned a durable record's SUFFIXED text (raw content + `TRANSIENT_RECORD_SUPERSEDING_NOTE`), but `resolveSlotContent` compared it directly against the caller's raw, unsuffixed `slot.content`/`clearedText` — a suffixed string can never equal a bare one, so the "content unchanged, skip" path never actually fired for any transient slot (trailing or non-trailing) once a durable record of that kind existed. Append-on-change's central claim, "most turns append nothing," was false from when it was built (`c02d404d0`): a full fresh copy was appended every turn a slot had live content, changed or not. This shipped-and-reverted code never reached users, but every earlier measurement of the mechanism was taken against a version paying full-copy-per-turn cost while still showing a reference-stable prefix (the delta property was real; the token cost was not what it looked like). - The tool-failure ledger and verification-obligation transients both need to sit at the literal tail of the sent message sequence when active (`TransientRecordSlot.trailing`), but append-only and "always last" are in permanent tension: anything appended after a trailing record — including ordinary turn growth, not just another transient — displaces it for good. The resolution is re-append-to-reclaim, not reposition, and its frequency is structural, not host-transient-driven: measured over a 15-turn run (one verify-fail/verify-pass cycle, 12 ordinary reads between) with zero host transients, 14/14 turns the ledger/obligation were live fired a trailing re-append, 12/14 of those with genuinely unchanged content — displaced purely by the previous turn's ordinary assistant-reply-plus-tool-result landing after them. An adoption reopens dispatch publication for members with an unpublished terminal, because a managed-lane terminal for a lane never dispatched in that session's ledger throws. The turn helper uses the `turn` store role: no controller assertion, every write fenced by its exact turn id. Records with `parentPid`/`parentStartTime` are upgraded on read.
- Host identity (`kernel/reliability/host-identity.ts`): Linux reads `/etc/machine-id` synchronously; macOS and Windows read their machine id with a bounded shell-less spawn started once by the process-matrix runtime (`warmHostIdentity()`), and records written before it finishes carry only the hostname. Never make that read synchronous on the startup path.
- Accounting obligations (`core/cost/auto-learn-accounting.ts`) record the learner (pid, host, machine id) and the owning session process (`owner`, `ownedAt`). A live owning session adopts its obligations before delivery. An obligation whose owner has been proven dead for 7 days or more is settled as `expired` (`usage: unaccounted`, or `delivered` if already confirmed, with a reason), its hold is released and it moves to `expired/` (at most 256). Records without an owner never expire until adopted. The session-lease half of the rule (every lease holder of the session dead) is not built into it yet.
- The ICM runtime lease, learning-journal publishers and reoffer claim journals use `judgeOwner`; `foreign` and `unknown` never permit takeover.
- Bash runs in persistent per-agent shell sessions (`shell-session.ts`): a nonce sentinel carries the exit code; timeout/abort/silence kills the whole session tree and the next exec respawns — state loss is by design; explicit `shellPath` or a changed per-command env falls back to per-command semantics. On Linux each command reopens the existing relay pipe through `/proc/self/fd` for independent file-status flags; duplicating the descriptor would let a child change `O_NONBLOCK` for later commands too. The session relay and detached-descendant lifetime remain unchanged. Shell discovery is process-lifetime: successful platform resolutions are cached, failures are not.
- Root bash runs git. The operator is asked only before deleting the repository, a directory that contains it, the home directory, a filesystem root, or a disk. Lane WIP git is held structurally, not by a bash classifier: the typed `worktree_sync` `git_add`/`git_commit` actions take explicit in-lane paths and a literal message, and the lane gate (G8/G10) refuses main mutation. `classifyDangerousGitBash` (quote-aware lexer) is a pure classifier with no production caller. Repository delivery poison is `RepositoryMutationObserver`, not a per-tool name list. `shared_guarded` does not contain destructive process damage. Shared-worktree process calls own a tracked process tree: bash `wait`s for job children, and a one-shot process group is empty before the tool returns. A frozen candidate that is no longer the live tree re-enters completion and reruns JEV-024. Certify-time unowned changes and a HEAD that left the admission baseline stay terminal.
- Extension load failures are isolated startup warnings, never fatal: failed factories restore shared state and dispose subscriptions; `/reload` is transactional and preserves the current runtime on a failed generation.
- Session replacement prepares cwd-bound resources while the predecessor remains live, then retires it before SDK construction. Recovery runs during construction, so preparing an SDK session early can persist a false process-loss terminal. Same-spelling resumes reload their manager after retirement; history-sensitive options belong to activation, and unused preparation owns its loader cleanup.
- Landing advances main before refreshing the hub checkout. Refresh uses a two-tree merge of the old main and tested tip, preserving unrelated staged and unstaged owner edits. A refresh or later persistence failure leaves a transaction to reconcile; ready-to-merge replay must refresh before publishing an epoch, including when the physical checkout already reached the target.
- Runtime replacement and runtime readers share `RuntimeGenerationAdmission`, keyed by `agentDir`. New work reserves a reader before readiness or durable admission; `registerInFlightWork` only records existing recovery/process ownership. A prepared foreground reader crosses replacement only through its host-owned settled-boundary handoff, retaining submission and history ownership. Accepted resource disposal is the full-reload commit boundary: later memory initialization errors retain that generation. Deferred extension messages retain their originating candidate attempt; discarded attempts report refusal, while restored-old startup and accepted-generation initialization have separate dispositions. Async callbacks created during committed lifecycle hooks reenter ordinary admission after validating their shared runtime; they retain no candidate resource or reload privilege. A user-message refusal before delivery still settles its acceptance callback once.
- Runtime admission is shared by directory, but closing is owned by each session's builder: disposing one session must not close a sibling's admission. Shutdown cancels pending input immediately and joins admitted mutations before destroying their runtime dependencies, including memory. Awaiting disposal from that exact writer's active candidate callback is refused before closing; a void disposal request can still initiate shutdown without waiting on itself.
- Bundle lifetime protection ends only after the outer session shutdown's required releases succeed. Run, reflection and compaction settlement still use bounded waits, but a timeout is disclosed and quit still resolves: the bundle stays protected until the late run, reflection or compaction has physically ended, then releases (never earlier, and never held to process exit); a partially throwing constructor is protected on a conservative basis. This does not cancel physical work. Bridge-release errors preserve the runtime's active/restored/committed disposition rather than triggering fatal UI handling solely for retained protection.
- SessionManager physical mutations enter bundle admission before the transcript lock and before target-directory or staging-file creation. Existing-file appends omit `O_CREAT`; fresh prefixes use `wx`, and fork creation holds one lock through header and suffix. Loading captures a stable file revision; tail repair and migration/empty-file rewrites compare it again under the write lock. New branch publication cannot replace an existing destination. The guarantees require participating writers; external filesystem changes are not serialized by these advisory locks.
- An enrolled worker writes only inside its calling view's exact busy-claim scope, bound to the active transcript lock, birth parent, specialization and file revision. It permits existing-file appends; initial enrollment has a separate one-row scope inside ordinary bundle admission. Every physical append rechecks the claim. Scopes expire synchronously and never live on shared parsed cores. This permits admitted completion after foreground deletion while refusing new allocation/claim. Missing birth metadata, filesystem aliases and unknown hardlinks are refused; read-only inspection remains available.
- Worker canonical opens and reloads after an uncertain write require existing current-version history: malformed JSON, invalid UTF-8, oversized rows and unterminated tails refuse the load rather than disappear from its evidence. They never initialize missing or empty files. Ordinary root opens retain tolerant viewing and maintenance. Unenrolled worker mutation validates the current parsed revision and absence of durable enrollment, so deleting only the metadata envelope cannot bypass claim authority. Enrollment caches bind the header object as well as entry count.
- Strict history reloads detach their cold-payload indexes and restore the complete prior in-memory view, navigation revision and write fence if loading fails. Existing lazy payloads retain their original indexes. This rollback applies only where loading cannot write repairs; ordinary writable maintenance has separate physical outcomes. Successful reload still selects the physical tail and does not itself authorize owner-input reconciliation.
- Exclusive branch publication persists exact temporary-link identity before linking the target. Later admitted mutation reconciles only that owned temporary inode, including after process restart. Unknown extra hardlinks remain an error. A failure to refresh revision after a completed write invalidates continuation without replacing the write's result.
- Synchronous file-lock borrowing uses an exact active scope minted by the shared lock owner. Nested SessionManager writes can reuse a worker transcript lock without releasing or reacquiring it; escaped, foreign and expired scopes are rejected. Async ownership does not expose a synchronous scope.
- Session persistence notifications carry a frozen original session identity and entry IDs. Canonical rows and mandatory source/label bindings publish before observers; optional cache failures invalidate the originating caches and still announce the completed write. Serialization rechecks its original session/branch before mutation, including after callback-bearing encoding. Observers cannot add listeners to the notification already in progress.
- `SessionManager.openReadOnly` validates and projects existing history without tail repair, migration writes or missing-file creation. Worker enrollment checks use this path; writable owners retain normal open-time maintenance. Pre-v2 migration replaces entry IDs, so its payloads stay in memory until a writable rewrite persists those IDs. Read-only legacy IDs are temporary view identities and have no canonical byte locations. `flushBufferedEntries` with nothing buffered is a no-op on a read-only manager, so receipt-origin capture over an existing anchor never throws there.
- Streaming session loads validate the first physical record on their own descriptor before invoking row callbacks. The preliminary path header check is not authority for a later load; skipped malformed rows cannot promote a later header into the first record. Invalid nonempty headers yield no loaded entries and cannot trigger empty-file initialization.
- Worker storage identity, metadata codecs, specialist claims and immutable birth references live under `kernel/session`. Core orchestration imports or re-exports those same implementations; cached transcript revisions and process launch remain core-owned. Shared ICM view limits feed the birth-reference byte formulas without importing the view state machine into storage.
- Worker birth-snapshot capture takes birth-bundle admission before its capture-index lock. Snapshot creation, orphan replacement, dispatch preparation and rollback share that scope; normalization occurs before admission and read-only opening requires no mutation authority. Allocated project workers first hold the specialization lock, which only their exact preparation journal may borrow; rejected lane candidates remain unjournaled. This preserves specialization → bundle → capture ordering and prevents retained snapshot stores from recreating reserved or permanently deleted bundles.
- Root and worker mailbox writes admit the mailbox's acting parent bundle before taking the mailbox lock; project ownership is then checked under the transcript lock. Only expiry can use an exact active retention reservation, without granting ordinary admission to callbacks. Claimed or previously observed project mailboxes refuse missing or changed bindings. Quiescent context release retains its separate settlement path so a busy adopted worker can finish after deletion is requested.
- Existing worker transcript and handoff locks skip parent-directory creation. Quiescence takes bundle inspection before its mailbox lock; only acquisition-time `ENOENT` permits checking absent mailbox state under that exclusion. Known bindings and settlement errors still fail. Inspection borrows an existing bundle lock without granting ordinary mutation admission, including after permanent deletion is requested.
- Orchestration event appends admit the current parent bundle before locking the cursor. Opportunistic compaction uses the same boundary but skips deletion reservations so projection reads remain available; it never revives a retained deletion. Both lock layers honor caller retry/sleep policy. A held inspection lock can be borrowed for admission only after rechecking the deletion marker. Active worker completion uses the current parent's lifetime lease, not its transcript's immutable birth parent.
- Worker terminal-output capture and action-journal writes use current-parent bundle admission. Action-journal inspection shares the noncreating bundle-file inspection path with mailbox quiescence; an absent journal does not authorize execution. Only an initially absent file is empty history. Journal capacity is checked after replay lookup and before adding an entry, so the writer cannot publish a 65-entry file that its reader rejects.
- Persisted worker-terminal recovery keys tool calls and results by assistant entry plus provider call ID, using the canonical lifecycle identity encoder. Provider IDs may repeat in distinct turns. Result lookup still requires the durable assistant binding and matching invocation request/scope; same-assistant duplicates and incomplete evidence refuse recovery.
- Live worker callbacks scope pending/persisted tool assistants to the accepted provider request. Tool hooks and result receipts must match that request ID; snapshot/message callbacks also retain the active provider attempt. IDs reused in a later request do not skip persistence or reservation consumption. Unknown/malformed tool results still persist their pending assistant before the result, after the normal argument-repair boundary.
- Worker command receipts use request-scoped identities and stable aliases across bounded-history eviction. Report checks must match the exact command digest captured before display shortening; credentials have no digest, and historical records without one remain unverified. `run_process` command identity preserves executable/argument boundaries as JSON. Ambiguous references never select a receipt. Judging and counting share the same resolver: explicit zero exit is success, errors or nonzero exits are failures, absent outcomes remain unverified, and `not_run` or repeated references cannot inflate counts.
- Answer-claim collection walks tool calls and results in transcript order. Each assistant owns its call-ID map; duplicate IDs within that message stay ambiguous, matched results consume their call once, and retained invocation request IDs prevent replay from counting again. Unmatched results, tool-name mismatches, malformed retained receipts and invocations known not to have completed cannot establish inspection or delivery. A later request reusing a provider call ID cannot change earlier evidence. Completed operation outcomes survive later hook/projection failures; a present malformed receipt never takes the absent historical-receipt path.
- Worker report checks reach claim review as identified command receipts, never aggregate count overlays. The collector folds each at its matching invocation, checking command identity and outcome; a typed test result counts once and retains its original order. Recovered completions carry their already validated attempt transcript into review and inconclusive-item resolution; live runs retain their own full execution slice. Installed report-review failures become bounded parent-review blockers without repeating completed work.
- Parent claim windows retain messages and accepted worker receipt entries in branch order, with one tool-call matching state across intervening receipts. A turn without a work unit uses its exact opening entry rather than its latest steering message. Unknown placement of unpersisted tool evidence is refused. Worker receipts deduplicate by semantic publication identity; conflicting copies or malformed publication evidence cannot establish accepted worker credit.
- Independent verifiers bind both the subject task and its exact attempt before admission. Verdicts belong to attempts, survive task retries and share one identity resolver across recovery, fleet reservations and projections. Historical task-level verdicts are proof only when their generation is unambiguous; current dependency execution and task-evidence objective completion reject unresolved verification, while replay preserves recorded history. Late verdicts retain their evidence without reversing a newer attempt, cancellation or manual failure.
- Shared filesystem locks, atomic writes and bounded reads live in `kernel/storage`; bundle paths and lifetime/deletion coordination live in `kernel/session`. Core entry points re-export these same owners, including their lock queues and lease state. The kernel and host must never maintain separate copies of that coordination protocol.

## State-machine ownership (owner input, releases, waits, timers)

- One owner per lifecycle. Owner input is owned by `OwnerInputLedger` (`core/owner-input-ledger.ts`): an id is minted at acceptance and stamped on the message; the single Delivered commit point is the user entry being persisted (`notePersisted` from the foreground lifecycle adapter, which also writes the id into the session entry so a restore recognizes a delivered input). Owner rules, the blocker clear, the owner-policy enqueue, optional-tool intent promotion and goal activation run on Delivered; every other end (withdrawn, held, cancelled, refused) is explicit and visible. Matching is by stamped id, never by text. An idle foreground hands admitted input to a delivery run (`ForegroundInputPort`), event-driven.
- Queued and own-turn image records each own an independent pin claim. Preparation pins each image before another write can prune; a pre-publication failure releases only that claim, while an uncertain publication retains it. Replacement releases only the prior record's claim. Restored unreadable references retain exact filenames across rewrites, independent of retired claims; legacy identities are resolved on private metadata before publication. Image mutations share a directory lock with no contention wait; reads remain independent. Legacy sidecars expire normally and are not released by new record publication.
- Taking queued input for reuse resolves all preserved image references before withdrawing that input; failed reads leave it queued and pinned. Explicit clear still discards it. Clipboard-only images use `[Attachment #N]`, outside durable image-reference syntax. Pending labels own their bytes and suppress implicit latest-image lookup; explicit other image references remain resolvable. Failed send-now submissions return images through the same clipboard owner as take-back.
- A queue snapshot restored from history is borrowed: another parked branch can still rely on its image claim. Navigation installs the destination baseline before reconciling input, then publishes a fresh snapshot even for an unchanged queue; an empty queue over a destination with no record publishes nothing, so navigation does not move the leaf. Only successful publication makes the new record owned; later linear edits may release that claim. Borrowed claims remain until normal expiry. This preserves parked branches without retaining every intermediate historical snapshot or scanning the whole tree on each edit.
- Direct prompts retain their acceptance branch through asynchronous input hooks. An unhandled prompt claims that context before turn preparation; stale input becomes held, while a handled command may navigate normally. A prompt that queues later retains its original position and context. Its own-turn recovery record retires only after an owned queued record confirms the same input ID, or delivery/explicit withdrawal ends custody; failed or bounded-out writes retain the source record.
- Kernel queue drains retain each unstarted occurrence until its `message_start`. End-of-run restores the remainder ahead of later arrivals before notifying listeners, including batches drained to start `continue()`. Active batches remain run-owned and cannot be withdrawn through the waiting queue. Started messages never return automatically: a failing persistence callback may already have committed their history.
- A stamped owner message forces the session-prefix write before its canonical entry is published in memory and the foreground adapter announces delivery. Single messages, routed batches and copied branches share the storage owner's durability rule. Unstamped initial metadata can remain buffered; explicit in-memory sessions retain their no-file behavior. A failed pre-write admission cannot leave a duplicate buffered owner row for a retry to append again.
- A post-publication session error carries the original session, ordered entry IDs, exact source objects and durability in `SessionAppendCommittedError`. Unknown physical writes have no committed receipt. Foreground notifications settle independently without replacing that evidence; routed buffers retire the exact accepted occurrences before propagating errors, preserving newly arrived input. A full flush that receives new input exits through the existing unpersisted-input handoff instead of dropping the suffix or flushing indefinitely.
- Canonical append and buffered-flush writers can confirm a fully written suffix after an I/O error while retaining the original file lock. Confirmation requires the opened file's identity, exact final size, full suffix bytes and a stable read; initial creation covers the header and buffered prefix too. Canonical publication and notifications then run normally before the original error is reported as committed. Raw physical-only writes and partial or unreadable results retain uncertainty.
- An unknown owner-input write retains its live delivery effects and appears as `Write unresolved` without changing its stored text. Queue clear, navigation and shutdown cannot reinterpret it as undelivered or resend it. Recovery custody remains with the original session file; reopening alone does not prove safe replay, which requires canonical reconciliation of that write.
- Uncertain append evidence freezes each attempted row's parent and owner-input ID before encoding, then fingerprints the exact encoded row retained by the writer. Reconciliation must compare physical row bytes, never a reserialized mutable message or cold-loaded projection. An empty flush carries no attempted-row evidence and cannot prove anything about the entire buffered prefix.
- SessionManager owns message-to-entry identity for lifecycle callers. Ordinary-message lookups validate the current entry and exact object; custom-message bindings retain the exact canonical entry rather than its ID alone. New-session replacement invalidates the message index, and lifecycle reload discards its completed-message dedupe sets. A stale object cannot acquire authority from a reused ID in replacement history.
- Human-input replay restores only the attachments named by each saved answer, in their original order and multiplicity. New snapshots carry store-owned exact filenames and sequences; presentation clients cannot supply those references. Answer prose never invokes clipboard reference inference or latest-image fallback. Missing, unreadable or MIME-mismatched attachments remain absent with the replay's explicit loss notice.
- A resumed owner question retains its exact snapshot revision and branch anchor until foreground admission. Duplicate resumes share its preparation; navigation or disposal cancels that preparation without publishing into a replacement context. Owner interruption may checkpoint an interrupted answer, but cannot start another turn. Shutdown joins preparation only: joining the resumed model run can deadlock a runtime replacement initiated by that run.
- Auto Learn rereads skill and settings eligibility for each proposal, and reflection rereads learning policy between awaited writes. Learner-origin promotions also recheck the shared skill-evolution policy inside reflection; the outer proposal prefilter is not authority for a later write. Explicit reflection and rollback retain their own admission semantics.
- A learning batch captures session identity, file, branch generation and ancestry before asynchronous work. Navigation permanently invalidates its execution authority; ordinary descendant appends remain allowed. Nested preference admission inherits the same call context and explicit-authority flag through async-local storage. Later skill/settings edits and fallback targets use the original guard rather than recapturing a new branch.
- Forward learning audit publication has a bounded durable journal independent of the mutation. An owned intent is confirmed before the effect; the actual result and rollback are frozen before publication. A stale context retains that receipt for its original intent lineage, without repeating the effect. Publication attempts serialize their claim, append and acknowledgement; uncertain appends are reconciled from canonical session bytes. Missing receipts may be published through a healthy matching session, while malformed, conflicting or wrong-lineage evidence stays unresolved. Observer/skill-refresh failures cannot erase a returned effect result. This does not cancel an already-admitted storage commit.
- Structured organization reports creation and source removal separately. Creation without removal is a partial outcome whose rollback removes only the new OKF record; restoring hot memory requires confirmed removal and its exact target. Managed-content commit errors are reconciled under the content lock against exact bytes and pending metadata. Confirmed content with pending metadata remains an applied effect with a warning; a pending empty revision is never healed back to its deleted content. Change-notification failures are warnings, not storage failures.
- Memory cancellation is checked during preparation and at the first commit attempt. `MemoryMutationAdmission` then lets the storage owner finish that transaction's consistency writes and report its actual result. USER archive mutations share admission with the outer managed USER commit; empty-file healing, metadata reconciliation, drift backup and unchanged-index rebuilding do not admit the requested mutation. OKF creation and later hot-source removal have separate admissions, so cancellation between them retains the creation-only partial receipt. Admission is not proof that bytes landed.
- USER mutation selection reads the complete bounded archive, independently of the 400-entry prompt projection. Matching nonregular, unreadable, malformed or wrong-scope shards refuse mutation; missing storage alone means empty. Archive preparation freezes before/after bytes, validates projected and overflow-peak capacity, then writes overflow before shortening the source. Limits are 1,024 shards, 2,112 total directory entries, 1 MiB per file, 16 MiB of shard content and 50,000 preference entries. Partial I/O failures still require storage-transaction reconciliation; preparation alone does not make the multi-file operation atomic.
- Memory failure reports distinguish partial storage effects from unknown outcomes. Archive reconciliation credits matching after-images only for attempted commits, retains earlier confirmed effects when another file is unreadable/conflicting, and carries bounded evidence through the tool result. Collateral archive/index changes do not prove requested USER preference completion: both learning audits retain an incomplete reason and no generic inverse, and Auto Learn keeps it open. Unknown structured source cleanup also prohibits an inverse. Exceptions and incomplete results never justify fallback to a second memory target. These live receipts do not replace a durable transaction or authorize replay after a crash.
- USER audit acknowledgement uses a frozen intent reference and terminal report, including its original timestamp. `LearningWriteJournal.acceptExternal` confirms durable receipt custody independently of branch publication; it can reconstruct only a settled receipt obligation, never mutation authority. `LearningReceiptStore` keeps the latest 256 terminal outcomes separately from the 64 pending obligations. Memory-only publication transfers to terminal storage before retiring its pending file. Recovery reconciles exact terminal evidence after a peer retires the journal; conflicting outcomes or physical intent markers remain errors. Terminal history may be pruned only after a replacement receipt is confirmed, and failed pruning does not invalidate custody.
- The USER storage transaction lives beside its managed state as `.transaction.json`, under the existing USER content lock. Its bounded plan covers archive shards, index and the outer USER commit; attempted/completed steps and an immutable receipt survive interrupted writes. Recovery never replays content. A complete or no-effect receipt clears only after audit custody and matching current storage; partial/unknown outcomes retain an inspection barrier before mutation, startup healing and operator accept/restore. Pending USER reads remain available where readable, and unavailable projections emit diagnostics without blocking unrelated memory. A retained receipt is transferred before a peer-retired transaction is forgotten, so an older provider cannot resurrect it over newer work.
- USER prompt snapshots publish active content and archive availability together under the USER lock after explicit read/mutation/recovery boundaries. Unreadable, truncated and over-budget preferences never mean empty: static, dynamic and handoff projections preserve those distinctions, and changed-state fallback records are active content rather than clear-only markers. Archive rendering keeps 400 entries with one lookahead for truncation; mutation reads remain complete. Already-managed operator reads and active-only writes refresh the archive view too. Post-startup notices use the same active-generation reporting and revision deduplication as startup; no per-turn filesystem polling is implied.
- Auto Learn captures its launching session object and ID for handoff and usage attribution. A replacement session cannot inherit that learner's charges or queued notice. Startup reoffers likewise bind one session for the scan and stop claiming further records when that owner is replaced; already admitted work remains subject to the captured session's lifetime guards.
- Auto Learn registers a bounded durable accounting obligation before spawning and freezes its usage before parent delivery. Cleanup requires an exact physical parent receipt and a published handoff, including an explicit zero receipt for a verified zero total. Its child ledger is selected by header identity, read stably with byte/row/discovery bounds, and rejected for malformed charge rows or conflicting duplicate receipts. The source fingerprint must still match after delivery; a missing or damaged ledger never certifies zero usage. Pending obligations protect artifacts from both history and work-run retention. Failed exits retain evidence for at least seven days; elapsed retention never substitutes for a receipt.
- Accounting recovery runs at existing startup/turn boundaries, yields between records, and requires the matching session file and live session/UI owner. Hold identity is journaled before admission; known pre-spawn cancellation is journaled before cleanup. A crash in the prepared-to-spawn window remains inspection-required, while a running child needs same-host proven process absence before lost-terminal recovery. A published handoff can repair a failed accounting acknowledgement independently of its notice; notice removal also requires that acknowledgement.
- Auto Learn reoffer claims hide pending records before applying and bind a journal to a UUID, source digest, host and PID. Only same-host confirmed process absence permits unknown-outcome recovery; age, remote ownership and probe uncertainty never authorize it. Exact completed outcomes retry publication only. Handoff writes, claim transitions and retention share one store. A notice marker precedes final publication and remains until the parent accepts its next-turn message; queue admission is not durable transcript consumption. Recovered notices have separate capacity from fresh applications. A durable scan cursor advances through held, terminal and malformed records in bounded batches. Legacy identity-free claims remain inspection-required.
- Learning audit IDs are unique effect identities, never counts of prior records. Concurrent rollback requests for one ID share its active execution; historical duplicate IDs are refused as ambiguous before any inverse runs. Rollback confirms a bounded intent before executing, retains known success for receipt-only retries, and requires a valid intent-to-applied chain after restart. An intent without proven completion requires inspection, including when an inverse reported failure after possible partial effects. Branch changes defer publication; buffered session entries never count as physical proof. In-memory sessions provide process-lifetime protection only.
- Skill promotion records its normalized name and exact definition digest. Digest-bearing rollback archives only that `SKILL.md`, preserving supporting files; a versioned archive marker precedes the move and allows definition-only restore without replacing an active definition. Name-only manual curation retains whole-directory semantics. Promotion, repair, archive and restore share locks keyed by physical resource roots, including symlink aliases; external filesystem editors do not participate. Removing a root definition can expose nested definitions during discovery, so rollback does not imply unloading its entire subtree.
- Every release has one outcome: `core/util/resource-release.ts` (`RetainedReleases`, `AsyncRetainedReleases`, `runReleaseSteps`): released, retained (a named retry owner, capped exponential backoff on the injected `TimerPort`, a wake for dependents, a last-chance pass at shutdown) or abandoned. A release that fails while the owner shuts down keeps lease, hold and claim for the dead-owner reaper; in a live session it is retried.
- Retained-release timer failures keep resource ownership and successful-release notifications intact. Retry calls return infrastructure errors without poisoning the asynchronous queue; snapshots disclose a bounded `retryError` and never claim an unarmed delay. Disarming invalidates callback identity before clearing the timer, so a failed clear cannot block shutdown, replay a closed retry or erase a newer alarm. If allocation fails, only a later explicit retry/retain can rearm; no substitute timer or recursive retry is used.
- A goal execution (`GoalSessionController.beginExecution`) belongs to the foreground submission holding the foreground when it begins (its epoch) and ends only when that submission releases the foreground (`ForegroundRecoveryControllerDeps.onSubmissionReleased` → `endSubmissionExecution`), whatever the run's outcome; the explicit start authority ends with it. No caller ends one, and nothing ends one at `agent_end`: a run's `agent_end` may announce a retry that is then abandoned, and a turn's claim correction runs after it under the same execution.
- Background tool tasks capture their held execution's goal even after active-goal replacement. An A task cannot acquire B authority merely because B becomes current. Its terminal remains durable; continuing B requires explicit input. Genuinely unbound turns retain current-goal ownership, and intentional ended-goal adoption follows the execution lease's existing resolver.
- A background tool's cancellation terminal fences logical waiting, not physical execution. A later correlated completion retains output, execution evidence and usage while preserving canceled status and refusing passing verification; while the superseded terminal is undelivered, the new revision carries that terminal's own output (a cancellation cause included), because a resume restores and delivers only the newest snapshot. Every new terminal snapshot has a strictly increasing completion timestamp; delivery and observation match session, task and that timestamp, so reading the cancellation notice cannot consume a later result. Runtime observation is cleared for the new revision while its original goal and submission epoch remain unchanged.
- Background tool images are durable image artifacts with a manifest on the terminal record. `tool_task action=image taskId=… imageIndex=1` returns one image; this path remains available when `artifact_retrieve` is excluded. Notification text preserves numbered image positions and a retrieval hint, never the base64. Image payloads are admitted up to 64 MiB of serialized data and manifests up to 16 MiB; capture failure reports loss without claiming retention. Views above 4.5 MiB base64 are resized while stored pixels remain unchanged. Task-owned artifact references survive cache eviction and resume; lineage reads resolve inherited images. Bounded artifact reads enforce actual payload size under the artifact lock, and an unavailable local payload never falls through to an ancestor.
- ICM node publication precedes view/queue bookkeeping. A later write error can therefore leave a valid node despite a failed compaction outcome. Both failure and cancellation settlement recheck publication after locked reconciliation, returning a published outcome and emitting the node event when it exists. Missing running ownership without a published node remains an error; never resolve it by treating every absent claim as complete.
- ICM visible-record reconciliation is owned by `projection.sqlite`, whose identity and revision are bound in `root.json`. Once established, missing or replaced projection authority fails closed rather than recreating generation zero. Reconciliation preserves raw records, permanent IDs, source identities and occurrence dates; all ordinary record reads and navigation apply the same projection. Old background candidates whose sources are unavailable receive reversible neutral placeholders while unrelated history stays readable; only canonical consumption proof permits rederivation. A changed record invalidates every summary ending after its earliest changed ID, including later disjoint summaries that may have read it through their causal prefix. Tree reads and index recovery enforce this revision frontier. Compaction captures its projection revision before reading its target and prefix, then publication checks both that revision and the exact live claim under the writer lock. Superseded claims cannot publish or complete replacement work; lease changes clear cached nodes.
- ICM deferred work lives in `queue.sqlite`; `queue.json` is its schema-3 authority marker. SQLite transactions own claims, arrival generations, retry eligibility and parent insertion. Scheduling reads indexed bounded rows; failed leaves do not consume the eight running slots. Work is claimed in context-endpoint order (a leaf is its message, a parent the message after its range; a merge first at a tie): each kind names a candidate, fresh and retry alternating within the kind (stored never-attempted leaves belong to the fresh class; released work comes in endpoint order, failed work oldest failure first behind it), and the two kinds' candidates are compared by endpoint. Database schema 3 retains the endpoint indexes and adds durable recovery eligibility; schemas 1 and 2 migrate in place on open. The background-versus-arrival distinction for view batches lives in `refreshContinuousChatView`: only a message arrival commits partial batch progress, the causal view never inherits the turn view's merges, and `catchUpView`'s closing refresh is a background fit. The earliest unfinished leaf remains the causal cutoff. Legacy JSON imports stream into a provisional database, preserve the cutoff and hashed original bytes, checkpoint before rename, and publish the authority marker last. A committed database is never rebuilt from the legacy queue; interrupted marker publication is repaired only against matching legacy provenance.
- Exhausted ICM overflow and empty-reply jobs wait for a changed effective summary model, effort or prompt identity, or explicit recovery. Their failure and pending node remain durable; ordinary arrivals still retry transport and storage failures. A failed job retains its starting configuration, so an old-model result cannot impose a recovery hold on a replacement configuration.
- Every ICM view a model reads goes through `renderContinuousChatView`, which collapses the oldest sibling pairs down to the state's low mark once it passes its high mark (turn view 64/128 KB; worker birth view and compaction causal view 16/32 KB). The stored views are not caps and nothing renders one whole. The causal view once reached a compaction request as stored: unbuilt and failed parents held it at ten times its mark in a recorded session, so every later request grew with the backlog (up to 49,000 tokens against about 9,000 intended, roughly a third of that session's summary spend).
- ICM cache boundaries cover only complete four-line blocks before the first unresolved rendered node, including a collapsed parent. Host metadata carries an explicit empty prefix and each row's projection provenance. Cache diagnostics retain bounded partition/reconciliation transitions while still rejecting changed shared stable nodes without a new projection revision.
- An uncertain ICM disposition retains its exact claim and command under the lease and writer lock. Idempotent acknowledgement cannot rewind later arrivals or accept a newer attempt's state. Its receipt blocks new claims until the original matching retry consumes it. Lease release or loss discards old in-memory receipts and closes the scheduler under the project lock; a failed close retains the existing release owner and prevents reacquisition until settled.
- ICM migration markers and session attachment/settlement metadata use the same project writer lock and exact runtime lease as chat data. Session-ledger read/modify/write is one admitted transaction across host instances. Host disposal closes new startup, joins any existing startup before releasing the lease, and shares one disposal promise even across synchronous callbacks. Summary-model jobs remain independent of root-turn readiness; shutdown waits for owned startup I/O rather than letting it write after replacement.
- ICM compactions are admitted through the session's isolated-completion lane, whose signal session dispose aborts well before the chat host stops (the host first lets queued records append). The runtime receives that signal as `closing`: once it aborts, nothing new is claimed, and a port error of a running compaction is its cancellation, so the claim is released for the next owner instead of being recorded as failed and reported as `Continuous-chat compaction <node> failed: This operation was aborted`. A request admitted before the close still completes and publishes; `stop()` still aborts whatever runs at the end.
- The ICM migration completion timestamp is a validated chat timestamp at both metadata read and write. It is the cutoff for later-session recovery; damaged values must reject the marker rather than make every later session look ineligible.
- ICM lease acquisition owns its exact token and exit cleanup before publication, since rename can succeed before directory flush reports failure. Failed acquisition uses the normal token-checked release outside the project lock; uncertain cleanup remains with the existing retry owner. A refused acquisition never releases another attempt's lease.
- Closing an ICM host aborts its startup listing/import/recovery. Cancellation is checked after source reads and before metadata admission, never recorded as a malformed or forgotten session; admitted writes finish before shutdown releases their lease. Legacy session reads own their descriptor and stream, with input errors propagated by stream iteration. Headerless validation streams through the same parser. Listing yields between file batches so synchronous header reads do not starve cancellation. Import reads only the permanent forget view, not the full summary tree; individual synchronous filesystem calls and an already-running forget read still settle normally.
- Memory activation owns cancellation before an ICM host exists. Supersession and shutdown abort opening through lease admission, index recovery, queue migration and session attachment; the runtime releases its lease only after recovery unwinds. Recovery scans yield between bounded batches. An admitted atomic write or SQLite promotion finishes before reporting cancellation, and a promoted database remains authoritative. This opening signal never owns a retained live chat. Single synchronous decodes, allocations, view construction and SQLite calls still settle normally; cancellation does not impose aggregate storage bounds.
- Message and summary journal recovery share a descriptor-owned streaming reader with exact byte offsets. It retains one read chunk plus the largest complete record, not a full journal's text. A backward LF scan locates an incomplete tail without buffering it. Only successful parsing and unchanged descriptor/path identity permit tail truncation, using a separately validated write descriptor; healthy journals require read access only. Metadata maps and an individual record still have their own memory cost.
- Key-index recovery and growth rebuild from the authoritative message-index rows through fixed-size input chunks and an 8 MiB page-cache bound. Colliding digests retain each physical row's message ID. Dirty pages flush before eviction and atomic publication; the source descriptor and path must still match before rename. Only a zero-row rebuild permits an absent source. Positioned journal/index transfers share exact short-I/O handling. Large tables can trade additional disk I/O for bounded memory; aggregate journal metadata remains separate.
- ICM import validates the listed session header on the descriptor it actually reads before yielding any entries. Headerless sources bind their exact validated file revision. Each read stops at its opening size and checks for revision changes at the end; a changed source retries explicitly. The shared session-line character limit bounds decoding, with overflow treated as unavailable input rather than skipped history. A final revision check does not roll back earlier canonical import batches, so this is not a transactional snapshot against arbitrary in-place writers.
- ICM knowledge has one judge selection, re-read on every call: a bound System One, otherwise `SessionKnowledgeJudge` (the collection model through `StructuredLlmDecisionEngine`, offered to knowledge only). The judge is memoized per model and usage owner because admission fences on engine identity; a new instance mid-admission is a context change. Every judgment offers the same `submit_judgment` definition (`STRUCTURED_JUDGMENT_SUBMISSION_SCHEMA`, an answer list) and sends the program as a `cacheBoundary` block before the state, because the prompt-prefix monitor keys isolated lanes by lane kind, model and system prompt and a per-program tool schema broke that prefix on every program switch; the program's own answer schema is enforced after receipt with the same protocol error. Its judgments spend through `BoundedCompletionUsage` under the caller's `RequestSpendBudget` and origin (`knowledge-collection:<source>` for collection, `knowledge-collection:explicit:<uuid>` for the tool), so the existing per-source and per-session limits are the only counters. Admission keys its 0.9 gates on confidence provenance, not engine id: a self-reported answer is a certain 1 or 0, so inference, background forgetting and unkeyed rewrites of live facts are held (`uncalibrated_*`, `identity_ambiguous`). Forgotten identities keep no names (`entries.identity` is NULL, schema 5): `KnowledgeAdmission.screen` matches them only by `knowledgeId` digest across every kind and reach, and checks `meta.forget_fence` (over all forgets, the latest of each forget's earliest citation time; it blocks all older evidence, not only the forgotten fact's), the per-identity `evidenceFence` and forgotten sources before any paid judgment, so no forgotten subject or key ever reaches a judge. `slots()` lists live identities only. The tool-path current-turn rule reads `OwnerEvidenceLedger.isCurrentTurnSource`, an in-memory set cleared at every non-retry `agent_end` (`ReflectionController.finishCurrentTurnCue`) and on branch invalidation; it is intentionally not rebuilt on restart. Collection holds whose retry is `configuration` are re-claimed only when the configuration key (settings, cap, policy, model, engine identity and capabilities) changes, so switching the judge or a limit re-runs held work and nothing else does. `evidence:`/`context:` holds depend on the configuration key plus `store.revision()` (never on the latest owner source: a new message re-paid every held source), `accounting:unresolved` on the spending snapshot. `collection_sources.attempts` (schema 6) counts re-claims from paying holds (`accounting:` and `time:deadline` do not count; a deadline whose pass retained no new work, by `work.retainedCount()`, is `time:stalled` and counts; a `configuration:` hold resets it); at `MAX_SOURCE_RETRIES` the collector converts the hold to `configuration:retry_limit`, the price-independent bound. Background holds that only an exact id or a calibrated judge can lift (`identity_ambiguous` under a self-reported judge) use `configuration`. `KnowledgeAdmission.judge` retains admission/identity verdicts in `knowledge_work` (kind `grounding`, key = digest of program, state and engine id/model, value = content-free answers) behind the same `onRequestAdmitted` checkpoint as window grounding. `knowledge_work` `started` cells are the exactly-once guard: `read` throws `KnowledgeWorkUnresolved` for them, even after the request's charge settles, and the collector holds the source as `configuration:unresolved_work` (work ids include model/engine). Only the beginning caller, when its own request ended NOT aborted, calls `work.settle(id)`, which retires the cell (outcome NULL; `forgotten` only for the forget barrier) if `hasUsageReceipt(requestId)` (session `SemanticUsageDelivery`: not unresolved and held or canonical), i.e. a received, measured failure. Never release on read or on a receipt that arrives later: an aborted request's late reply is measured (the harness provider reports 24 tokens by default) and recorded on reopen, yet its result was never received (journey 1 long-collection `long-unresolved-refuses-replay`; releasing there issued an unscripted extraction). Long-source `requested` is true only from windows judged `explicit`. An unpriced model is refused before configuration enables collection (`model_unpriced`), never by a later spending hold.
- Shown-versus-stated owner text has one owner: `ownerShownRegions` in `core/learning/owner-evidence-ledger.ts`, computed once on the untrimmed original (quotation pairs by position, fences, indented code, blockquotes, quote elements, inline code). `locateOwnerQuote` maps matches on normalized text back through a per-code-unit origin map, because lowercasing and whitespace collapse change lengths; never match on one string and test regions on another. `isShownSpan` and `locateOwnerQuote` are shared with other owner-quote consumers, so their offsets stay original-text offsets. The fact-to-quote tie (`ownerCitationRefusal`, `core/memory/knowledge-citation.ts`) runs in both `KnowledgeAdmission.change` and `KnowledgeGrounding.candidate`, before any paid judgment; inline code counts as the owner's words there so identifiers in a stated sentence survive.
- `/knowledge` (`modes/interactive/knowledge-commands.ts`) reads through `MemoryOperatorPort.getKnowledgeOwnerControls()`, which exposes the canonical store and scope, and mutates only through `KnowledgeAdmission.ownerCommand` (built by `getKnowledgeAdmission`, so the same `assertCurrent` guard, store fences and receipts apply). An owner command needs no judge, because the owner named the exact record and revision and confirmed the result. Its citation is `owner-command:<operation id>` with the typed command as quote, the session id, and `at = max(now, lastEvidencedAt + 1ms)`, so forget's newer-than check and the put fence always order it after the revision the owner confirmed. Only `ownerCommand` mints that prefix, and the citation is never written to `OwnerEvidenceLedger`, so tool and collector citations still resolve only to original owner messages. The operation id is the canonical digest of action, id, expected revision, value and scope, so a retry at the same revision replays its receipt. Confirmation comes from `AgentSession.ownerConfirm`, which is defined exactly when the extension runner has a bound UI (the same condition as a tool's `ctx.hasUI`). The admission is created after the dialog, so no fence is held while the owner decides, and a revision that moved meanwhile is held as `target_changed`.
- A goal route retains its original objective identity across semantic judgments and asynchronous admission. A superseded route cannot adopt the current goal's budget, consume pending next-turn context, or publish gathered evidence under replacement authority. Previously accepted worker terminal settlement retains its historical identity and delivery route.
- Goal-bound System One stages retain the session branch anchor, exact goal ID, objective text and host lifetime through publication. Pending judgments require their observed objective text to remain current; ordinary ledger progress stays admissible. Foreground postflight validates its execution lease after task-directory admission; objective postflight validates its explicit objective there. Capturing the host goal only when a stage starts cannot identify a superseded turn. Recheck after awaited judgments and verdict observers; supersession is an objective interruption, not evaluator unavailability. Already accepted guidance remains available for the next route; mandatory verification retains its separate branch and candidate ownership.
- Completion findings (source `completion`) are replaced, not resolved: each completion evaluation makes the open completion findings exactly the ones it raises, and closes the rest as `superseded` only when both the completion and challenge stages were judged. An unavailable evaluator never closes a finding. `goal complete` is admitted while only completion findings are open; any other finding still holds it. The outcome findings name the unshown required outcomes (`completion-evidence-gaps.ts`) and are stored without the volatile probability, so the objective loop's recovery fingerprint stays stable across re-evaluations. The model has no way to waive a finding: `/verification waive <id|all> <reason>` is an owner-only command that records the closing as `waived` with its reason, and a blocked verification loop reports `owner_exit:/verification`.
- Verification receipt persistence is owned by `verification-session-storage.ts`: the reserved `pi_semantic_verification_obligations` journal type stores a complete v1 checkpoint followed by at most 31 v2 deltas. Deltas retain exact receipt IDs/order and changed bodies; every reconstructed state passes the existing snapshot validator. Replay requires the exact preceding verification entry on the selected ancestry, matching branch, consecutive sequence and bounded depth; missing or malformed links fail closed. A branch rebind writes a complete checkpoint. The single decoded cache keys manager and entry object identity, so reloads with the same entry ID invalidate it. Old full snapshots remain readable; older binaries reject a v2 head rather than silently dropping obligations. These custom records are excluded from direct ICM ingestion; reducing their disk amplification does not itself reduce summary-model calls.
- Completion wire projections keep observation bodies in the global `evidence` table and reference their canonical IDs from criterion evidence and check observations. Both completion stages receive the full table and hard constraints; missing references provide no evidence, and a recorded constraint `verified` flag is not independent proof. The richer `outcomeEvidence()` result remains the internal source for naming unmet outcomes. Reference normalization removes repeated bodies without clipping the evidence or partitioning the global challenge.
- Work-diff capture retains complete patches within its storage bound; the bounded completion projection is a preview. Completion-account file claims consume complete file diffs and citations. `cause.paths` selects complete changed-file evidence for a causal claim without excluding other files from scope review. An indivisible request above the evaluator budget remains an evidence gap; production code must not be shortened to fit it.
- Peer review distinguishes grounded defects from missing evidence. Insufficient evidence opens a separate receiving-lane obligation with the review identity and limitations; discarded quotes never establish defects. Its resolution requires fresh evidence addressing the gap or an explicitly justified narrower claim retaining the limitation, not an unchanged rerun or a successful unrelated command.
- The peer is root-only. Its tool and reviewer-required completion share one branch-owned journal; concurrent identical requests share an execution, while failed attempts remain non-reviewed. Findings survive later reviews, candidate changes and System One mode changes. With System One off, explicit root dispositions retain evidence without claiming semantic validation. Disposing an inactive failed attempt frees capacity but never supplies completion credit.

The shared access resolver checks it before credential selection and every HTTP retry; disabling after a paid response still retains its usage receipts. - Persistent bots and teams live at `state/bots/store.json`. Mutations take the shared file lock before reload and hold it through atomic publication; notifications follow lock release. Public records are detached copies. Blackboard appends use their own file lock and atomic writer, and a failed read cannot become an empty overwrite. Bot blackboards remain host-written from reports; chat bots are read-only unless created with `--write`.
- Bot-store subscriptions own a directory watcher so atomic file replacements invalidate all subscribed projections. Content digests suppress repeated local-write notifications; queued refreshes are generation-fenced and disposal closes the watcher. - Decision-ledger schema discovery and alteration run under one SQLite immediate transaction, with a busy timeout set for both Node and Bun drivers. Typed task-fit outcomes are nullable for existing rows and immutable once recorded; generic historical decisions remain advisory.
- Bot names are aliases; `BotRuntimeBindings` stores their runtime worker IDs in the owning parent session's branch snapshot. Reconfiguration preserves immutable worker grants by retiring an idle generation before binding a fresh one. Sends, controls, chat reads, roster projection and terminal blackboard updates resolve the same binding; an older generation cannot overwrite the current alias's blackboard. Worker history remains retained.
- Bot generation lookups cache typed contexts, including opaque unbound runtime IDs such as `collaboration:*`. Only persisted bot binding keys enter the strict context decoder; a managed lane's runtime ID is never a serialized bot key. Cached contexts are copied on both write and read.
- Teams are group chats with separate bot conversations and memory per group incarnation. A shared bot name does not share a transcript between groups. Group discovery, messages and replies use captured scope intersected with current membership; terminal output belongs only to its originating group. Recreated names receive a new incarnation, and unscoped legacy history stays available for root inspection rather than entering new group prompts.
- Every wait is `waitFor` (`core/util/wait.ts`): named wake sources, an abort, an explicit owner-steer decision, a deadline or watchdog bound, a typed end reason (`satisfied | timed_out | aborted | steered | disposed | unavailable`) that is reported to whoever waited, and `wait_start/progress/overdue/end` status events. Watchdog waits (foreground lease, idle, history rewrite) never give up on time because that strands work or admits two owners.
- Every recovery timer takes a `TimerPort` from the single `timers` source (`core/util/timer-port.ts`, `TimerOwner`); the harness injects virtual `HarnessTimers` (`world.timers`), so retry ladders and backoff alarms are driven deterministically. The orchestration event store stamps events on the same clock as the retry deadlines.
- A recovery decision reads its `TimerPort` clock once: the retry coordinator's backoff deadline (`wakeAt`) and the alarm armed for it use the same `now`, so the armed delay is exactly the announced backoff. Harness owner clocks are `Date.now()` plus the advanced time, so a second read inside one decision shifts the delay by real elapsed milliseconds (journey-2 R30 failed on Windows at 999 instead of 1000).
- Worker usage-persistence retries use the `worker-accounting` clock and outlive logical cancellation without keeping the process alive. The worker's physical-settlement watchdog uses `worker-settlement` and keeps its required join alive. Both clear opaque timer handles through their originating ports; timer-allocation failure reports the unscheduled receipt along with the original persistence failure.
- The accounting retry's no-wait lock policy covers both its write and synchronous publication reads, including projection compaction. The adapter scopes that storage policy until publication returns and restores it on failure; subsequent independent reads retain their normal policy.
- Worker physical timeout and resource release have separate lifetimes. A timeout remains a failed outcome; actual completion later enters the same cleanup owner and retains runtime admission until the run has physically settled; from then on a failed resource release keeps only the specialist hold, project claim and reservation (or transfers them to an existing retry owner), never the reload registration or runtime admission. Shutdown drains admitted cleanup and atomically closes further cleanup admission before disposing shared owners. Still-pending attempts retain exact lease/fence identity and resource holds, are reported as shutdown failures, and may require process restart; callbacks must not clean up through finalized owners.
- Text with paths that the model reads is bounded with `boundedText`/`boundedLine` (`core/util/bounded-line.ts`): head and tail around one elision, never cut inside a quoted path; a single path uses the path mode so no truncated head is mistaken for a real path by the alias extractor.
