# System Knowledge

Long-term reference for how this system works: invariants the code relies on and sharp edges that are
not obvious from reading it. Entries are short, present-tense, and topical — no dates, authors,
incident narratives, or progress notes. New durable facts go directly into the fitting section;
anything fully encoded in code, tests, or docs does not belong here.

## Delegation and Orchestration

- Workers are persistent specialists: conversations are keyed by `(parentSessionId, logicalAgentId)` and survive across tasks. `delegate start` with `agentId` dispatches onto an idle worker's transcript and keeps its admitted grant (`authority`/`profileId` are rejected on reuse); `list` reports per-agent `activity`. `start` must never silently ignore `agentId`.
- Clean worker-owner shutdown reserves suspended project contexts in `handoff`, including owed mailbox messages. This is same-parent continuation authority, not fleet-wide idle availability; acquisition consumes the reservation under a new generation. Goal cancellation can change task status without settling those obligations, so reclamation must not depend on still being suspended. Unsafe crash snapshots remain busy and require their original recovery proof.
- Worker retry is host-owned and evidence-gated, built on suspend/resume — there is no parallel re-dispatch path. Retries require a classified-transient failure detail (`classifyFailure`; missing or `unknown` never retries); `maxAttempts: 1` never ladders. Retry count and not-before are persisted atomically with the fenced suspension, restart recovery retains both, and terminal transitions clear the durable ladder while terminal publication clears its process timer.
- Token budgets charge `budgetedTokens()` — cache reads at `CACHE_READ_BUDGET_WEIGHT` — in both the capability gateway and the worker-tree coordinator; face-value cache-read counting turns `maxTokens` into a request counter. Grants below `MIN_VIABLE_WORKER_TOKEN_BUDGET` reject at admission; bounded failures carry `detail`; worker provider calls retry transient transport failures with jittered backoff.
- Background workers notify the foreground root by lane record plus a bounded completion event; root output is retrieved explicitly via `delegate` action `status`. Late worker output never enters an active foreground transcript — it races the foreground model.
- A blocked worker-wait restore is woken by write-reservation availability (`subscribeReservationAvailability` → `notifyAvailability`), not `subscribeStateChanges` and not a 1s poll. The 300s restore bound is a watchdog only; a reservation release must resume the waiter on the event.
- Delegated memory is a bounded query capability, not delegated file access: granted per call and by the lane profile, delivered source-labeled via `memory_read`; raw memory/state/auth paths stay denied; the mutation tool is never exposed to workers.
- The worker claim envelope is authoritative, but non-JSON reports are retained as bounded plain text with disclosure, never rejected outright. Worker tool loops resolve tool-call protocol from the lane model, never the foreground model. Concurrency admission counts running workers only; durable fleet admission separately caps depth, direct children, persistent identities, and queued dispatches, while ordinary starts and persistent-agent turns reserve mandatory-verifier headroom before durable mutation.
- Omitted `forkTurns` is `none` even for same-provider/model root workers. Explicit `all` or a turn count remains available only inside the exact provider/model boundary. Worker terminals that need parent review wake the parent through the terminal handoff; they must not queue Review now / Keep blocked, because that latch blocks automatic parent wake. Workers never spawn: `delegate` is in `WORKER_TOOL_ADAPTER_FORBIDDEN_NAMES` and a worker authority naming it is rejected at admission, so only the root starts, steers and cancels workers. A worker token/cost/wall/tool budget denial terminals the lane; it is not a per-call block the model can retry around.
- `delegate interrupt` is a halt, never a silent stop: `WorkerAgentControlCoordinator.interruptWorkerAgent` records one `WorkerLaneHalts` entry per running lane and the worker loop takes it once at its next request boundary (`AgentLoopConfig.getHaltRequest`, polled before every provider request). The loop then injects the halt message and spends one tool-free request on the model's own report; `runWorker` turns that report into a `blocked` / `worker_interrupted` claim with `parentReviewRequired` whatever status the report claims, so a halt can never read as completion, and the controller never retries a delivered halt. The terminal handoff is the only wake path, so a worker that reaches no boundary within `haltReportDeadlineMs` (120 s) is cancelled and the cancellation is what the parent hears. The halt is `delivered` when the loop takes it; one the run finishes before reaching is moot and the ordinary handoff stands. `force` keeps the old suspend-and-abort for System One's steer-and-resume (`agent-session.ts` worker control) and is not model-facing. The worker stays an idle persistent agent: a blocked/review-pending latest result with no newer task is `awaitingParent` in `list`, and the parent answers with `follow_up` on the same agentId.
- `ForegroundTerminalHandoffController.flushProviderBoundary` (`agent.beforeSteeringPoll`) folds a terminal into a request only when its known `ownerEpoch` equals the current foreground submission epoch. Unknown or different ownership takes the idle-delivery path. `WorkerNotificationCoordinator.noteAttemptOwnerEpoch` captures ownership once by exact attempt ID at fresh native dispatch, managed dispatch, or mailbox-turn creation. Names and lane IDs can repeat across execution kinds and generations; they cannot key this ownership. A refreshed pending notification retains its captured epoch. Mailbox turns capture only when the ledger returns `created: true`; replay never borrows the current epoch. Epochs stay process-local and are not written into the durable orchestration contract.
- Terminal observation acknowledges delivery, not mutation review. Bounded `delegate list` and `tasks` results carry their exact attempt IDs; only items retained in the serialized result can be observed. Waits capture `terminalAttemptIds` with their result; `terminalLaneIds` are display metadata only. Coarse activity reads and arbitrary transcript pages do not establish terminal exposure. Native agent ordering excludes managed-process attempts even when their display names collide.
- Native attempt membership is resolved by `nativeAgentIdForAttempt`: managed execution has no native owner; a bound native `agentId` takes precedence over its queued `logicalLaneId`. Tree attempt budgets, retirement blockers, queued-context recovery and native turn sequencing use this rule. Managed attempts cannot lease a native binding. Uncorrelated native turn tasks use a separate hashed namespace from managed turn tasks; correlated mailbox task identities retain their original stable hash.
- `agentLoop`'s `runLoop` return value (`newMessages`, seen by callers as `loop.result()`) has always silently disagreed with that same run's own `message_end` event stream about what it added: a message committed only into `sourceContext.messages` (the kernel's `provider-request-planner.ts`, transient records included) was invisible to `newMessages` while fully visible via emitted events. Harmless until something compared the two - `worker-attempt-executor.ts`'s `onMessage` builds its own `durableCallbackMessages` from every `message_end` (a generic catch-all, any role), then `callbackEvidencedCompletion` (same file) asserts `isDeepStrictEqual(result.messages.slice(historyLength), durableCallbackMessages)`, where `result.messages` traces to `newMessages` via `reflection-controller.ts:889`. Once the kernel's transient-record host-gap hook started emitting `message_start`/`message_end` for a committed record (turn-economics remediation, step 3), it showed up in one side and not the other, throwing `WorkerCompletionProtocolError("...suffix without exact callback evidence.")`. Fixed at the root in `agent-loop.ts`: the hook's closure now also does `newMessages.push(message)` alongside its emit calls, so the return value matches the event stream it already produces - a general agentLoop correctness fix, not a worker special case.
- RESOLVED, fixed same day: the divergence traced above (`isRawWorkerTranscriptMessage`'s stale role allowlist, off-by-one via a silently-skipped persisted entry) is fixed. Canonical predicates added to packages/coding-agent/src/kernel/messages.ts, both exhaustively checked against `AgentMessage["role"]` so a 5th kind forces reconsideration: `isWireNativeAgentMessageRole` (roles `convertToLlm` passes through unchanged - {user, assistant, toolResult}, used by anything that wants "is this already wire-Message-shaped") and `isCoreConversationMessageRole` (roles that are genuine, persistable conversation turns - {user, assistant, toolResult, custom} - deliberately disagreeing with the first on "custom", which is real conversation content once committed even though it still needs conversion before the wire). - FOLLOW-UP, same day: the fix above closed the actual bug but left the underlying hazard alive - committing a transient record into `sourceContext.messages` and recording it (for a host's own persistence to see) were still two separate statements in `provider-request-planner.ts`, which a future edit could pull apart or a new call site could add without knowing it needed both. Made structurally impossible rather than left as convention: `commitTransientRecords` (packages/coding-agent/src/kernel/transient-records.ts) is now the ONLY function that ever folds `pendingTransientRecords` into `sourceContext.messages` - it does that AND calls `onTransientRecordsCommitted` in the same call, always, so there is exactly one way to commit a transient record and it always does both halves. `provider-request-planner.ts`'s old two-statement block (`sourceContext = {...}` then a separate `await config.onTransientRecordsCommitted?.(...)`) is now one call: `sourceContext = await commitTransientRecords(sourceContext, pendingTransientRecords, config.onTransientRecordsCommitted)`. Not a hard compile-time guarantee (`sourceContext.messages` is still a plain array nothing prevents splicing by hand elsewhere), but the only convenient, discoverable path - a bypass would be a visible deviation, not an easy-to-miss two-line pattern.

## TUI and Terminal

- East Asian ambiguous characters occupy 2 columns on CJK-codepage consoles; width mode is probed at startup (print `·`, DSR `6n`, read the CPR column) because locale sniffing cannot detect it. All width math goes through `visibleWidth`/`graphemeWidth`; ambiguous width is never hardcoded to 1; probe consumers must not outlive startup (CPR is byte-identical to modified-F3 sequences); `PI_AMBIGUOUS_WIDTH=wide|narrow` overrides.

## Compaction and Long Sessions

- Context-GC's already-sent freeze (`frozenBelow`, derived from `sentPrefixCount` via `context/prefix-stability.ts`'s `frozenPrefixLength`) and its recency window (`preserveRecentMessages`/`recentStart`) protect from opposite ends of the transcript. Both marks in `ProviderRequestPrefixState` (`sentPrefixCount` for packing, `sanitizerSentPrefixCount` for dedup-erasure) are session-scoped: `Agent` carries them across prompts and the planner's post-acceptance write is monotone (`Math.max`). Below the mark nothing changes spelling except as a context-GC grid-crossing batch; a message packed once stays packed while frozen. The marks drop only when the history they count is replaced: a compaction applied between runs resets them in `_refreshAfterCompaction` (every compaction path goes through `applyResult`), an admission `replan` inside a run lowers them to the prefix the new history shares with the old by reference (`lowerPrefixMarksToSharedPrefix`, which also drops the sanitizer's erasure memory), and reload/fork/branch switches call `resetSanitizerPrefixHorizon()` (`session-tree-navigator.ts`, `sdk.ts`, `agent-session.ts`). A stale mark after a replaced history freezes the whole new history (no packing, no dedup) until it regrows past the old count. Do not tune `preserveRecentMessages` or the pack stride to chase packing gaps; they are a separate, deliberate tradeoff.
- Token measurement is a pure read: `TokenBudget.anchor()` anneals EWMA state per call, so it runs only from the per-turn pipeline on fresh persisted usage. The compaction loop's within-threshold skip runs on cycle 1 only, using the same `shouldCompact` predicate that triggers compaction.
- Gated facts are bounded and de-noised (verb+path, deduped, capped, harness plumbing excluded); the summary budget derives from that demand; verification failure details thread to warnings, never flattened to a bare cause. The open-error classifier is signal-first (`isError` → `exitCode` → bash-only anchored text), never whole-text keyword matching.
- Verification scores exact identities: read paths as recalled items, open errors weighting operation and error identity independently; failure breakdowns cross the retry boundary into the applied checkpoint; both verification loops share one implementation.
- Long-session performance: no quadratic prefix work (append then reverse once; retain stream fragments and join once at the delimiter; lazily serialize only the transport in use). Compacted-away payloads ≥ 16KiB become disk-backed getters, and provider session resources invalidate immediately after compaction applies. Retention and UI bounds are byte-based, never count-only.
- Field-acceptance replays copy the session file to a scratch id and resume with `--no-extensions`; live session files are never replayed, and `/compact` is never passed as a `-p` prompt with extensions active.

## Local Models and Reliability

- Native tool-calling is serving-stack-scoped, not a property of the weights: identical GGUF can have a working tool channel under one runtime and none under another. Probe verdicts are keyed by provider/model ref; the runtime is part of model identity.
- Local-class (loopback) providers emit nothing — headers included — until the first generated token, so prefill lands in the connect phase. The adaptive resolver treats local connect as the quiet bound and raises profiled `connectMs` from measured prefill throughput; remote providers keep the stock bound. A `text-protocol` demotion probed under starved transport (stock bounds, CPU serving) is invalid evidence — re-probe with adequate bounds.
- A reachable Ollama server does not mean its configured model is ready: `/api/tags` is verified after managed startup and the owned runtime stops on absence. Child stdio is ignored alongside `unref()` so CLI invocations exit instead of hanging on pipe handles.

## Providers

- `StreamOptions.requestGuard` is synchronous and request-local. It survives wrapper spreads and is consumed by `dispatchGuardedProviderRequest` after the session chain's admission/auth/redaction waits or at a raw `stream`/`streamSimple` handoff. No await separates guard and delegate; the callback is stripped before provider code sees options. Refusal is a zero-usage terminal stream, preserving error/abort semantics and releasing admission. Provider-internal work after handoff is outside this boundary.
- A successfully parsed provider stream is delivered even if the caller abort signal races the terminal push. Mid-stream abort is the transport's job (`terminateAssistantStreamWithError`); `completeAssistantStream` must not inspect `signal.aborted`. Responses `response.output` and `output_item.done` are authoritative when incremental `added`/`delta` events were skipped — fast or coalesced xAI/OpenAI streams otherwise land as empty assistant turns. Message, reasoning, and function-call ids are attached on `output_item.added`; `done`/`response.output` must reuse that block even after `currentBlock` has moved on. Creating a second text or tool-call block for the same item stores the status sentence or tool twice.
- Degenerate collapse drops later text that repeats an earlier block. Parallel tool calls with distinct ids are kept even when name and arguments match; the Responses assembler reuses a function-call block by item/call id so the same stream item is not stored twice.
- `EventStream.end()` must settle `result()`. Ending without a `done`/`error` event is an error, never an unresolved promise. `complete()` and the text-protocol wrapper consume that settlement; a hang here is a deadlock of the turn.
- Fugu/Sakana orchestration usage detail fields are categories already included in `total_tokens`: allocate them to normalized categories for cost, never add them to `totalTokens` again.
- The Codex Responses WebSocket reports its 60-minute connection lifetime as a nested `error.code: websocket_connection_limit_reached` before response output; the request replays once on a fresh socket, only before output starts.
- ChatGPT subscription meter headers (`x-codex-*`) are reset windows, not USD spend; they are recorded as redacted diagnostics and `(sub)` cost stays token accounting.

## Tooling, Shell, and Extensions

- Global `~/.pi/agent/AGENTS.md` (and CLAUDE.md/GEMINI.md in that directory) is always loaded into the system prompt. Repository copies are off until that directory/project opts in (`projectContextFiles: "on-demand"` via `/settings` → Project AGENTS.md). Opt-in lists paths only; `--no-context-files` skips project files. The global file is not optional.
- Tool-call repair is validate-then-repair through the named registry (`tool-repair/{registry,analyzer,repairer}.ts`): valid arguments pass unchanged, and there are no tool-specific pre-coercion shims. Delegated worker actions pass through the same choke point.
- Extension tools share a runner-scoped identity map: after a successful result, schema fields that are `*Id`/`card`/`project`/`board` (including nested `name.id` → `nameId`) fill vacant args on the next call from the same extension. Builtin tools are excluded; unresolved `needs_*`/`ambiguous*` statuses are not retained.
- Tool-failure recovery never ends a run, a turn, or a tool batch: refusal is always scoped to one exact operation and every other tool stays admissible. An operation whose last run was unproductive is admitted again once the world cursor moves — any successful tool call, or a new user turn — so corrective work always re-admits what it repaired; there are no attempt counts, probe quotas, or circuits that persist for the session. Error classes the execution-error catalogue marks transient keep one immediate identical retry per episode. Admission is reconstructed from the transcript when a new run starts with an empty gate, counting world advances in transcript order so a resumed session admits exactly what an uninterrupted one would. Memory occurrence counts are not an admission budget. Execution identity omits resource-envelope fields (`timeout` and siblings); changing only the wait bound is the same operation. `owner_authorization_required` is prompt-scoped and must never become a repetition state. Goal start/action failures return `isError` — a successful-looking `goal start failed` text is invisible to the gate. Consecutive repeated assistant lines or the same sentence repeated inside one paragraph are collapsed before the next provider turn; a toolless stream that is already looping is aborted instead of waiting for `done`.
- An errored tool result declares `errorKind`. `operation_outcome` means the tool ran the operation to completion and is reporting its own negative status (a non-zero process exit, an empty match): the tool's output reaches the model verbatim, it never becomes a `[harness]` record, and it resolves any earlier failure for that operation. `tool_failure` — the default, including for results written before the field existed — keeps the bounded harness record. A tool call the agent made is never erased from the transcript except for a superseded success or a discard-attempt directive, where the harness owns the attempt and its arguments must not reappear.
- An extension's `beforeToolCall` block (`{block: true, reason}`) looks, from a static read of `agent-loop.ts` alone, like it loses its discriminator before persistence — it does not, and this is a trap worth knowing before re-deriving it the hard way. The block branch (~1638-1652) computes `failureCode: "blocked"`, `phase: "policy"`, `diagnostic: reason` on the in-turn outcome object, distinct from a real failure's codes, and `createErrorToolResult(reason)` (~2135-2140) genuinely does hardcode `details: {}` — but that is never the result that gets persisted. Every immediate/rejected outcome routes through `finalizeRejectedToolCall`, which calls `rememberToolFailure` with those exact fields and rebuilds the result via `createToolFailureResult(record)` (`tool-failure-memory.ts:1381`), whose `details.piToolFailureMemory` carries the full record — failure code and reason both — before anything is written; `readVisibleToolFailureCode` finds the code in the visible `[harness]` text too. No ledger-conflation gap exists at this layer. A coding-agent-side durable block record (`autonomy/extension-tool-block.ts`, surfaced in `AutonomyDiagnosticSnapshot.extensionBlocks`) was built and verified end to end regardless — reason text intact at the point a consumer actually reads it — then set aside as redundant now that the primary mechanism already carries the same information: revisit only on its own merits (e.g. block-rate visibility), never as a substitute for a gap that turned out not to exist. Separately: a block's reason text was once observed missing from a live provider request — real, but traced to append-on-change's own ledger rendering on a later turn, not to this mechanism; append-on-change was reverted, then re-landed 2026-09-01 (see the two entries below), so that observation is live again and worth re-checking against the current mechanism rather than assumed moot.
- `transient-records.ts`'s `lastDurableTransientContent` returned a durable record's SUFFIXED text (raw content + `TRANSIENT_RECORD_SUPERSEDING_NOTE`), but `resolveSlotContent` compared it directly against the caller's raw, unsuffixed `slot.content`/`clearedText` — a suffixed string can never equal a bare one, so the "content unchanged, skip" path never actually fired for any transient slot (trailing or non-trailing) once a durable record of that kind existed. Append-on-change's central claim, "most turns append nothing," was false from when it was built (`c02d404d0`): a full fresh copy was appended every turn a slot had live content, changed or not. This shipped-and-reverted code never reached users, but every earlier measurement of the mechanism was taken against a version paying full-copy-per-turn cost while still showing a reference-stable prefix (the delta property was real; the token cost was not what it looked like). Verified via an isolated 3-call probe with identical content each call: pre-fix appended counts were 1,1,1, post-fix 1,0,0. Fixed at the single shared read point — strip the known suffix before comparing.
- The tool-failure ledger and verification-obligation transients both need to sit at the literal tail of the sent message sequence when active (`TransientRecordSlot.trailing`), but append-only and "always last" are in permanent tension: anything appended after a trailing record — including ordinary turn growth, not just another transient — displaces it for good. The resolution is re-append-to-reclaim, not reposition, and its frequency is structural, not host-transient-driven: measured over a 15-turn run (one verify-fail/verify-pass cycle, 12 ordinary reads between) with zero host transients, 14/14 turns the ledger/obligation were live fired a trailing re-append, 12/14 of those with genuinely unchanged content — displaced purely by the previous turn's ordinary assistant-reply-plus-tool-result landing after them. Adding a host transient that changes every other turn produced identical counts and `fullyStable: true` held at every turn regardless, so host-transient volatility is not the lever here; making informational transients "stabler" would not reduce this cost. Budget the ledger/obligation's own bounded text (bounded via `MAX_ACTIVE_FAILURES`) once per turn for the duration of any live failure/obligation window as the real, structural price of a byte-stable prefix during recovery.
- Only two things stop a wedged run, both cost guards, never the recovery gate: `maxStallTurns` (repeated normalized tool-call signature) and `maxProviderTurns`. A stall stop spends one final tool-free provider request so the model authors its own closing message; a provider turn limit or a provider error does not, and the harness never fabricates model text in either case.
- Process-tree termination has two authorizations: an owned live `ChildProcess` handle (`killTree(child)`, `killTreeNow(child)`) is authorized by ownership and never reads the host's ancestry; a bare pid (`killTreeNow(pid)`) must pass the ancestry gate, which fails closed when the observer fails. On Windows that observer is a cold PowerShell/CIM enumeration bounded at five seconds and can time out on a loaded host, so harness-owned children must always be killed by handle, never by pid.
- Bash runs in persistent per-agent shell sessions (`shell-session.ts`): a nonce sentinel carries the exit code; timeout/abort/silence kills the whole session tree and the next exec respawns — state loss is by design; explicit `shellPath` or a changed per-command env falls back to per-command semantics. Shell discovery is process-lifetime: successful platform resolutions are cached, failures are not.
- Root bash runs git. The operator is asked only before deleting the repository, a directory that contains it, the home directory, a filesystem root, or a disk. Lane WIP git is held structurally, not by a bash classifier: the typed `worktree_sync` `git_add`/`git_commit` actions take explicit in-lane paths and a literal message, and the lane gate (G8/G10) refuses main mutation. `classifyDangerousGitBash` (quote-aware lexer) is a pure classifier with no production caller. Repository delivery poison is `RepositoryMutationObserver`, not a per-tool name list. `shared_guarded` does not contain destructive process damage. Shared-worktree process calls own a tracked process tree: bash `wait`s for job children, and a one-shot process group is empty before the tool returns. A frozen candidate that is no longer the live tree re-enters completion and reruns JEV-024. Certify-time unowned changes and a HEAD that left the admission baseline stay terminal.
- Extension load failures are isolated startup warnings, never fatal: failed factories restore shared state and dispose subscriptions; `/reload` is transactional and preserves the current runtime on a failed generation.
- Session replacement prepares cwd-bound resources while the predecessor remains live, then retires it before SDK construction. Recovery runs during construction, so preparing an SDK session early can persist a false process-loss terminal. Same-spelling resumes reload their manager after retirement; history-sensitive options belong to activation, and unused preparation owns its loader cleanup.
- Landing advances main before refreshing the hub checkout. Refresh uses a two-tree merge of the old main and tested tip, preserving unrelated staged and unstaged owner edits. A refresh or later persistence failure leaves a transaction to reconcile; ready-to-merge replay must refresh before publishing an epoch, including when the physical checkout already reached the target.
- Runtime replacement and runtime readers share `RuntimeGenerationAdmission`, keyed by `agentDir`. New work reserves a reader before readiness or durable admission; `registerInFlightWork` only records existing recovery/process ownership. A prepared foreground reader crosses replacement only through its host-owned settled-boundary handoff, retaining submission and history ownership. Accepted resource disposal is the full-reload commit boundary: later memory initialization errors retain that generation. Deferred extension messages retain their originating candidate attempt; discarded attempts report refusal, while restored-old startup and accepted-generation initialization have separate dispositions. Async callbacks created during committed lifecycle hooks reenter ordinary admission after validating their shared runtime; they retain no candidate resource or reload privilege. A user-message refusal before delivery still settles its acceptance callback once.
- Runtime admission is shared by directory, but closing is owned by each session's builder: disposing one session must not close a sibling's admission. Shutdown cancels pending input immediately and joins admitted mutations before destroying their runtime dependencies, including memory. Awaiting disposal from that exact writer's active candidate callback is refused before closing; a void disposal request can still initiate shutdown without waiting on itself.

The coding-agent package ships its tracked `docs/` in the standalone release archives; verify archive contents when changing packaged documentation.

## State-machine ownership (owner input, releases, waits, timers)

- One owner per lifecycle. Owner input is owned by `OwnerInputLedger` (`core/owner-input-ledger.ts`): an id is minted at acceptance and stamped on the message; the single Delivered commit point is the user entry being persisted (`notePersisted` from the foreground lifecycle adapter, which also writes the id into the session entry so a restore recognizes a delivered input). Owner rules, the blocker clear, the owner-policy enqueue, optional-tool intent promotion and goal activation run on Delivered; every other end (withdrawn, held, cancelled, refused) is explicit and visible. Matching is by stamped id, never by text. An idle foreground hands admitted input to a delivery run (`ForegroundInputPort`), event-driven.
- Every release has one outcome: `core/util/resource-release.ts` (`RetainedReleases`, `AsyncRetainedReleases`, `runReleaseSteps`): released, retained (a named retry owner, capped exponential backoff on the injected `TimerPort`, a wake for dependents, a last-chance pass at shutdown) or abandoned. A release that fails while the owner shuts down keeps lease, hold and claim for the dead-owner reaper; in a live session it is retried.
- A goal execution (`GoalSessionController.beginExecution`) belongs to the foreground submission holding the foreground when it begins (its epoch) and ends only when that submission releases the foreground (`ForegroundRecoveryControllerDeps.onSubmissionReleased` → `endSubmissionExecution`), whatever the run's outcome; the explicit start authority ends with it. No caller ends one, and nothing ends one at `agent_end`: a run's `agent_end` may announce a retry that is then abandoned, and a turn's claim correction runs after it under the same execution.
- Background tool tasks capture their held execution's goal even after active-goal replacement. An A task cannot acquire B authority merely because B becomes current. Its terminal remains durable; continuing B requires explicit input. Genuinely unbound turns retain current-goal ownership, and intentional ended-goal adoption follows the execution lease's existing resolver.
- A background tool's cancellation terminal fences logical waiting, not physical execution. A later correlated completion retains output, execution evidence and usage while preserving canceled status and refusing passing verification. Every new terminal snapshot has a strictly increasing completion timestamp; delivery and observation match session, task and that timestamp, so reading the cancellation notice cannot consume a later result. Runtime observation is cleared for the new revision while its original goal and submission epoch remain unchanged.
- Background tool images are durable image artifacts with a manifest on the terminal record. `tool_task action=image taskId=… imageIndex=1` returns one image; this path remains available when `artifact_retrieve` is excluded. Notification text preserves numbered image positions and a retrieval hint, never the base64. Image payloads are admitted up to 64 MiB of serialized data and manifests up to 16 MiB; capture failure reports loss without claiming retention. Views above 4.5 MiB base64 are resized while stored pixels remain unchanged. Task-owned artifact references survive cache eviction and resume; lineage reads resolve inherited images. Bounded artifact reads enforce actual payload size under the artifact lock, and an unavailable local payload never falls through to an ancestor.
- ICM node publication precedes view/queue bookkeeping. A later write error can therefore leave a valid node despite a failed compaction outcome. Both failure and cancellation settlement recheck publication after locked reconciliation, returning a published outcome and emitting the node event when it exists. Missing running ownership without a published node remains an error; never resolve it by treating every absent claim as complete.
- ICM deferred work lives in `queue.sqlite`; `queue.json` is its schema-3 authority marker. SQLite transactions own claims, arrival generations, retry eligibility and parent insertion. Scheduling reads indexed bounded rows; failed leaves do not consume the eight running slots. Fresh/retry leaves alternate (stored never-attempted leaves belong to the fresh class), with an eligible parent after at most four leaf claims. The earliest unfinished leaf remains the causal cutoff. Legacy JSON imports stream into a provisional database, preserve the cutoff and hashed original bytes, checkpoint before rename, and publish the authority marker last. A committed database is never rebuilt from the legacy queue; interrupted marker publication is repaired only against matching legacy provenance.
- An uncertain ICM disposition retains its exact claim and command under the lease and writer lock. Idempotent acknowledgement cannot rewind later arrivals or accept a newer attempt's state. Its receipt blocks new claims until the original matching retry consumes it. Lease release or loss discards old in-memory receipts and closes the scheduler under the project lock; a failed close retains the existing release owner and prevents reacquisition until settled.
- A goal route retains its original objective identity across semantic judgments and asynchronous admission. A superseded route cannot adopt the current goal's budget, consume pending next-turn context, or publish gathered evidence under replacement authority. Previously accepted worker terminal settlement retains its historical identity and delivery route.
- Goal-bound System One stages retain the session branch anchor, exact goal ID, objective text and host lifetime through publication. Pending judgments require their observed objective text to remain current; ordinary ledger progress stays admissible. Foreground postflight validates its execution lease after task-directory admission; objective postflight validates its explicit objective there. Capturing the host goal only when a stage starts cannot identify a superseded turn. Recheck after awaited judgments and verdict observers; supersession is an objective interruption, not evaluator unavailability. Already accepted guidance remains available for the next route; mandatory verification retains its separate branch and candidate ownership.
- Every wait is `waitFor` (`core/util/wait.ts`): named wake sources, an abort, an explicit owner-steer decision, a deadline or watchdog bound, a typed end reason (`satisfied | timed_out | aborted | steered | disposed | unavailable`) that is reported to whoever waited, and `wait_start/progress/overdue/end` status events. Watchdog waits (foreground lease, idle, history rewrite) never give up on time because that strands work or admits two owners.
- Every recovery timer takes a `TimerPort` from the single `timers` source (`core/util/timer-port.ts`, `TimerOwner`); the harness injects virtual `HarnessTimers` (`world.timers`), so retry ladders and backoff alarms are driven deterministically. The orchestration event store stamps events on the same clock as the retry deadlines.
- Text with paths that the model reads is bounded with `boundedText`/`boundedLine` (`core/util/bounded-line.ts`): head and tail around one elision, never cut inside a quoted path; a single path uses the path mode so no truncated head is mistaken for a real path by the alias extractor.
- Recovery coverage is registered in `test/fixtures/harness/fault-matrix.ts`: every recovery row has a fault mark and a control mark per System One mode, enforced at harness close; an open row names the harness extension it needs.
