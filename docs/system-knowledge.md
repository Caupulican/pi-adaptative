# System Knowledge

Long-term reference for how this system works: invariants the code relies on and sharp edges that are
not obvious from reading it. Entries are short, present-tense, and topical — no dates, authors,
incident narratives, or progress notes. New durable facts go directly into the fitting section;
anything fully encoded in code, tests, or docs does not belong here.

## Delegation and Orchestration

- Worker execution reads its parent only through `ParentExecutionContext` (`core/delegation/parent-execution-context.ts`): environment, policy and judges, foreground-state readers, parent writes. `AgentSession`'s background-lane wiring is the foreground composition, and every member stays a lazy closure because the session swaps its manager, settings and resources on resume and reload and builds memory, the model router and tool performance after that wiring. The context's `getSessionManager()` is a read-only `ParentSessionReader`; every parent transcript append goes through `ParentWritePort` (claim and lane snapshots, notices, terminal reports, task profiles, receipt-origin anchors). The foreground port is `AgentSession`'s wiring plus the transcript writes the background-lane controller builds once (`createForegroundTranscriptWrites`), so foreground effects are the existing appends.
- A host that is not the parent records its parent writes in the attempt's outbox (`AttemptRuntimeState.parentWrites`, bound 16, events `attempt.parent_write_recorded`/`attempt.parent_write_imported`). The parent imports them when its worker lifecycle opens and on each recovery pass: per attempt in ledger order, stopping at the first write that has not landed, under the parent's session-file mutation lock. An import appends only when no entry carries the write's marker (`parentWriteId` on claims and notices, the attempt id on terminal reports) and acknowledges only after the entry is persisted, so a stop between append and acknowledgement never duplicates. A write the parent can never land (invalid record, no notice or report owner) is refused once with a warning and acknowledged, never held. A terminal is not published while its attempt still holds writes, so the claim lands before the completion it explains. Foreground attempts never record writes, so these paths find nothing there.
- Routines away (`core/routines/away-routine-host.ts`, `away-routine-admission.ts`). `AwayRoutineSupervisor` lives in the bot daemon and wakes on its routine store's change, its own `alarmAt` and the daemon's renewal tick; passes never overlap and every pass reloads the store and reads settings first. A parent is closed when no session-lease holder other than this process's `away-host` holds (the supervisor's own, including a host whose open is still in flight, since its lease is taken before the open yields) has a standing other than `dead` (an open session in the same process counts); an unreadable registry is `unknown` and refuses with a recorded reason. Admission is `awayRunRefusal` over the saved intent: only the read capabilities plus `network.http`, `process.exec` only for a `readOnly` profile (whose shell then admits only the deterministic read-only line, as with System One off), no write paths, knowledge references, objective or subscriptions; event schedules are decided away only by the parent's event feed (below), never by a host's scheduler (readiness is process-local). The pinned worker and verifier models must be known and priced (`AwayModelSource`; an unpriced one is refused, not left to fail every slot). The spend gate is arbitrated in the store's claim (`input.away`) by `routineAwayCharge` (`routine-contract.ts`), in integer micro-dollars, on the occurrence's persisted phase and no supervisor memory: claimed, dispatching, running or pending away occurrences are charged the full `maxUsdPerRun`; uncertain ones the full bound until `updatedAt` + uncertain retention + 24 h; terminal ones with a `dispatchKey` their `awaySettlement.costUsd` (else the bound) until `awaySettlement.at` + 24 h; terminal ones without a `dispatchKey` nothing. `awaySettlement` is written by `finishRoutineOccurrence`/`resolveUncertainRoutineOccurrence` from `RoutineWorkerExecutor.spentUsd` (the sum of the attempts' canonical `usageAccounting`, undefined while any attempt is live), so a daemon restart keeps it; `routineJournalHasRoom` keeps an entry while it is charged. A run is admitted while `charged + (k + 1) * maxUsdPerRun <= maxUsdPerDay`, so one run can exceed its bound by what it spends past `maxUsdPerRun` (a usage receipt recorded after the attempt ended is not in the settlement). A routine is held (`routineAwayHeld`, reason `ROUTINE_AWAY_HELD_REASON`) while an away occurrence of its incarnation is unsettled or its result is undelivered, so one run away exists per routine and the parent's next run's missed count covers the held slots. Every guard throw in dispatch becomes `RoutineAdmissionRefused`; a claim no executor took (no `executionRef`, `dispatchKey` dropped) is released to pending without `executor` by `deferRoutineOccurrence`, and `releaseLapsedAwayClaims` releases a parent's lapsed away claims when its host cannot open (`AwayParentUnavailable`). The supervisor's idle memo fingerprint (`fingerprintOf`) is the store file stamp, the `models.json` stamp, the parent's due routines, the journal room (`routineJournalRoom`) and the due routines without a journal share (`routineJournalShare`), recomputed after a claim from the post-claim occurrences; a journal or share wait whose room returns by time arms the alarm at its exit instead of relying on a store change, and a spend wait arms the retry at the store's `awayRetryAt` instead of memoizing idle. Every refusal claims nothing, leaves the slot due and is written once per reason to the routine's `awayRefusal` (`recordRoutineAwayRefusals`, which never moves `revision`) before it is reported; the parent's scheduler reports it once on open and its claim clears it. A host's model-call port is one ephemeral in-process `AgentSession` (`isChildSession: true`, in-memory manager) used only for `runIsolatedCompletion`, so provider auth is reached through the public SDK path. An away host applies only the owner's GLOBAL settings (both its settings managers are `projectTrusted: false`, trusted project or not): no project's settings (edge mode such as `yolo`, worker delegation, model policy, packages, profiles) can loosen a run nobody is watching, and the run reads no project instruction files. Both of its resource loaders set `installMissingPackages: false`, so an unattended process never installs a configured package (a package that is not installed is skipped, as in offline mode) and never races a session installing it. A partial host takes a pending worker mailbox turn by that turn's own control message (`runsControlMessage`, from the same away dispatch keys as `runsAttempt`), never by its agent: a reused specialist's run turn has no attempt until it is taken, so an agent-level test refuses the host's own run, and once the agent has a run away it would also take the parent's turns. A turn that is not the host's, and every turn behind it, stays pending for the parent. The same message test gates the rest of a partial host's mailbox work: worker reply acknowledgements and session-root replies by their request message, conversation delivery (`mailboxMessagesForConversation`) to host events and the host's own messages, and `startWorkerAgentTask` returns `worker_specialist_busy` (the scheduler releases the claim with a reported reason and the host's slot is freed) when a turn the host does not own is pending on the agent, before anything is enqueued. `runsAgent` gates only the inactive host-event transport reconciliation. A run away is bounded in the worker, not only in the claim: `runCostBound` makes its run budget port price requests (`pricesRequests`), so before each provider request `WorkerTreeBudgetCoordinator` caps `maxTokens` with `affordableOutputTokenLimit` over the request's estimated input and the run's remaining USD, and refuses (`WorkerRunCostRefusal`, a terminal `BoundedCompletionFailureError` thrown before any reservation exists) an unpriced (`costDefaulted`) model or a request whose input alone exceeds the remainder. The foreground has no `runCostBound` and is unchanged. `workerReadRoot` (away: the parent's cwd) confines a worker's read scopes to that root plus the worker's own cwd, and its read-only shell's `isDeniedPath` to the plan's read paths, judged on both the written and the canonical path. Away hosts run no System One and record no decision-ledger rows; `localCommitBranch` is undefined away. The open parent's import runs in its bot-store listener, registered before the scheduler's, so recorded writes land before that run's result is delivered.
- Event routines away (`core/routines/away-event-feed.ts`, `host/ci/ci-away-event-sources.ts`, `host/bot-daemon-entry.ts`). The supervisor keeps one `AwayEventFeed` per closed parent (never one per routine) with an enabled, pinned event routine that `awayRunRefusal` admits and whose saved origin has a session file, while the global `proactivity.ciEvents` is not false and the daemon was given `eventSources` (only the process entry `runBotDaemonEntry` injects `createCiAwayEventSources`; core never builds a host source). The feed opens the parent's own `OrchestrationEventStore` in a fresh `DurableTaskRuntime` and a `HostEventSessionController` with the parent's session id, so its `consumerId` is the session's own and the CI journal's per-consumer cursor and idempotent accept carry across the handover. `canDeliver` is false and every root/task delivery is rejected or left dormant, so deliveries stay pending for the session and the closed transcript is never written (accepted events anchor at its leaf). The factory builds the same `createCiHostRuntime` source for the parent's cwd with `role: "away-host"`; readiness is the feed's own seal. Decisions run in a `DeliveryLane` on runtime and routine-store changes: `decideAwayEventRoutines` applies `decideEventRoutine` with no claim (a `pending` occurrence) under `routineAwayHeld`, and the supervisor's next pass claims that occurrence as a recoverable run (spend gate in the claim; the host's scheduler never decides an event routine, since `schedulable` excludes them away). A non-clear connection (`host-event-source` notice) becomes the routines' `awayRefusal` (prefix `AWAY_CI_UNFOLLOWED`, then the source's own text), reported once per reason; clear removes refusals with that prefix (`clearRoutineAwayRefusals`), including those an earlier daemon left. `ELOCKED` skips a decision (the holder's save notifies the feed again). A factory that returns no source (`AwayEventFeedUnavailable`) is a refusal retried after `OPEN_RETRY_MS`. A feed closes (sources stopped, consumer parked, controller closed, then one report naming why) when the parent opens, its file is gone, no event routine may run away, the lease registry is unreadable, away settings turn off or the supervisor closes. Cost: one CI discovery loop (a ledger runtime, its fs watchers and gh polling) per closed parent, not counted in `maxParentHosts`; a source shared by several consumers is the follow-up. The feed's runtime and an away host's runtime both append to the parent's ledger in one process; every runtime operation refreshes and appends with `expectedLastOrdinal` under the store's file lock (`synchronizeIndexesUnlocked`), so ordinals never collide. A replay gap the feed commits, and the `ended` record a successor journal's registration writes (the source's `storeIdentity`), are told by the session's `HostEventSessionController` at its next construction (`observeSources`). Handback: the journal's consumer activation carries `role: "away-host"`; a session's `CiSourceStore.claim` (no role) replaces a live away activation, any other live activation throws `CiConsumerHeldError` (as does every activation-scoped call of a replaced activation). The away source on `CiConsumerHeldError`, and any source on a sink `HostEventError("closed")` (the feed's sink once the parent is open), goes dormant without retrying; the away one calls `onHeld`, the feed's `handBack` wakes the supervisor (deferred by a microtask), and the supervisor closes the feed with one report (a handed-back feed of a parent that is closed again is closed and re-opened after `OPEN_RETRY_MS`, its report once per hold). The feed also hands back when a decision finds the parent open. The away source records no GitHub interests (the session's recorded listeners stay the collection's), and its connection is stored with its redacted text and role; the session's claim returns it (`awayConnection`) and keeps it on the consumer until the session's own first `recordConnection`, and the session reports it once through `reportConnection` with the source's own scope and reason (so a state that still holds is not told twice) as a `host-event-source` harness notice with the owner's next turn.
- Acting ahead on failing CI (`core/proactivity/act-ahead-controller.ts`, records in `act-ahead-record.ts`). `BackgroundLaneController._getActAhead` builds it for the main session only; it reads the host-event feed and the orchestration store through its deps and never builds the worker lifecycle to look for a failure (`hostEvents.feed` returns nothing until the lifecycle exists, `workers.subscribe` is the store's own subscription), so a session that never delegates opens no ledger for it. A checkout without a repository or a worktree-sync engine is remembered in memory (`unworkable`) and records nothing. Failure evidence enters core only through the injected `CiFailureEvidenceReader` (`provideCiFailureEvidence`, filled by `GithubActionsCiProvider.failureEvidence`: read-only gh, 80 lines / 8 KiB, timestamps dropped, `redactKnownSecrets`), and the worker sees it inside `wrapUntrustedText`; the worker is dispatched with `turnOrigin: {k: "host-event", thirdParty: true}`, the one taint `attemptTurnOrigin` reads (no memory broker, no specialist reuse), and its terminal notification is `separate` (`ownsNotification`), so its report opens no run. Both check runs go through the worktree engine's `exec` port (`sh -c` / `cmd /c`, the land gate's path), never `execCommand`, with secret-named environment variables removed and output cut at 4 KiB; journey 3 scripts them through `VirtualShell`. Lanes are created with `base` at the failing sha and released with `confirm: "yes-discard-lane"`; the release is awaited before the episode's `settled` record so session close joins it. Each state change is a `custom` `act-ahead` entry in the root transcript: dedupe by `failureKey`, recovery on start (an episode without `settled` is finished or ended and its lane discarded), and the rolling-day bounds (`daily-usage.ts` sums `actAheadAttempts` and `actAheadUsd` from `admitted` charges and `settled` corrections across the stored sessions). The notice is one `next-owner-turn` harness notice of kind `act-ahead`, scope `<episode>` and reason `ready:<episode>` (the delivery id omits the scope, so a bare `ready` made every later episode's notice look already saved); a notice keeps its first line up to 240 characters, so the basis and the patch path come first in its text. Passes are serialized by `running`, assigned before the pass starts: a pass's synchronous prefix acknowledges the worker's terminal notification, and that store commit calls the host-event and worker subscriptions synchronously, so a pass started inline re-entered and ran a second validation of the same episode.
- Proactive note feedback (`core/proactivity/proactivity-feedback.ts`, wired in `ProactivityController.runOnce` and `gate`). Topics are code-derived when a note is delivered and saved in the note message's `details.topics[i]` (index-aligned with `details.notes`): a note whose `evidenceIds` resolve to evidence sources gets `source:<digest of sorted refs>` with a fingerprint over `ref@revision`; any other note gets the review subject (`subjectTopicKey`: `goal:<goalId>` or `conversation`) with a fingerprint over preferences, the `captureReviewContext` text and the goal summary. A note message without `topics` (stored before this) is never judged. Outcomes are decided at the next review's admission, inside the try after the first `assertCurrent` and before the daily-bound measurement, only when `feedback.enabled` and `getSystemOneEngine()` returns an engine; the records (`custom` `proactivity_feedback`, version 1, one per note message) are appended after a second `assertCurrent`, then the subject is re-checked and may return `topic_suppressed`. The reply is the first owner-spoken user message after the note's `parent_input_consumed` entry, restored through `ownerPasteRestorer` and reduced to `ownerTypedText`; no reply within `FEEDBACK_REPLY_WINDOW_MS` (or a later one) is `expired`, no letter or digit is `no_typed_words`, both settled without a request. One `proactivity.feedback` request (at most four note messages) asks two Nouls per note, `acts_on_note_<i>` and `declines_note_<i>`, read with `readAskedNoul(..., "required_true", "advisory")`; code maps the bands (hard yes on one, hard no on the other, or hard no on both) and everything else is `unknown`. A non-abort evaluator failure records `evaluator_unavailable` so the paid question is not repeated; an abort rethrows and records nothing. `foldFeedback` is the only reader: deterministic in branch order, 30-day TTL, 64 topics evicted by least recent update, `decided` holds every record's note entry id (also of records past the TTL). `gate()` folds and pays the owner-knowledge read only when the current subject key is suppressed at all; delivery folds again and drops raised notes whose topic is suppressed before `selectNotesToDeliver`. A source topic's lift is seen only by a new review's reads, so `getFeedbackState` lists it until its end; subject topics are listed only while the current subject and fingerprint match. `topic_suppressed` has no harness notice (`proactiveReviewNotice` default). Journey 1 judges note replies with System One phase declarations: the request arrives at the next review, so its Nouls are declared in the phase of the reply turn, which is still the active phase when that review runs.
- Every worker-reachable policy member is composed by a factory over readers, and the foreground passes its existing stateful instances into it (never a second custody, gate, queue or vault): `createWorkerSkillAccess` (any vault that serves reads; exclusions need the vault's `appendPolicyEntry` writer), `createWorkerRequestPlanner` (`CacheLaneGuard` owns custody, knowledge and the worker early-compaction verdicts; brain-curation appends take a per-call writer and are root-only), `createWorkerSettlementPolicy` (`SettlementJudges` over System One and the expensive-tier consult; unsettled worker items go through `ParentWritePort.recordUnsettledForOwner`, which a non-parent host must record, never drop) and `createWorkerEdgePolicy` (`sessionEdgeGrants` over `edgeRecordsOnBranch`, `createSessionOperationGate`, `ModelPoolPolicyView` over `branchPoolPolicyReader`). A worker is refused by the operation gate, never asked, so owner-word settling and `askOperator` are foreground-only. `localCommitBranch` and handoff are in-memory owner-word state never restored from the branch: a host without the owner must take the delivery binding from the routine's saved intent.
- Workers are persistent specialists: conversations are keyed by `(parentSessionId, logicalAgentId)` and survive across tasks. `delegate start` with `agentId` dispatches onto an idle worker's transcript and keeps its admitted grant (`authority`/`profileId` are rejected on reuse); `list` reports per-agent `activity`. `start` must never silently ignore `agentId`.
- Clean worker-owner shutdown reserves suspended project contexts in `handoff`, including owed mailbox messages. This is same-parent continuation authority, not fleet-wide idle availability; acquisition consumes the reservation under a new generation. Goal cancellation can change task status without settling those obligations, so reclamation must not depend on still being suspended. Unsafe crash snapshots remain busy and require their original recovery proof.
- Session-bundle deletion has one token-owned remover and a durable retention/permanent policy. Refused admission never publishes new destructive intent. Explicit deletion validates the foreground header and acquires ownership before removing history or usage journals; busy worker artifacts may remain as a reported partial outcome. Its exact reservation guards the later worker eligibility inspection. Failed or uncertain removal keeps the permanent barrier; strict foreground absence can retry an already permanent deletion. Only a settled local operation or proven-dead same-host owner can be reclaimed. Partial retention cleanup bypasses age checks only when the existing retention marker is confirmed again under lock. Admission can retire a settled retention marker after strict bundle absence; permanent and legacy ownership-free markers never reopen this way.
- Persisted SDK sessions acquire a bundle lifetime lease before asynchronous startup and session-bound recovery. Direct `AgentSession` construction requires an exact unclaimed lease from `acquireSessionBundleLease`; transfer revokes the caller's release capability. Deletion and lease admission share one lock. Replacement holds both predecessor and target through retirement, activation and rollback; admission failure cleans the candidate while preserving the active predecessor. Lease registries are bounded to 64 holders and prune only proven-dead same-host processes. A holder has a role: `session`, or `away-host` for the away supervisor's hold (`acquireSessionBundleLease(..., { role: "away-host" })`); the registry is written at schema 3 only while an away-host holder exists, so older builds read every other registry. Job-store control binds and judges only `session` holders, so an away host never makes a parent count as open for collaboration control. In-memory sessions create no lease files.
- Worker retry is host-owned and evidence-gated, built on suspend/resume — there is no parallel re-dispatch path. Retries require a classified-transient failure detail (`classifyFailure`; missing or `unknown` never retries); `maxAttempts: 1` never ladders. Retry count and not-before are persisted atomically with the fenced suspension, restart recovery retains both, and terminal transitions clear the durable ladder while terminal publication clears its process timer.
- A retained retry owns its exact attempt, pending entry and alarm generation. Timer allocation failure keeps the original deadline or failure backoff and is retried on the next recovery/capacity event, including after ordinary queue recovery is complete. Queue-full retries use capacity events. Removing or replacing an entry invalidates its callback before best-effort timer cleanup; one failed clear cannot block terminal publication or the rest of shutdown. Recovery stops between callback-bearing phases when disposed.
- Token budgets charge `budgetedTokens()` — cache reads at `CACHE_READ_BUDGET_WEIGHT` — in both the capability gateway and the worker-tree coordinator; face-value cache-read counting turns `maxTokens` into a request counter. Grants below `MIN_VIABLE_WORKER_TOKEN_BUDGET` reject at admission; bounded failures carry `detail`; worker provider calls retry transient transport failures with jittered backoff.
- Background workers notify the foreground root by lane record plus a bounded completion event; root output is retrieved explicitly via `delegate` action `status`. Late worker output never enters an active foreground transcript — it races the foreground model.
- A blocked worker-wait restore is woken by write-reservation availability (`subscribeReservationAvailability` → `notifyAvailability`), not `subscribeStateChanges` and not a 1s poll. The 300s restore bound is a watchdog only; a reservation release must resume the waiter on the event.
- Delegated memory is a bounded query capability, not delegated file access: granted per call and by the lane profile, delivered source-labeled via `memory_read`; raw memory/state/auth paths stay denied; the mutation tool is never exposed to workers.
- The worker claim envelope is authoritative, but non-JSON reports are retained as bounded plain text with disclosure, never rejected outright. Worker tool loops resolve tool-call protocol from the lane model, never the foreground model. Concurrency admission counts running workers only; durable fleet admission separately caps depth, direct children, persistent identities, and queued dispatches, while ordinary starts and persistent-agent turns reserve mandatory-verifier headroom before durable mutation.
- Omitted `forkTurns` is `none` even for same-provider/model root workers. Explicit `all` or a turn count remains available only inside the exact provider/model boundary. Worker terminals that need parent review wake the parent through the terminal handoff; they must not queue Review now / Keep blocked, because that latch blocks automatic parent wake. Workers never spawn: `delegate` is in `WORKER_TOOL_ADAPTER_FORBIDDEN_NAMES` and a worker authority naming it is rejected at admission, so only the root starts, steers and cancels workers. A worker token/cost/wall/tool budget denial terminals the lane; it is not a per-call block the model can retry around.
- Native workers communicate through `bot_message` when their immutable grant includes `workflow.message` and that tool. It uses the existing parent mailbox, current bot bindings and captured sender attempt; idle peers wake through the ordinary scheduler. Replies infer their destination from the delivered request. Messaging grants no spawning or peer access, and explicit profiles remain restrictive.
- Worker task fitness is checked at execution admission, including explicit model pins and reused mailbox turns. The complete task, actual model and effort determine the judgment; model availability and a role named worker do not establish suitability. Unconfirmed lightweight classification never counts as strong. Explicit System One disablement keeps the deterministic admission path without claiming semantic validation.
- An uncertain task-fit result names its evaluation and a fingerprint of the exact instructions, objective, model, effort and role. After an additional reasoning round, the root can record `workerTaskFit: adequate` or `inadequate` through `systemone resolve_uncertainty`. Only an explicit affirmative decision for the pending evaluation/question admits an unchanged retry; generic dispositions, other sessions and stale evaluation completions cannot. This never resolves independent verification obligations or grants execution capabilities.
- Managed and native worker profiles share `lendableToolSurface`: a parent holding bash may lend the catalogued read-only search, listing and repository tools. Explicit worker requests still intersect the worker ceiling, and a single approved route needs no model-selection request.
- Worker usage receipts carry the originating durable goal identity when available and the worker binding as provenance. Their cumulative usage can include descendants or other model calls, so binding metadata never justifies repricing the aggregate; missing historical origin stays unassigned.
- Queued worker admission keeps asynchronous directory and fitness work in the scheduler's owned preflight. Dispatch rechecks exact current fitness inputs and capacity before the synchronous execution-lease transition; a stale approval returns to preflight while retaining queue ownership.
- `delegate interrupt` is a halt, never a silent stop: `WorkerAgentControlCoordinator.interruptWorkerAgent` records one `WorkerLaneHalts` entry per running lane and the worker loop takes it once at its next request boundary (`AgentLoopConfig.getHaltRequest`, polled before every provider request). The loop then injects the halt message and spends one tool-free request on the model's own report; `runWorker` turns that report into a `blocked` / `worker_interrupted` claim with `parentReviewRequired` whatever status the report claims, so a halt can never read as completion, and the controller never retries a delivered halt. The terminal handoff is the only wake path, so a worker that reaches no boundary within `haltReportDeadlineMs` (120 s) is cancelled and the cancellation is what the parent hears. The halt is `delivered` when the loop takes it; one the run finishes before reaching is moot and the ordinary handoff stands. `force` keeps the old suspend-and-abort for System One's steer-and-resume (`agent-session.ts` worker control) and is not model-facing. The worker stays an idle persistent agent: a blocked/review-pending latest result with no newer task is `awaitingParent` in `list`, and the parent answers with `follow_up` on the same agentId.
- `ForegroundTerminalHandoffController.flushProviderBoundary` (`agent.beforeSteeringPoll`) folds a terminal into a request only when its known `ownerEpoch` equals the current foreground submission epoch. Unknown or different ownership takes the idle-delivery path. `WorkerNotificationCoordinator.noteAttemptOwnerEpoch` captures ownership once by exact attempt ID at fresh native dispatch, managed dispatch, or mailbox-turn creation. Names and lane IDs can repeat across execution kinds and generations; they cannot key this ownership. A refreshed pending notification retains its captured epoch. Mailbox turns capture only when the ledger returns `created: true`; replay never borrows the current epoch. Epochs stay process-local and are not written into the durable orchestration contract.
- Terminal observation acknowledges delivery, not mutation review. Bounded `delegate list` and `tasks` results carry their exact attempt IDs; only items retained in the serialized result can be observed. Waits capture `terminalAttemptIds` with their result; `terminalLaneIds` are display metadata only. Coarse activity reads and arbitrary transcript pages do not establish terminal exposure. Native agent ordering excludes managed-process attempts even when their display names collide.
- Terminal publication and recovery retain the captured attempt identity. A terminal lane record is reprojected only from its matching task/attempt, with parent routing from that same snapshot; missing or contradictory identities remain unresolved. Notification acknowledgement, publication fences and retry-alarm cleanup use that exact attempt. A newer attempt on the same lane cannot inherit an older terminal or lose its retry alarm to that terminal's replay.
- Worker receipt origin belongs to each dispatch, not a persistent specialist's birth context. New root work confirms its parent branch anchor on disk before durable admission; an empty or buffered session prefix is flushed through the session owner. Live navigation fences survive admission waits and callback boundaries but are never serialized. Mailbox replay, child dispatch and verifier recovery retain their original origin; missing historical origin is never inferred from the currently open branch. Capturing origin alone does not publish or accept worker evidence.
- Native worker results freeze receipt facts from their exact terminal transcript slice before awaited review. Receipt eligibility is recorded after host findings and before independent verification changes the public outcome; reviewing a partial, blocked or inconclusive claim cannot make those facts accepted. Invalid or oversized facts remain explicitly unavailable, with no truncation or reconstruction from retained transcript pages. Result status and review acknowledgement alone do not authorize receipt publication.
- Worker receipt publication is an attempt-owned obligation, independent of terminal notification and usage delivery. Required parent review binds the exact attempt, result and facts digest; required verification binds its exact verifier attempt. Startup and result, verification, review, branch and persistence events retry publication even when delegation is disabled. Parent history is checked under the existing bundle/transcript lock before append; only confirmed physical publication permits the separate runtime acknowledgement. Conflicting or duplicate publications, uncertain history, and histories beyond 64 MiB or 100,000 entries remain pending with diagnostics. In-memory publication receives no physical acknowledgement. Legacy receipts without final acceptance identity cannot establish accepted worker evidence.
- Automatic bundle retention checks pending worker content and usage receipts under its exact deletion reservation before expiring mailboxes or removing files. Unreadable projection evidence defers deletion; a fresh reservation is released so recovery remains possible. Task cancellation does not retire unpaid usage or an older result's potentially publishable facts. Exact receipt acknowledgement or immutable negative verification settles content custody. In-memory content receipts have no physical acknowledgement and therefore retain their bundle; permanent user-requested deletion remains a separate policy. Retention and runtime share projection replay, but only runtime requests compaction.
- Worker notification timers are auxiliary to delivery: an unavailable watchdog never prevents a handoff, and failed timer cleanup never reclassifies an accepted handoff. Alarm tokens invalidate before adapter cleanup, including disposal and reentrant allocation. Failed retry allocation retains outstanding records with a warning and waits for the next notification event or recovery; it cannot reject the serial delivery tail. Callback boundaries recheck disposal before further durable writes or outbox publication.
- Root and worker mailbox reads distinguish initial file absence from unavailable or malformed storage. Only initial `ENOENT` means an empty mailbox; permission/layout errors and files disappearing during a bounded read remain errors. A project mailbox frame must contain its payload, and binding may initialize missing storage but must reject a null payload. Read failures flow to existing wait/reconciliation errors rather than implying that no replies or obligations exist.
- Native attempt membership is resolved by `nativeAgentIdForAttempt`: managed execution has no native owner; a bound native `agentId` takes precedence over its queued `logicalLaneId`. Tree attempt budgets, retirement blockers, queued-context recovery and native turn sequencing use this rule. Managed attempts cannot lease a native binding. Uncorrelated native turn tasks use a separate hashed namespace from managed turn tasks; correlated mailbox task identities retain their original stable hash.

- Routine calendar schedules (`core/routines/calendar-schedule.ts`) are owned by one pure module: five-field cron, IANA zone through `Intl.DateTimeFormat`, no dependency. Wall slots map monotonically to instants: a repeated wall time runs once at its first instant, a skipped one at the transition instant, and slots collapsing onto one instant run once. The cursor stores the next slot computed at claim (`{kind:"calendar", nextAt}`); stored state and occurrence validation never re-derive slots from zone data, which may change between runtimes. An update without a zone keeps the saved one (`RoutineSessionController.persist`). The day-field rule is classic cron: a field starting with `*` (`*/2` included) is unrestricted, and OR applies only when neither starts with `*`. The forward search spans one Gregorian cycle (146,097 days, after which dates and weekdays repeat), so a satisfiable rule always finds its next slot, however sparse (29 February on a given weekday can recur decades apart), and a rule matching no date is refused at save; `nextAt: null` arises only when no representable instant remains. - The routine scheduler (`routine-scheduler-controller.ts`) never lets one failure stop a session's routines. A pass delivers pending results first (an acknowledged terminal entry is what the journal can prune), then reconciles, claims and dispatches; the claim and each occurrence's reconciliation, dispatch and delivery are isolated, a failing unit warns once per reason (`faults`) and the pass ends with a `RETRY_DELAY_MS` retry. The 256-entry occurrence journal is shared by every session of the agent dir. `routineOccurrenceSettled` decides pruning (oldest `updatedAt` first, only when room is needed): a terminal entry whose result and any earlier result are acknowledged, or an uncertain one whose uncertainty was acknowledged and that stayed uncertain for `ROUTINE_UNCERTAIN_RETENTION_MS` (7 days); a pruned uncertain run is no longer reconciled, so a late native notification of its worker takes the generic coordinator path. One routine may hold at most `ROUTINE_JOURNAL_SHARE` (32) unsettled entries (`routineHasJournalShare`): past it a clock slot or event attempt stays due and the claim returns the routine in `journalShareFull`, which the scheduler warns once (`share|<id>` fault) and leaves out of its alarm like a full journal, and a manual run is refused; cancelled notices and expiry notices are not share-checked. Without room the claim returns `journalFull` and leaves due slots and event attempts unconsumed instead of throwing, and the scheduler warns once per streak and leaves due routines out of its alarm, since only a store change (which wakes it) can make room. Alarms use `alarmAt`, which re-reads the port clock at least every `WALL_ALARM_RECHECK_MS`, because platform timers stop during suspend and do not follow wall steps. Clock faults: nothing is claimable while the clock reads before the routine's `updatedAt` (an occurrence is validated as never older than its definition, so claiming it would make the store unreadable); a manual run refuses with that reason. ## TUI and Terminal

- Verification candidate capture uses `captureCandidateSnapshotAsync` on the per-tool-call path; the synchronous variant is for cold event boundaries. The bot roster is a cached projection in `BackgroundLaneController`, invalidated by bot-store, lane-tracker and orchestration events.
- Orderly and fatal interactive shutdown retain process error guards until exit. Fatal shutdown reports its original error before callback-bearing cleanup and discloses host-stop failures before exiting. Cleanup uses the same stop-once owner as normal shutdown, so a reentrant exception cannot repeat terminal teardown; late promise rejections are reported on stderr while shutdown continues.
- Agent-owned message arrays publish a shared revision through the kernel mutation methods. Context estimates, cached-token queries and verification-obligation views reuse that revision; arbitrary caller arrays without a revision are not memoized. In-place message changes must pass through the owner rather than relying on array length or trailing-message identity.
- Daily usage queries return the current projection and coalesce asynchronous refreshes. Pending totals remain explicitly pending; publication checks the original session and day window. Session-file reads retain canonical header, row-size and file-revision checks, and cached disk records contain usage rather than complete conversation payloads.
- Historical Antigravity response costs can be reconstructed only from an exact upstream catalog model match, including a supported preset suffix. These are API-equivalent estimates, not subscription bills. Cumulative worker reports may include descendant models and cannot be repriced as one model; recorded non-Antigravity zero costs remain zero. Task timing without a recorded execution clock is explicitly estimated.
- `pi accounting-reconcile` defaults to the current project's retained history; `--cwd`, `--session` and `--all` select mutually exclusive scopes. It creates accounting sidecars without model calls, execution recovery or transcript changes. Its JSON report separates recorded charges from API-equivalent estimates and reports per-source failures.
- Historical worker accounting decodes only validated archival metadata, independently of current execution-policy admission. Exact parent/attempt/receipt identity and complete token/raw-cost conservation authorize response expansion. Source revisions include orchestration cursor, events, snapshots and child transcripts; changes invalidate projections. Inherited receipts use their original parent's evidence without importing its unrelated pending charges. Headerless fragments have content-bound accounting identity only, never runnable session identity.
- Task call counts union lifecycle IDs with retained response identities; an incomplete lifecycle journal does not erase older calls. Tool active intervals end at the referenced real result timestamp, never a recovery publication timestamp; synthetic unknown outcomes remain unresolved. Identified worker-only tasks keep separate rows and cannot replace the selected foreground task.
- Compaction and branch-summary response components conserve every token category and recorded cost before per-model pricing. Journal-owned checkpoints carry reference-only usage; consumers charge their semantic receipts once, using the original response date. Historical maintenance lacking model provenance keeps its recorded amount and exposes incomplete API-equivalent coverage instead of borrowing the foreground model.
- Paid-request admission materializes the session through its canonical buffered-prefix writer and rechecks ownership after persistence callbacks. - East Asian ambiguous characters occupy 2 columns on CJK-codepage consoles; width mode is probed at startup (print `·`, DSR `6n`, read the CPR column) because locale sniffing cannot detect it. ## Compaction and Long Sessions

- Context-GC's already-sent freeze (`frozenBelow`, derived from `sentPrefixCount` via `context/prefix-stability.ts`'s `frozenPrefixLength`) and its recency window (`preserveRecentMessages`/`recentStart`) protect from opposite ends of the transcript. Both marks in `ProviderRequestPrefixState` (`sentPrefixCount` for packing, `sanitizerSentPrefixCount` for dedup-erasure) are session-scoped: `Agent` carries them across prompts and the planner's post-acceptance write is monotone (`Math.max`). Below the mark nothing changes spelling except as a context-GC grid-crossing batch; a message packed once stays packed while frozen. The marks drop only when the history they count is replaced: a compaction applied between runs resets them in `_refreshAfterCompaction` (every compaction path goes through `applyResult`), an admission `replan` inside a run lowers them to the prefix the new history shares with the old by reference (`lowerPrefixMarksToSharedPrefix`, which also drops the sanitizer's erasure memory), and reload/fork/branch switches call `resetSanitizerPrefixHorizon()` (`session-tree-navigator.ts`, `sdk.ts`, `agent-session.ts`). A stale mark after a replaced history freezes the whole new history (no packing, no dedup) until it regrows past the old count. Do not tune `preserveRecentMessages` or the pack stride to chase packing gaps; they are a separate, deliberate tradeoff.
- Transcript-recall observations (memory searches and the proactive review's memory evidence) go stale only on ingests that may change captured content: a `message` or `custom_message` entry, a branch switch, a rewrite or a first flush. `SessionEntriesPersistedEvent.leafAppend.types` marks a batch that only grew the last-entry lineage; bookkeeping entries appended that way (semantic usage receipts, labels, model changes) are capture-neutral, advance no content sequence and add no index revision. A review's own usage accounting must never stale the evidence it just read.
- Token measurement is a pure read: `TokenBudget.anchor()` anneals EWMA state per call, so it runs only from the per-turn pipeline on fresh persisted usage. The compaction loop's within-threshold skip runs on cycle 1 only, using the same `shouldCompact` predicate that triggers compaction.
- Gated facts are bounded and de-noised (verb+path, deduped, capped, harness plumbing excluded); the summary budget derives from that demand; verification failure details thread to warnings, never flattened to a bare cause. The open-error classifier is signal-first (`isError` → `exitCode` → bash-only anchored text), never whole-text keyword matching.
- Verification scores exact identities: read paths as recalled items, open errors weighting operation and error identity independently; failure breakdowns cross the retry boundary into the applied checkpoint; both verification loops share one implementation.
- Long-session performance: no quadratic prefix work (append then reverse once; retain stream fragments and join once at the delimiter; lazily serialize only the transport in use). Compacted-away payloads ≥ 16KiB become disk-backed getters, and provider session resources invalidate immediately after compaction applies. Retention and UI bounds are byte-based, never count-only.
- Field-acceptance replays copy the session file to a scratch id and resume with `--no-extensions`; live session files are never replayed, and `/compact` is never passed as a `-p` prompt with extensions active.

## Local Models and Reliability

- Pi-managed Ollama registrations set `supportsDeveloperRole: false` and `maxTokensField: "max_tokens"`: Ollama’s OpenAI adapter forwards role names to the renderer and reads `max_tokens` for generation limits. Re-registration retains other per-model compatibility settings.

- Native tool-calling is serving-stack-scoped, not a property of the weights: identical GGUF can have a working tool channel under one runtime and none under another. Probe verdicts are keyed by provider/model ref; the runtime is part of model identity.
- Local-class (loopback) providers emit nothing — headers included — until the first generated token, so prefill lands in the connect phase. The adaptive resolver treats local connect as the quiet bound and raises profiled `connectMs` from measured prefill throughput; remote providers keep the stock bound. A `text-protocol` demotion probed under starved transport (stock bounds, CPU serving) is invalid evidence — re-probe with adequate bounds.
- Ollama startup readiness is proven from the exact spawned child's post-bind `Listening on <ln.Addr()>` log, not by adopting any reachable server. The reader drains bounded stdout/stderr and unreferences the pipes; after the bind proof, `/api/tags` verifies the configured model and startup fails closed when it is absent. `OllamaRuntime` canonicalizes HTTP(S) `localhost` to `127.0.0.1` once in its constructor and reuses that URL for `OLLAMA_HOST`, readiness, health and API calls; readiness then requires the exact numeric host and port logged by the child.

## Providers

- `StreamOptions.requestGuard` is synchronous and request-local. It survives wrapper spreads and is consumed by `dispatchGuardedProviderRequest` after the session chain's admission/auth/redaction waits or at a raw `stream`/`streamSimple` handoff. No await separates guard and delegate; the callback is stripped before provider code sees options. Refusal is a zero-usage terminal stream, preserving error/abort semantics and releasing admission. Provider-internal work after handoff is outside this boundary.
- A successfully parsed provider stream is delivered even if the caller abort signal races the terminal push. Mid-stream abort is the transport's job (`terminateAssistantStreamWithError`); `completeAssistantStream` must not inspect `signal.aborted`. Responses `response.output` and `output_item.done` are authoritative when incremental `added`/`delta` events were skipped — fast or coalesced xAI/OpenAI streams otherwise land as empty assistant turns. Message, reasoning, and function-call ids are attached on `output_item.added`; `done`/`response.output` must reuse that block even after `currentBlock` has moved on. Creating a second text or tool-call block for the same item stores the status sentence or tool twice.
- Degenerate collapse drops later text that repeats an earlier block. Parallel tool calls with distinct ids are kept even when name and arguments match; the Responses assembler reuses a function-call block by item/call id so the same stream item is not stored twice.
- `EventStream.end()` must settle `result()`. Ending without a `done`/`error` event is an error, never an unresolved promise. `complete()` and the text-protocol wrapper consume that settlement; a hang here is a deadlock of the turn.
- Fugu/Sakana orchestration usage detail fields are categories already included in `total_tokens`: allocate them to normalized categories for cost, never add them to `totalTokens` again.
- The Codex Responses WebSocket reports its 60-minute connection lifetime as a nested `error.code: websocket_connection_limit_reached` before response output; the request replays once on a fresh socket, only before output starts.
- ChatGPT subscription meter headers (`x-codex-*`) are reset windows, not USD spend; they are recorded as redacted diagnostics and `(sub)` cost stays token accounting.
- Antigravity account discovery resolves prices through the shared model catalog, including long-context tiers. Unknown models remain unpriced; model-family guesses must not supply rates.

## Tooling, Shell, and Extensions

- The shell read/write line is one walk (`walkCommand` in `core/model-router/read-only-shell-policy.ts`) over the shared tokenizer's output (`tokenizeShellCommand`, `core/tools/shell-command-parser.ts`); no raw-text regex judges a command. Its callers differ only in how they may write: the router's mutation check and System One's observational line (`readOnlyShellPrograms`) none, requirement checks (`readOnlyShellViolation` with `admitTestRuns`) only new paths, plus the project's tests and `tsc --noEmit` as check runs, a `readOnly` worker lane only its scratch directory. The tokenizer drops backslash-newline (PowerShell backtick-newline) continuations, honours `#` and `<# #>` comments, reads `2>&1` as a descriptor copy and `>&word` as a file target (`redirectTakesTarget`, which the credential guard and search parsing use too), and records command, process, arithmetic and parameter expansions found outside single quotes (`expansions`) and PowerShell `{}`, `()`, `$()`, `@()`, `@{}` bodies (`groups`), so a `|` or `;` inside a script block stays inside it. The walk splits simple commands on `; & && || | |&` and newlines and reads `for`/`while`/`until` loops, `if`, `case`, `{ }` groups and `( )` subshells structurally (`parseShellCompound` over the tokenizer's `compound` mode, which makes POSIX `(`, `)` and `;;` operators and marks quoted words; reserved words count only unquoted in command position; nesting is bounded by `MAX_COMPOUND_DEPTH`, 16): every simple command in every body is judged like a top-level one, a compound command's redirections from the directories it starts in, a subshell's `cd` ends with it, and a loop's condition and body are judged once with `loop` set. It refuses function definitions, `((`, `for ((`, `select`, unclosed constructs and words after a closer; a loop variable, and every variable a `read` sets (its name operands and `-a` array; `read`, `break` and `continue` are on the read-only list), must be lowercase letters and digits or an allowlisted name, never a lowercase name the shell reads (`SHELL_LOWERCASE_PARAMETERS`: zsh's tied `path`, `cdpath`, `fpath`, `manpath`, `mailpath` and its special parameters); in a lane a `for` loop's words are judged as paths (a glob by every match) and bound as the shell spells them (`loopValues`, at most `MAX_GLOB_MATCHES`), so `$f`/`${f}` in its body is judged as each value (`boundSpellings`), a `read` into a bound loop variable is refused, and a `for` without `in` binds nothing; a program that opens no operand (`NON_PATH_PROGRAMS`, such as `echo`) still has its glob words judged, since the shell expands them; a lane's `cd` inside a loop is refused (the gate does not count passes). It refuses heredocs (the body is not judged), command, process and arithmetic expansions and any `${...}` beyond a plain name, length, default or pattern trim; judges `command`, `env`, `timeout`, `time`, `nice`, `stdbuf`, `xargs`, `bash|sh -c`, `pwsh -Command` and `ssh host cmd` by the program they run (depth 2); and admits a leaf only from `READ_ONLY_COMMANDS` with structural git, npm, node, sed and test rules. Assignments (leading, bare, `env NAME=v`, `${NAME:=v}`) follow an allowlist: LANG, LC_*, TZ, NO_COLOR, COLUMNS, TERM, FORCE_COLOR, plus CI and NODE_ENV in a requirement check's test run; anything else (`RIPGREP_CONFIG_PATH`, `GIT_*`, the path variables) is refused with its name. Program-source options (`-e`, `-f`, `--regexp`, jq `-f`, awk `-f`/`-e`, sed `-e`/`-f`) are read before positionals, so a path before `-e` is still a path; jq `-L` values are recursive read roots; awk `ARGV`/`ARGC`, `file:` URLs and `curl -K` are effects. `tsc` is not on the read-only list: what it writes (`.tsbuildinfo` through a configured `incremental`) depends on configuration the arguments do not show. A read-only lane without `network.http` also makes the host download nothing for it: its bash, grep and find tools get `resolveInstalledManagedTool` (`utils/tools-manager.ts`), which resolves a managed tool (ripgrep, fd) only when it is already installed and otherwise fails with a provisioning error that names the missing grant; a lane that holds `network.http` keeps the installing resolver.
- A `readOnly` worker's shell is judged per call by `readOnlyShellViolation` with the lane scope the tool surface builds (`ReadOnlyShellLaneScope`: the `network.http` grant, the worker's scratch directory created before admission, the home directory, the inherited `CDPATH`, harness storage for recursive searches, the credential guard's denied-path policy). The walk tracks `cd`/`env -C`/`git -C` (at most `MAX_TRACKED_DIRECTORIES`, 64, the same bound as the credential guard; more is refused), expands only `~`, `$HOME` and the scratch variables (any other `$` in a path operand is refused, because the lane shell keeps variables between calls), refuses reassigning or unsetting the path variables, and expands globs with the `glob` package (`**` as `*`, as without globstar). Every path is judged in its lexical and its physical form (`physicalPathSync` in `autonomy/path-scope.ts`: `..` is the parent of the physical directory reached so far, as the kernel resolves `link/../x`). A link-following recursive search (`rg -L`/`--follow`, `grep -R`/`--dereference-recursive`, `diff -r` without `--no-dereference`, `Get-ChildItem -Recurse -FollowSymlink`; a letter cluster holding the follow letter counts) has every link below its roots judged by where it leads, file or directory, and each linked directory walked in turn once per canonical path (`followedLinkViolation`); a tree of more than `MAX_FOLLOWED_ENTRIES` (20,000) entries is refused, naming the bound. A lane's bash and python save their full output in the scratch directory (the read-only shell reads it; the `read` tool's grant holds only the read paths), and the lane's bash notice for a broad search names shell readers on that file (`outputReadableByShellOnly`) instead of read offsets. `/proc/<pid>[/task/<tid>]/{environ,mem}` are denied (`cmdline` is not: `ps aux` prints it anyway) and a network share (`\\host\share`, `//host/share`, `\\?\UNC\`) is network reach. Without `network.http` the lane's commands run with `GIT_NO_LAZY_FETCH=1`, `GIT_TERMINAL_PROMPT=0`, `GIT_PAGER=cat` and `core.fsmonitor=false` appended through `GIT_CONFIG_COUNT` (`createWorkerRunEnvironment(..., { offline })`); a `readOnly` lane also runs npm with `npm_config_update_notifier=false` and `npm_config_logs_max=0`, and no worker inherits `RIPGREP_CONFIG_PATH` (`ARGUMENT_STEERING_VARIABLES` in `worker-run-environment.ts`: a ripgrep configuration file adds options the command line does not show). Every lane's denied paths include the machine credential stores (`machineCredentialStorePaths`: SSH, GPG, cloud, cluster, registry and git credentials, keychains) and the secret-manager bootstrap files; the boundary judges a command's own arguments, so git and ssh still read their keys themselves.
- The credential guard (`core/secrets/credential-exposure-guard.ts`) judges every tool call through one generator, `toolCredentialAssessment`, whose path questions (`protected`, `token`, `file`, `storage`) are answered by `CredentialPathPolicy`'s synchronous or asynchronous methods (`runCredentialWalk`, `runCredentialWalkAsync`), so the two checks cannot drift (the asynchronous check once skipped `patch`). A shell line is tokenized in its tool's dialect, judged from every directory a `cd`/`chdir`/`pushd`/`Set-Location` in it may reach, and its nested substitutions, PowerShell blocks and `bash -c`/`pwsh -Command` scripts, input redirections and every command word at any position (a wrapped program) are judged too, except that a top-level POSIX line whose every simple command's program (after assignments and unquoted reserved words) is in `DATA_ONLY_PROGRAMS` (programs that print or read, such as `echo`, `cat`, `grep`) has only the command at each program position judged, so `echo grep -r x` is data; nested substitutions, `bash -c` scripts and fallback lines always get the every-word scan; the raw-text dotenv backstop ignores an exclusion's value (`--exclude='.env*'`). The path policy expands `~`, `$HOME`, `${HOME}`, `$USERPROFILE`, `$env:USERPROFILE` and `%USERPROFILE%` and compares the resolved path and the canonical form of the unnormalized spelling (a `..` after a symbolic link); the native probe canonicalizes through the longest existing prefix. Searches (deny mode, the worker lanes): a named protected path or a glob that can expand to a dotenv name is a credential read; a search root (a directory operand, a glob's directory, or `.` for a recursive search without operands) that contains a protected path (`containsProtectedPath`, minus `searchableFiles` such as the project's own settings file) is refused, glob or not; a recursive grep needs a dotenv exclusion (`--exclude='.env*'`) or a narrow non-dotenv include glob, and rg is admitted unless `--hidden`, `-.`, `-uu` or `--no-ignore*` lets it read hidden files without a `!.env*` glob; every other search without a file filter runs and its output lines are masked by file (`mockProtectedSearchLines`, which also reads the grep tool's `path:` header with its indented `N:` lines). A tool call's saved full output (bash and python through `OutputAccumulator`) is written through the mock its result gets: the guard runs the call inside `runWithPersistedOutputMask` (`core/tools/persisted-output-mask.ts`), the accumulator takes the scoped mask when it is constructed, and `MaskedOutputStream` passes it blocks of complete lines in order (`createCredentialBlockMask` keeps a PEM block or search group open across blocks), holding an armored `-----BEGIN ...-----` block until its end line (past 1 MiB it is one `[REDACTED]` line and the rest is dropped); known values are masked within a block. A filtered git query's overflow spill (`runGitQuery` in `core/tools/git-filter.ts`, past the retained head) is written through the same scoped mask and into the bash tool's `outputDirectory`. The foreground saves under the work root as before; a worker lane saves in its scratch directory, which is removed when the worker ends, so a worker's command receipt names no output path. Foreground `!` commands (`bash-executor.ts`) do not pass through the guard and save raw output. The harness's own memory, skills and sessions are searchable without a glob. The dedicated grep tool passes `--hidden`; in a worker lane it skips protected files itself (`GrepToolOptions.excludeFile`, applied in a directory search before the match limit in the rg, fff and bounded-walk paths; a file named as the path is still searched), and the lane boundary's `grepToolSkipsProtectedFiles` lets such a directory search run without a glob. Other deny-mode callers still need one. The foreground's mock mode never refuses; it masks the same reads. Limits: the guard and the read-only line judge recognizable command text, a policy gate rather than OS isolation; a `$VAR` operand is one file the guard cannot resolve; the link walk sees the tree when the command is judged, not when it runs; non-hidden `*.env` files (`prod.env`) reached by rg are masked, not refused; repository configuration that runs programs (`diff.external`, other configured helpers) is outside the gate.
- `soul.md` in the agent directory is the agent's identity (a persona file): the name opens the prompt and the body sits under it as standing text. The agent may write the file, so its body goes through `scanContextFileThreats` before it becomes instructions (a finding replaces it with a notice); it has no size limit by owner decision. Read once per builder for cache stability. The loader (`projectAgentIdentity`) screens the whole document once, name and body together (`scanContextFileThreats` plus the invisible-unicode strip), before either is read; a finding replaces the whole identity, default name included, with the notice. Writes to it are owned by `SoulController` (`core/soul/`), exposed as `session.soul`. Agent writes: `ToolGateController.beforeToolCall` calls `SoulController.checkWrite` through the `soulGate` dep (absent in a worker session) after the operation gate (YOLO does not skip it: it guards identity, not permission) for the root agent's `write` or `edit` whose realpath is `<agentDir>/soul.md` (case-insensitive for Windows and macOS; a missing file resolves through its real existing parent plus the name, so the creating write is gated). The candidate is the whole document the call leaves: a `write`'s inline `content`, or the current file with the `edit`'s edits applied by the edit tool's own planner (`planEditsToNormalizedContent`, `applyEditMatchPlanToSource`); a `contentRef` or `payloadRef` is refused (the `write` tool only creates files, so an update of an existing soul is an `edit`), and an edit that does not apply is left to the edit tool to fail. That exact text passes `checkSoulText`; then, only while System One is available (the session's recorded engine exists), the `soul-review` decision program (override, authority, covert, external required false; identity required true; `consequence: "high"`, 20 s deadline) runs through `DecisionEngineRouter.evaluateOrFallback`. All settled good allows; any adverse blocks with the decision codes in a reason under 240 characters; an unsettled band blocks with "simplify the text" and the same text is evaluated at most twice; an evaluation that fails or times out while an engine is bound holds the write, never writes it unreviewed: the call is blocked with a `correction` telling the model not to write again, nothing is written or recorded, and the bytes the write path stores (`<screened text>\n`) are kept with the file text they were based on (one held write: a newer held write replaces it, a newer allowed write drops it at once with its text kept as `withheld` and the notice told at that call's settlement, `write-replaced` when the newer text landed and `write-dropped` otherwise; a call whose own abort cancelled the review is blocked without holding). An engine that can never run the review (`DecisionEngineRouter.select(SOUL_REVIEW_PROGRAM, "high")` finds none: no boolean decisions, or the default policy refuses its confidence provenance; reachable only through an SDK-supplied steering plane engine) is the `unsupported` outcome, a configuration fault: the gate blocks and records `block` with a `write-unsupported` notice naming it, a held write ends with its text kept, and a change found at settlement is reverted with that reason; nothing is held or retried for it. Retries are event-driven and never on the admission path: a settled `ok` evaluation of this session while no gate review runs (`onSemanticEvaluation`, subscribed only while something is held), an answered gate review, and at most every 2 minutes at a tool admission; one retry pass runs at a time, and after a failed retry (a failed review or a write the lock refused) no trigger starts another within 30 s (`HELD_RETRY_MIN_SPACING_MS`), so System One answering other questions cannot spend the 5 failures in seconds while only the soul review fails. Whether a held write still applies is decided inside the settlement order (`serialized`) and from the accounting, never from a raw read (`heldStanding`): a difference on disk while calls run is a change their settlement has not judged yet (a sibling's shell write it may still revert) and the write waits; with no call running it is the owner's and is adopted first, as at admission; the write is stale when `ownerChanges` moved since the hold or the accounted text is no longer the based-on text. `ownerChanges` counts owner saves and restores, owner adoptions and the deferred give-up adoption, and not reverts: a digest cannot see an owner round trip back to the same text, and a revert restores what the owner had. Held changes (`AwaitingReview`) and deferred verdicts use the same count. Allowed: the harness writes it through the owner write path (`SoulController.write` with `accountedOnly`: screen, soul lock, refusal when the file is no longer the based-on text or not the accounted revision) and records `agent`/`allow`; the allowance is kept on the held write, so a write the lock refuses is retried without a second review, and 5 refusals or 10 minutes end it `write-locked` with its text kept. Adverse or unsettled: a `block` record, not written. Stale: dropped with its text kept as a `withheld` entry; 5 failed retries: dropped the same way; no engine bound any more: written `unreviewed` (the no-engine rule). Evaluations run on the recording engine, so they land on the semantic evaluation ledger like every other judgment. Owner writes (`/soul`, `/soul restore`) pass the screen and skip the judgment. Any other writer (`bash`, `python`, a script, another tool, a second process) is caught after the fact, by revision evidence rather than time. `SoulWatch` holds the last accounted-for revision of the file: its text, the sha256 of that text and a stamp (mtime, ctime, size, inode, so a timestamp-preserving write still moves ctime); an unchanged file costs one `stat`. At admission of every root tool call (`SoulController.checkWrite`, first line) the file is reconciled with that revision: a difference found while no other call is running happened between calls, so it is adopted as the owner's (recorded `owner`/`unreviewed`, never judged, never reverted; a deletion between calls is adopted as absence). `SoulController.settleWrite`, called from `ToolGateController.afterToolCall`, reconciles again: a difference relative to the admission baseline happened while calls were running and is attributed to this call or to a parallel sibling (whichever settles first reports it, in its own result). It is judged on that exact revision like a gated write: the deterministic screen, then the soul review while System One is available. Accepted: recorded `agent` with reviewer `allow`, or `unreviewed` when no engine is bound. A review that fails or times out leaves the revision on disk awaiting review (`AwaitingReview`): it is not adopted as the owner's (reconcile is skipped while it stands), the call's result says it is held, and it is retried like a held write; its verdict commits like any other. A newer revision or an owner save supersedes it (dropped; the new revision is judged or adopted as usual); after 5 failed retries it is reverted with its text kept as `withheld`, because keeping it would be an unreviewed agent change. Each scope (`write`, `change`) tells the owner once per episode through the `soul-review` harness notice kind (`write-held`, `change-held`) and once at its end (`write-applied`, `write-rejected`, `write-stale`, `write-withheld`, `write-locked`, `write-replaced`, `write-dropped`, `write-unsupported`, `change-accepted`, `change-reverted`, `change-withheld`, `change-replaced`); when no notice can be kept the text is a warning. An awaiting change keeps owning its revision until its commit returns: a revert that throws leaves it held, so the next admission cannot adopt it as the owner's. Held state lives in the process. `SoulController.close` runs first in `dispose`, before the agent is aborted and before `afterToolCall` is unset, so calls still settle after it; the invariant is that after close no review starts (a per-controller `AbortController` cancels the gate, settlement and retry reviews in flight; `verdict` returns `unavailable` once closed), no proposal is held without a `withheld` record (`holdWrite` after close records it and blocks; `checkWrite` refuses soul writes after close), and while an engine is bound no unreviewed agent text stays on disk. Close records a held write `withheld` with a warning, then reconciles the file once: a settlement in flight (`settlingCalls`) finishes its own change (its aborted review makes the verdict `unavailable`, which after close reverts with the text kept, never `AwaitingReview`); a running call's allowed text landing is left to its settlement; the held change's revision, or any difference while calls run, is reverted to the accounted text (the held change's restore target while the owner count is unchanged) with its text kept as `withheld` (screen failures are `reverted`, a deletion is put back, no engine bound accepts it `unreviewed`); a difference with no call running is the owner's. If the soul lock refuses, it stays on disk with a warning. Nothing held is applied across a restart, and `/soul restore` brings a withheld text back. A process killed without `dispose` (or an SDK caller that never disposes) leaves a held change on disk, and the next session starts from it. Adverse, unsettled or failing the screen: the accounted-for text is written back (a file that did not exist is removed), a typed `reverted` entry is recorded, the owner is warned and the model gets a notice under 240 characters appended to the call's result; a deletion is put back as a typed `removed` entry; a gated write whose text another writer replaced is reverted to the reviewed text. A verdict is valid for one revision only: it is committed under the cross-process soul lock (`state/soul/write`, `withFileLockSync`) after the file is read again, and if the digest is no longer the observed one the verdict is discarded without writing or advancing the accounting; the new revision is reconciled the same way (judged again while other calls still run, at most 3 rounds, otherwise adopted with a warning; adopted as the owner's when none runs). Text, digest, stamp and history advance together for the same verified bytes. Owner saves and restores take the same lock and refuse to replace a file that is no longer the text the owner started from. Crash order of a revert: the text to restore is stored as a version, the file is replaced atomically, then the history entry is appended; a crash after the replace leaves the right file with no entry (the next write records it as a baseline), a crash before it leaves the offending file, which the next load screens and the next session starts from. A verdict the lock refuses (`withLock` returns `held: false` after its bounded retries) is not dropped: `SoulController` keeps it as a `DeferredSettlement` (the exact revision, the accounting digest it was made against, and the commit), and `resolveDeferred` runs first at every admission and settlement. While it is pending, the revision it owns is never adopted as the owner's and no new judgment starts. It is retried; it is dropped when the file is a newer revision or an owner save/restore advanced the accounting (the authority to restore is gone, owner priority); it expires after 5 retries or 10 minutes, adopting the current text with a warning and a typed `unresolved` history entry. A revert that completes at a later admission is told to the model in the next settled call's result. Every history read-modify-write and version prune takes the same soul lock (`recordAudit`; blocked attempts included; inside a locked operation they run directly, so the lock is never acquired twice), because the history file is rewritten whole; an entry the lock refuses is kept in a bounded queue (32) and written first by the next locked operation. Remaining gaps: the offending text is on disk from its write until the end of the call (for a background process, until a later call ends), so another session can load it in that window; an external editor that writes between the last digest check and the replacement is overwritten (the lock binds only harness actors; the window is a few microseconds); a change by the owner while a root tool call is running is indistinguishable from that call's and is judged as the call's; a root call refused after admission (by the soul gate or a later gate), aborted before it starts or abandoned never reaches `afterToolCall`, so `checkWrite` registers the invocation cleanup (`registerCleanup`, which runs on refusal, abandonment or after finalization) to drop its running entry and to tell `write-dropped` when it carried an allowed write that replaced the held one; a running entry is still dropped after an hour for a caller that passes no cleanup; deferred records (verdict, history entries) live in the process, so a crash while the lock is contended loses them (the file keeps whatever text it had, and the next session starts from it). History: `state/soul/history.jsonl`, one JSON line `{at, sha256, author, reviewer, bytes}` per write (plus `event` for `reverted`, `removed`, `unresolved`, or `withheld: true` on an `agent`/`unreviewed` entry for a text no review let in: a field and not an event because every released reader keeps an entry with an unknown field when it rewrites the file but drops one with an unknown event, and its version file with it), where `sha256` and `bytes` name the text the file actually held after the write and `versions/<sha256>.md` keeps it whole (a blocked attempt is a `block` entry that keeps no text); a file found with text no kept version holds is first recorded as an `owner` baseline. The record boundary is truthful: an allowed agent write is only held by the gate (keyed by its tool call); `SoulController.settleWrite`, called from `ToolGateController.afterToolCall` (`soulGate`), records it only when the tool call succeeded and from the file as it is then on disk. If that text differs from the reviewed text it is recorded `unreviewed`, run through the deterministic screen, and the owner is warned; a failed call records nothing. Owner saves and restores record after `writeFileAtomicSync`, from the file as written. Bounded to the last 20 entries and the versions they name; `/soul restore <n>` writes version n (newest first) back through the same screen. Residual gap: another writer that changes the file between the review and the tool's own read is detected after the fact, not prevented.

- Standing rules are rule hooks (`src/core/rule-hooks/`), not prompt text and not something the model chooses to read: a model can skip any rule that depends on its own call. `rule-hook-rules.ts` lists each rule as `topic`, a trigger (tool names plus an optional predicate over the call args) and a body (at most 4096 chars; a function of `RuleHookContext` when it needs a dynamic value such as the package root). When a trigger tool call finishes without error, `ToolGateController.afterToolCall` appends one text block `RULE <id>\n<body>` to that call's result (`RuleHookDelivery.collect`, after every gate that can still turn the result into an error, outside the untrusted-content fence) and lists the delivered ids in the result's `details.piRuleIds` (`detailsWithRuleIds`; the key is `RULE_IDS_DETAIL_KEY` in `kernel/session/message-retention.ts` and is one of `RETAINED_RECEIPT_DETAIL_KEYS`, so the oversized-details stub keeps it), so the rule lands in history and is cached with the prefix, and its id survives when context packing replaces the result's text. A `preflight` rule is delivered by a host check that is about to accept an action instead: the goal tool's completion preflight (`getCompletionRuleRefusal`, `core/tools/goal.ts`) asks `RuleHookDelivery.refusalFor("noticed-items")` after the deterministic completion checks and before the System One judgments, for the one place every model-driven completion reaches (goal `complete`, `increment` with nothing left to satisfy, `update_goal` complete; owner `completeGoalManually` and System One's automatic objective completion are not model calls and are exempt). - `transient-records.ts`'s `lastDurableTransientContent` returned a durable record's SUFFIXED text (raw content + `TRANSIENT_RECORD_SUPERSEDING_NOTE`), but `resolveSlotContent` compared it directly against the caller's raw, unsuffixed `slot.content`/`clearedText` — a suffixed string can never equal a bare one, so the "content unchanged, skip" path never actually fired for any transient slot (trailing or non-trailing) once a durable record of that kind existed. Append-on-change's central claim, "most turns append nothing," was false from when it was built (`c02d404d0`): a full fresh copy was appended every turn a slot had live content, changed or not. This shipped-and-reverted code never reached users, but every earlier measurement of the mechanism was taken against a version paying full-copy-per-turn cost while still showing a reference-stable prefix (the delta property was real; the token cost was not what it looked like). Verified via an isolated 3-call probe with identical content each call: pre-fix appended counts were 1,1,1, post-fix 1,0,0. Fixed at the single shared read point — strip the known suffix before comparing.
- The tool-failure ledger and verification-obligation transients both need to sit at the literal tail of the sent message sequence when active (`TransientRecordSlot.trailing`), but append-only and "always last" are in permanent tension: anything appended after a trailing record — including ordinary turn growth, not just another transient — displaces it for good. The resolution is re-append-to-reclaim, not reposition, and its frequency is structural, not host-transient-driven: measured over a 15-turn run (one verify-fail/verify-pass cycle, 12 ordinary reads between) with zero host transients, 14/14 turns the ledger/obligation were live fired a trailing re-append, 12/14 of those with genuinely unchanged content — displaced purely by the previous turn's ordinary assistant-reply-plus-tool-result landing after them. Adding a host transient that changes every other turn produced identical counts and `fullyStable: true` held at every turn regardless, so host-transient volatility is not the lever here; making informational transients "stabler" would not reduce this cost. Budget the ledger/obligation's own bounded text (bounded via `MAX_ACTIVE_FAILURES`) once per turn for the duration of any live failure/obligation window as the real, structural price of a byte-stable prefix during recovery.

## State-machine ownership (owner input, releases, waits, timers)

- One owner per lifecycle. Owner input is owned by `OwnerInputLedger` (`core/owner-input-ledger.ts`): an id is minted at acceptance and stamped on the message; the single Delivered commit point is the user entry being persisted (`notePersisted` from the foreground lifecycle adapter, which also writes the id into the session entry so a restore recognizes a delivered input). Owner rules, the blocker clear, the owner-policy enqueue, optional-tool intent promotion and goal activation run on Delivered; every other end (withdrawn, held, cancelled, refused) is explicit and visible. Matching is by stamped id, never by text. An idle foreground hands admitted input to a delivery run (`ForegroundInputPort`), event-driven.
- Queued and own-turn image records each own an independent pin claim. Preparation pins each image before another write can prune; a pre-publication failure releases only that claim, while an uncertain publication retains it. Replacement releases only the prior record's claim. Restored unreadable references retain exact filenames across rewrites, independent of retired claims; legacy identities are resolved on private metadata before publication. Image mutations share a directory lock with no contention wait; reads remain independent. Legacy sidecars expire normally and are not released by new record publication.
- Taking queued input for reuse resolves all preserved image references before withdrawing that input; failed reads leave it queued and pinned. Explicit clear still discards it. Clipboard-only images use `[Attachment #N]`, outside durable image-reference syntax. Pending labels own their bytes and suppress implicit latest-image lookup; explicit other image references remain resolvable. Failed send-now submissions return images through the same clipboard owner as take-back.
- A queue snapshot restored from history is borrowed: another parked branch can still rely on its image claim. Navigation installs the destination baseline before reconciling input, then publishes a fresh snapshot even for an unchanged queue; an empty queue over a destination with no record publishes nothing, so navigation does not move the leaf. Only successful publication makes the new record owned; later linear edits may release that claim. Borrowed claims remain until normal expiry. This preserves parked branches without retaining every intermediate historical snapshot or scanning the whole tree on each edit.
- Direct prompts retain their acceptance branch through asynchronous input hooks. An unhandled prompt claims that context before turn preparation; stale input becomes held, while a handled command may navigate normally. A prompt that queues later retains its original position and context. Its own-turn recovery record retires only after an owned queued record confirms the same input ID, or delivery/explicit withdrawal ends custody; failed or bounded-out writes retain the source record.
- Kernel queue drains retain each unstarted occurrence until its `message_start`. End-of-run restores the remainder ahead of later arrivals before notifying listeners, including batches drained to start `continue()`. Active batches remain run-owned and cannot be withdrawn through the waiting queue. Started messages never return automatically: a failing persistence callback may already have committed their history.
- A stamped owner message forces the session-prefix write before its canonical entry is published in memory and the foreground adapter announces delivery. Single messages, routed batches and copied branches share the storage owner's durability rule. Unstamped initial metadata can remain buffered; explicit in-memory sessions retain their no-file behavior. A failed pre-write admission cannot leave a duplicate buffered owner row for a retry to append again.
- A post-publication session error carries the original session, ordered entry IDs, exact source objects and durability in `SessionAppendCommittedError`. Unknown physical writes have no committed receipt. Foreground notifications settle independently without replacing that evidence; routed buffers retire the exact accepted occurrences before propagating errors, preserving newly arrived input. A full flush that receives new input exits through the existing unpersisted-input handoff instead of dropping the suffix or flushing indefinitely.
- Canonical append and buffered-flush writers can confirm a fully written suffix after an I/O error while retaining the original file lock. Confirmation requires the opened file's identity, exact final size, full suffix bytes and a stable read; initial creation covers the header and buffered prefix too. Canonical publication and notifications then run normally before the original error is reported as committed. Raw physical-only writes and partial or unreadable results retain uncertainty.
- An unknown owner-input write retains its live delivery effects and appears as `Write unresolved` without changing its stored text. Queue clear, navigation and shutdown cannot reinterpret it as undelivered or resend it. Recovery custody remains with the original session file; reopening alone does not prove safe replay, which requires canonical reconciliation of that write.
- Uncertain append evidence freezes each attempted row's parent and owner-input ID before encoding, then fingerprints the exact encoded row retained by the writer. Reconciliation must compare physical row bytes, never a reserialized mutable message or cold-loaded projection. An empty flush carries no attempted-row evidence and cannot prove anything about the entire buffered prefix.
- SessionManager owns message-to-entry identity for lifecycle callers. Ordinary-message lookups validate the current entry and exact object; custom-message bindings retain the exact canonical entry rather than its ID alone. New-session replacement invalidates the message index, and lifecycle reload discards its completed-message dedupe sets. A stale object cannot acquire authority from a reused ID in replacement history.
- Human-input replay restores only the attachments named by each saved answer, in their original order and multiplicity. New snapshots carry store-owned exact filenames and sequences; presentation clients cannot supply those references. Answer prose never invokes clipboard reference inference or latest-image fallback. Missing, unreadable or MIME-mismatched attachments remain absent with the replay's explicit loss notice.
- A resumed owner question retains its exact snapshot revision and branch anchor until foreground admission. Duplicate resumes share its preparation; navigation or disposal cancels that preparation without publishing into a replacement context. Owner interruption may checkpoint an interrupted answer, but cannot start another turn. Shutdown joins preparation only: joining the resumed model run can deadlock a runtime replacement initiated by that run.
- Auto Learn rereads skill and settings eligibility for each proposal, and reflection rereads learning policy between awaited writes. Learner-origin promotions also recheck the shared skill-evolution policy inside reflection; the outer proposal prefilter is not authority for a later write. Explicit reflection and rollback retain their own admission semantics.
- A learning batch captures session identity, file, branch generation and ancestry before asynchronous work. Navigation permanently invalidates its execution authority; ordinary descendant appends remain allowed. Nested preference admission inherits the same call context and explicit-authority flag through async-local storage. Later skill/settings edits and fallback targets use the original guard rather than recapturing a new branch.
- Forward learning audit publication has a bounded durable journal independent of the mutation. An owned intent is confirmed before the effect; the actual result and rollback are frozen before publication. A stale context retains that receipt for its original intent lineage, without repeating the effect. Publication attempts serialize their claim, append and acknowledgement; uncertain appends are reconciled from canonical session bytes. Missing receipts may be published through a healthy matching session, while malformed, conflicting or wrong-lineage evidence stays unresolved. Observer/skill-refresh failures cannot erase a returned effect result. This does not cancel an already-admitted storage commit.
- Structured organization reports creation and source removal separately. Creation without removal is a partial outcome whose rollback removes only the new OKF record; restoring hot memory requires confirmed removal and its exact target. Managed-content commit errors are reconciled under the content lock against exact bytes and pending metadata. Confirmed content with pending metadata remains an applied effect with a warning; a pending empty revision is never healed back to its deleted content. Change-notification failures are warnings, not storage failures.
- Memory cancellation is checked during preparation and at the first commit attempt. `MemoryMutationAdmission` then lets the storage owner finish that transaction's consistency writes and report its actual result. USER archive mutations share admission with the outer managed USER commit; empty-file healing, metadata reconciliation, drift backup and unchanged-index rebuilding do not admit the requested mutation. OKF creation and later hot-source removal have separate admissions, so cancellation between them retains the creation-only partial receipt. Admission is not proof that bytes landed.
- USER mutation selection reads the complete bounded archive, independently of the 400-entry prompt projection. Matching nonregular, unreadable, malformed or wrong-scope shards refuse mutation; missing storage alone means empty. Archive preparation freezes before/after bytes, validates projected and overflow-peak capacity, then writes overflow before shortening the source. Limits are 1,024 shards, 2,112 total directory entries, 1 MiB per file, 16 MiB of shard content and 50,000 preference entries. Partial I/O failures still require storage-transaction reconciliation; preparation alone does not make the multi-file operation atomic.
- Memory failure reports distinguish partial storage effects from unknown outcomes. Archive reconciliation credits matching after-images only for attempted commits, retains earlier confirmed effects when another file is unreadable/conflicting, and carries bounded evidence through the tool result. Collateral archive/index changes do not prove requested USER preference completion: both learning audits retain an incomplete reason and no generic inverse, and Auto Learn keeps it open. Unknown structured source cleanup also prohibits an inverse. Exceptions and incomplete results never justify fallback to a second memory target. These live receipts do not replace a durable transaction or authorize replay after a crash.
- USER audit acknowledgement uses a frozen intent reference and terminal report, including its original timestamp. `LearningWriteJournal.acceptExternal` confirms durable receipt custody independently of branch publication; it can reconstruct only a settled receipt obligation, never mutation authority. `LearningReceiptStore` keeps the latest 256 terminal outcomes separately from the 64 pending obligations. Memory-only publication transfers to terminal storage before retiring its pending file. Recovery reconciles exact terminal evidence after a peer retires the journal; conflicting outcomes or physical intent markers remain errors. Terminal history may be pruned only after a replacement receipt is confirmed, and failed pruning does not invalidate custody.
- The USER storage transaction lives beside its managed state as `.transaction.json`, under the existing USER content lock. Its bounded plan covers archive shards, index and the outer USER commit; attempted/completed steps and an immutable receipt survive interrupted writes. Recovery never replays content. A complete or no-effect receipt clears only after audit custody and matching current storage; partial/unknown outcomes retain an inspection barrier before mutation, startup healing and operator accept/restore. Pending USER reads remain available where readable, and unavailable projections emit diagnostics without blocking unrelated memory. A retained receipt is transferred before a peer-retired transaction is forgotten, so an older provider cannot resurrect it over newer work.
- USER prompt snapshots publish active content and archive availability together under the USER lock after explicit read/mutation/recovery boundaries. Unreadable, truncated and over-budget preferences never mean empty: static, dynamic and handoff projections preserve those distinctions, and changed-state fallback records are active content rather than clear-only markers. Archive rendering keeps 400 entries with one lookahead for truncation; mutation reads remain complete. Already-managed operator reads and active-only writes refresh the archive view too. Post-startup notices use the same active-generation reporting and revision deduplication as startup; no per-turn filesystem polling is implied.
- Auto Learn captures its launching session object and ID for handoff and usage attribution. A replacement session cannot inherit that learner's charges or queued notice. Startup reoffers likewise bind one session for the scan and stop claiming further records when that owner is replaced; already admitted work remains subject to the captured session's lifetime guards.
- Auto Learn registers a bounded durable accounting obligation before spawning and freezes its usage before parent delivery. Cleanup requires an exact physical parent receipt and a published handoff, including an explicit zero receipt for a verified zero total. Its child ledger is selected by header identity, read stably with byte/row/discovery bounds, and rejected for malformed charge rows or conflicting duplicate receipts. The source fingerprint must still match after delivery; a missing or damaged ledger never certifies zero usage. Pending obligations protect artifacts from both history and work-run retention. Failed exits retain evidence for at least seven days; elapsed retention never substitutes for a receipt.
- Accounting recovery runs at existing startup/turn boundaries, yields between records, and requires the matching session file and live session/UI owner. Hold identity is journaled before admission; known pre-spawn cancellation is journaled before cleanup. A crash in the prepared-to-spawn window remains inspection-required, while a running child needs same-host proven process absence before lost-terminal recovery. A published handoff can repair a failed accounting acknowledgement independently of its notice; notice removal also requires that acknowledgement.
- Auto Learn reoffer claims hide pending records before applying and bind a journal to a UUID, source digest, host and PID. Only same-host confirmed process absence permits unknown-outcome recovery; age, remote ownership and probe uncertainty never authorize it. Exact completed outcomes retry publication only. Handoff writes, claim transitions and retention share one store. A notice marker precedes final publication and remains until the parent accepts its next-turn message; queue admission is not durable transcript consumption. Recovered notices have separate capacity from fresh applications. A durable scan cursor advances through held, terminal and malformed records in bounded batches. Legacy identity-free claims remain inspection-required.
- Learning audit IDs are unique effect identities, never counts of prior records. Concurrent rollback requests for one ID share its active execution; historical duplicate IDs are refused as ambiguous before any inverse runs. Rollback confirms a bounded intent before executing, retains known success for receipt-only retries, and requires a valid intent-to-applied chain after restart. An intent without proven completion requires inspection, including when an inverse reported failure after possible partial effects. Branch changes defer publication; buffered session entries never count as physical proof. In-memory sessions provide process-lifetime protection only.
- Skill promotion records its normalized name and exact definition digest. Digest-bearing rollback archives only that `SKILL.md`, preserving supporting files; a versioned archive marker precedes the move and allows definition-only restore without replacing an active definition. Name-only manual curation retains whole-directory semantics. Promotion, repair, archive and restore share locks keyed by physical resource roots, including symlink aliases; external filesystem editors do not participate. Removing a root definition can expose nested definitions during discovery, so rollback does not imply unloading its entire subtree.
- Every release has one outcome: `core/util/resource-release.ts` (`RetainedReleases`, `AsyncRetainedReleases`, `runReleaseSteps`): released, retained (a named retry owner, capped exponential backoff on the injected `TimerPort`, a wake for dependents, a last-chance pass at shutdown) or abandoned. A release that fails while the owner shuts down keeps lease, hold and claim for the dead-owner reaper; in a live session it is retried.
- Retained-release timer failures keep resource ownership and successful-release notifications intact. Retry calls return infrastructure errors without poisoning the asynchronous queue; snapshots disclose a bounded `retryError` and never claim an unarmed delay. Disarming invalidates callback identity before clearing the timer, so a failed clear cannot block shutdown, replay a closed retry or erase a newer alarm. If allocation fails, only a later explicit retry/retain can rearm; no substitute timer or recursive retry is used.
- A goal execution (`GoalSessionController.beginExecution`) belongs to the foreground submission holding the foreground when it begins (its epoch) and ends only when that submission releases the foreground (`ForegroundRecoveryControllerDeps.onSubmissionReleased` → `endSubmissionExecution`), whatever the run's outcome; the explicit start authority ends with it. No caller ends one, and nothing ends one at `agent_end`: a run's `agent_end` may announce a retry that is then abandoned, and a turn's claim correction runs after it under the same execution.
- Background tool tasks capture their held execution's goal even after active-goal replacement. An A task cannot acquire B authority merely because B becomes current. Its terminal remains durable; continuing B requires explicit input. Genuinely unbound turns retain current-goal ownership, and intentional ended-goal adoption follows the execution lease's existing resolver.
- A background tool's cancellation terminal fences logical waiting, not physical execution. A later correlated completion retains output, execution evidence and usage while preserving canceled status and refusing passing verification; while the superseded terminal is undelivered, the new revision carries that terminal's own output (a cancellation cause included), because a resume restores and delivers only the newest snapshot. Every new terminal snapshot has a strictly increasing completion timestamp; delivery and observation match session, task and that timestamp, so reading the cancellation notice cannot consume a later result. Runtime observation is cleared for the new revision while its original goal and submission epoch remain unchanged.
- Background tool images are durable image artifacts with a manifest on the terminal record. `tool_task action=image taskId=… imageIndex=1` returns one image; this path remains available when `artifact_retrieve` is excluded. Notification text preserves numbered image positions and a retrieval hint, never the base64. Image payloads are admitted up to 64 MiB of serialized data and manifests up to 16 MiB; capture failure reports loss without claiming retention. Views above 4.5 MiB base64 are resized while stored pixels remain unchanged. Task-owned artifact references survive cache eviction and resume; lineage reads resolve inherited images. Bounded artifact reads enforce actual payload size under the artifact lock, and an unavailable local payload never falls through to an ancestor.
- ICM node publication precedes view/queue bookkeeping. A later write error can therefore leave a valid node despite a failed compaction outcome. Both failure and cancellation settlement recheck publication after locked reconciliation, returning a published outcome and emitting the node event when it exists. Missing running ownership without a published node remains an error; never resolve it by treating every absent claim as complete.
- ICM visible-record reconciliation is owned by `projection.sqlite`, whose identity and revision are bound in `root.json`. Once established, missing or replaced projection authority fails closed rather than recreating generation zero. Reconciliation preserves raw records, permanent IDs, source identities and occurrence dates; all ordinary record reads and navigation apply the same projection. Old background candidates whose sources are unavailable receive reversible neutral placeholders while unrelated history stays readable; only canonical consumption proof permits rederivation. A changed record invalidates every summary ending after its earliest changed ID, including later disjoint summaries that may have read it through their causal prefix. Tree reads and index recovery enforce this revision frontier. Compaction captures its projection revision before reading its target and prefix, then publication checks both that revision and the exact live claim under the writer lock. Superseded claims cannot publish or complete replacement work; lease changes clear cached nodes.
- ICM deferred work lives in `queue.sqlite`; `queue.json` is its schema-3 authority marker. SQLite transactions own claims, arrival generations, retry eligibility and parent insertion. Scheduling reads indexed bounded rows; failed leaves do not consume the eight running slots. Work is claimed in context-endpoint order (a leaf is its message, a parent the message after its range; a merge first at a tie): each kind names a candidate, fresh and retry alternating within the kind (stored never-attempted leaves belong to the fresh class; released work comes in endpoint order, failed work oldest failure first behind it), and the two kinds' candidates are compared by endpoint. Database schema 3 retains the endpoint indexes and adds durable recovery eligibility; schemas 1 and 2 migrate in place on open. The background-versus-arrival distinction for view batches lives in `refreshContinuousChatView`: only a message arrival commits partial batch progress, the causal view never inherits the turn view's merges, and `catchUpView`'s closing refresh is a background fit. The earliest unfinished leaf remains the causal cutoff. Legacy JSON imports stream into a provisional database, preserve the cutoff and hashed original bytes, checkpoint before rename, and publish the authority marker last. A committed database is never rebuilt from the legacy queue; interrupted marker publication is repaired only against matching legacy provenance.
- Exhausted ICM overflow and empty-reply jobs wait for a changed effective summary model, effort or prompt identity, or explicit recovery. Their failure and pending node remain durable; ordinary arrivals still retry transport and storage failures. A failed job retains its starting configuration, so an old-model result cannot impose a recovery hold on a replacement configuration.
- Every ICM view a model reads goes through `renderContinuousChatView`, which collapses the oldest sibling pairs down to the state's low mark once it passes its high mark (turn view 64/128 KB; worker birth view and compaction causal view 16/32 KB). The stored views are not caps and nothing renders one whole. The causal view once reached a compaction request as stored: unbuilt and failed parents held it at ten times its mark in a recorded session, so every later request grew with the backlog (up to 49,000 tokens against about 9,000 intended, roughly a third of that session's summary spend).
- ICM cache boundaries cover only complete four-line blocks before the first unresolved rendered node, including a collapsed parent. Host metadata carries an explicit empty prefix and each row's projection provenance. Cache diagnostics retain bounded partition/reconciliation transitions while still rejecting changed shared stable nodes without a new projection revision.
- An uncertain ICM disposition retains its exact claim and command under the lease and writer lock. Idempotent acknowledgement cannot rewind later arrivals or accept a newer attempt's state. Its receipt blocks new claims until the original matching retry consumes it. Lease release or loss discards old in-memory receipts and closes the scheduler under the project lock; a failed close retains the existing release owner and prevents reacquisition until settled.
- ICM migration markers and session attachment/settlement metadata use the same project writer lock and exact runtime lease as chat data. Session-ledger read/modify/write is one admitted transaction across host instances. Host disposal closes new startup, joins any existing startup before releasing the lease, and shares one disposal promise even across synchronous callbacks. Summary-model jobs remain independent of root-turn readiness; shutdown waits for owned startup I/O rather than letting it write after replacement.
- ICM compactions are admitted through the session's isolated-completion lane, whose signal session dispose aborts well before the chat host stops (the host first lets queued records append). The runtime receives that signal as `closing`: once it aborts, nothing new is claimed, and a port error of a running compaction is its cancellation, so the claim is released for the next owner instead of being recorded as failed and reported as `Continuous-chat compaction <node> failed: This operation was aborted`. A request admitted before the close still completes and publishes; `stop()` still aborts whatever runs at the end.
- The ICM migration completion timestamp is a validated chat timestamp at both metadata read and write. It is the cutoff for later-session recovery; damaged values must reject the marker rather than make every later session look ineligible.
- ICM lease acquisition owns its exact token and exit cleanup before publication, since rename can succeed before directory flush reports failure. Failed acquisition uses the normal token-checked release outside the project lock; uncertain cleanup remains with the existing retry owner. A refused acquisition never releases another attempt's lease.
- Closing an ICM host aborts its startup listing/import/recovery. Cancellation is checked after source reads and before metadata admission, never recorded as a malformed or forgotten session; admitted writes finish before shutdown releases their lease. Legacy session reads own their descriptor and stream, with input errors propagated by stream iteration. Headerless validation streams through the same parser. Listing yields between file batches so synchronous header reads do not starve cancellation. Import reads only the permanent forget view, not the full summary tree; individual synchronous filesystem calls and an already-running forget read still settle normally.
- Memory activation owns cancellation before an ICM host exists. Supersession and shutdown abort opening through lease admission, index recovery, queue migration and session attachment; the runtime releases its lease only after recovery unwinds. Recovery scans yield between bounded batches. An admitted atomic write or SQLite promotion finishes before reporting cancellation, and a promoted database remains authoritative. This opening signal never owns a retained live chat. Single synchronous decodes, allocations, view construction and SQLite calls still settle normally; cancellation does not impose aggregate storage bounds.
- Message and summary journal recovery share a descriptor-owned streaming reader with exact byte offsets. It retains one read chunk plus the largest complete record, not a full journal's text. A backward LF scan locates an incomplete tail without buffering it. Only successful parsing and unchanged descriptor/path identity permit tail truncation, using a separately validated write descriptor; healthy journals require read access only. Metadata maps and an individual record still have their own memory cost.
- Key-index recovery and growth rebuild from the authoritative message-index rows through fixed-size input chunks and an 8 MiB page-cache bound. Colliding digests retain each physical row's message ID. Dirty pages flush before eviction and atomic publication; the source descriptor and path must still match before rename. Only a zero-row rebuild permits an absent source. Positioned journal/index transfers share exact short-I/O handling. Large tables can trade additional disk I/O for bounded memory; aggregate journal metadata remains separate.
- ICM import validates the listed session header on the descriptor it actually reads before yielding any entries. Headerless sources bind their exact validated file revision. Each read stops at its opening size and checks for revision changes at the end; a changed source retries explicitly. The shared session-line character limit bounds decoding, with overflow treated as unavailable input rather than skipped history. A final revision check does not roll back earlier canonical import batches, so this is not a transactional snapshot against arbitrary in-place writers.

Harness owner clocks are `Date.now()` plus the advanced time, so a second read inside one decision shifts the delay by real elapsed milliseconds (journey-2 R30 failed on Windows at 999 instead of 1000).
- Worker usage-persistence retries use the `worker-accounting` clock and outlive logical cancellation without keeping the process alive. The worker's physical-settlement watchdog uses `worker-settlement` and keeps its required join alive. Both clear opaque timer handles through their originating ports; timer-allocation failure reports the unscheduled receipt along with the original persistence failure.
- The accounting retry's no-wait lock policy covers both its write and synchronous publication reads, including projection compaction. The adapter scopes that storage policy until publication returns and restores it on failure; subsequent independent reads retain their normal policy.
- Worker physical timeout and resource release have separate lifetimes. A timeout remains a failed outcome; actual completion later enters the same cleanup owner and retains runtime admission until the run has physically settled; from then on a failed resource release keeps only the specialist hold, project claim and reservation (or transfers them to an existing retry owner), never the reload registration or runtime admission. Shutdown drains admitted cleanup and atomically closes further cleanup admission before disposing shared owners. Still-pending attempts retain exact lease/fence identity and resource holds, are reported as shutdown failures, and may require process restart; callbacks must not clean up through finalized owners.
- Text with paths that the model reads is bounded with `boundedText`/`boundedLine` (`core/util/bounded-line.ts`): head and tail around one elision, never cut inside a quoted path; a single path uses the path mode so no truncated head is mistaken for a real path by the alias extractor.
- Recovery coverage is registered in `test/fixtures/harness/fault-matrix.ts`: every recovery row has a fault mark and a control mark per System One mode, enforced at harness close; an open row names the harness extension it needs.
- Harness notices (`core/harness-notice.ts`, `HarnessNoticeController`) are the one owner of "an automatic capability stopped for a reason the owner can change". A capability calls `observe(kind, read)` only from detection points it already has (knowledge: collector terminal, settings change, foreground idle; proactivity: each gate skip, and `clear` when a review starts; routine result wakes: each new routine result delivery, held or not; routine pause and unschedulable zone: the end of each routine scheduler pass of the open parent, which a store write, a session start and a save all wake); there is no timer or poll. The reader returns a notice, `"clear"` (the capability works again), or `undefined` (normal flow, transient or the owner's own switch: not an episode boundary). A kind whose subjects hold states independently returns `{scope, state}` (the routine id for `routine-paused` and `routine-unschedulable`): episodes are kept per kind and scope in the runtime, while the delivery id stays kind plus reason, so each reason carries its subject (`<routineId>:<occurrenceId>` for a pause, `<routineId>:<incarnationId>:<zone>` for a zone). A routine the scheduler no longer lists (deleted, or another session's) is not observed, so its scope never clears; that costs one map entry per routine per runtime. The delivery id is `sha256([sessionId, kind, reason, generation])`, and the saved ledger is the authority: the latest saved generation covers a first observation after restart and any recurrence while it is still pending (`next-owner-turn`) or in flight; a new generation needs an observed end in this runtime plus the previous notice consumed, bounded at 32 per reason. Delivery goes through `deliverParentInput` with `mode: "next-owner-turn"`, deferred past the caller's stack; it acquires the foreground submission lease for the save, so the knowledge collector cancels and re-arms its alarm and the proactivity idle timer restarts around it. A save waits for a busy foreground (the lease is acquired, never refused) and lands when the turn ends; a branch navigation in between refuses it. An observed notice is kept in memory, one per kind and scope, frozen at its first observation (delivery id, text, digest), until it is saved: a later `clear` does not drop it, a newer reason of the same kind and scope supersedes it, and a session id change or `close()` discards it. It is saved only into a persisted root transcript whose leaf is persisted, so a notice alone never creates a session file; while one waits the controller subscribes to `onEntriesPersisted` and retries every waiting notice in one microtask after each saved entry (a new session's first saved entry, the owner's next turn), and a delivery id the ledger already holds drops it, so a retry never adds a second notice. A failed save is a warning and is retried with the next saved entry; the third failure drops it with a warning and reopens the episode, so the capability's next signal retries it as a recurrence. Past 32 waiting, a new one drops the oldest that is not being saved, with a warning (none is dropped while all are being saved). The reason stays covered while its notice waits or is retried, so the attempt's own `releaseSubmission` activity echo (notified synchronously) starts nothing. Not durable: a session that is not persisted (`--no-session`, an in-memory host) keeps nothing and `observe` returns false, and a runtime that ends or changes session before its session saved an entry loses the notices still waiting. Read failures are warnings, never thrown into the capability. Texts are owned next to their status types (`knowledgeCollectionNotice` in `context/memory-diagnostics.ts`, `proactiveReviewNotice` in `proactivity/proactivity-controller.ts`) and name a setting only when one lifts the state. A notice that an owner turn carried is logged once as a `work` record of the continuous chat (custom messages are never chat turns, but a consumed parent input is), so a journey leg that counts continuous-chat records after a notice was saved counts it on the turn that carries it (`journey-1-collection.ts`). A notice is not withdrawn when its state lifts before it is saved or before that turn: it states the state as it was first observed.
- Session persistence observers (`SessionManager.onEntriesPersisted`) run synchronously inside the write that announced the entries, possibly inside the caller's transaction (a root host-event append runs inside its task-runtime transaction, where a task-runtime read throws). A throwing observer never fails the committed write and is not retried: `_emitEntriesPersisted` hands `(observer, error)` to the `onObserverError` listeners (a failing listener is ignored). `reportSessionObserverFailures` (`core/session-observer-failures.ts`, subscribed by every `AgentSession`'s `HarnessNoticeController` and released by its `close()`) warns once per distinct observer and bounded redacted message, at most 8 per session id (the eighth says later ones are not reported), in a microtask past the write. Journeys fail on unclassified warnings, so an observer bug surfaces with its own message; a fixture observer that reads the task runtime defers its read with `queueMicrotask`.
