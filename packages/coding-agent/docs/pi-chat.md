# pi-chat

pi-chat is the packaged peer-agent message mesh. Agents running on the same machine discover each other and exchange short text messages while they work. It ships as the bundled extension `pi-chat` and is active whenever the active resource profile allows it (`all-active` does).

For persistent bots and their isolated group conversations, use [Bots and group chats](bots-and-groups.md).
Native workers use that parent-owned mailbox instead of joining this mesh.

## Tools and command

- `list_peers` lists connected peers (`includeSelf` adds this agent) and, marked offline, peers this process saw within the last 24 hours.
- `agent_send` sends one message to one or more peer ids, names or addresses. `expectReply` waits for the peer's acknowledgement up to `timeoutMs` (default 15 s, maximum 120 s). `to: "*"` broadcasts only when `broadcastEnabled` is true in `config.json`. A peer that is not on the mesh is not a failure: the message is held and the result is `queued` (see Held mail); a broadcast is live only.
- `/pi-chat status | setup | peers | help`. `setup` writes `config.json`, `identity.json` and `peers.json` after confirmation, so the agent keeps one persistent name. Every session joins the mesh under its own id, `session-<pi session id>`, so the same session is the same peer after a resume or a restart and sessions sharing a name stay separate peers; a name or address shared by two peers is refused as ambiguous and the call must use the id.

## Transport

One Unix socket per user, `~/.pi/pi-chat/sessions/local/broker.sock` (override the root with `PI_CHAT_STATE_ROOT`). The first process that finds no broker becomes it; every other process is a client. The wire protocol is newline-delimited JSON (`hello`, `registered`, `peers`, `send`, `incoming`, `delivery_ack`, `send_result`, `error`) and extends the user-level pi-chat extension's protocol with the credential fields. A `hello` that announces `protocol: 2` takes part in the credential handshake, and such a peer that does not echo its credential is refused on its first `send` or `delivery_ack`. A `hello` without it (the user-level extension and older sessions) is a legacy peer: it is registered with no credential, is never marked `verified`, and its messages reach receivers as `UNVERIFIED peer`; a legacy peer cannot take an id that is bound to a credential. Older sessions share one stored id, so when a legacy peer announces an id a live peer holds, or an id bound to a credential whose holder is disconnected, the broker routes it under `<id>~2`, `<id>~3`, ... instead of refusing it. Frames are shape-checked and bounded (128 KiB envelope, 32 KiB message, 16 KiB metadata). Native Windows has no transport yet; the extension then registers `/pi-chat` only.

`list_peers` shows a peer as busy while its own turn runs. A process only takes over the socket path after the file is proven dead (nothing answers, same inode), never from a broker that answers or is slow to answer.

## Held mail

A message to a named peer that is not on the mesh is written to that peer's inbox, `<state root>/inbox/<digest of the peer id>.json` (mode 0600), and the sender's result is `queued`. The file is the truth; the socket and a directory watcher only wake the recipient. When the peer's session joins the mesh, or its inbox file changes while it runs, it takes each held message through the same path as a live one: card, steering turn, untrusted-text fence, with `queued=<time>` in the frame so the model sees the delay. A held message is delivered once. It waits at most 24 hours, then expires, and the recipient session is shown one card naming how many held messages expired and from whom (the bodies are gone; the inbox remembers up to 64 such messages until the session has saved that card); at most 32 messages and 256 KiB of bodies wait per peer, and a peer whose session cannot take a message is tried again after 30 seconds, three times in all. Settling a message (delivered, failed or expired) drops its body and keeps a receipt for 24 hours, so sending again with the same `messageId` returns the message's fate: `queued`, `received`, or `failed` with the reason. A held message is not a reply target: it is delivered with no reply expected. The standing of held mail is `verified` only when the sender sealed an HMAC with the machine's session secret that the recipient's own secret checks, never because the file says so.

## Receiving

An incoming message shows a compact card (Ctrl+O expands it), notifies the UI, and is queued as a steering turn framed as untrusted peer text. It never authorizes credential use, commands, edits or privilege changes. Replies are bounded: every message carries a `hops` count in its metadata, one past the freshest message from the peer it answers, and `agent_send` refuses past 8 hops (10-minute window) so two agents cannot answer each other without the owner. The audit log (`sessions/local/audit.jsonl`) holds metadata only, never message bodies; the only place a body is stored is a held message's inbox file, until it is delivered, fails or expires.

A peer's message that arrives while a run the owner's words decide is in progress is queued and opens its own run when the owner's run ends; it never joins the owner's run. A run a peer's message started acts for the peer, not for the owner, also when the peer is `verified`, and so do later runs no one typed (a goal continuation, a routine or worker wake) until the owner types again. In it, `git push`, `gh` commands beyond reading, package publishing, starting or messaging other agents, writing harness files and running code the gate cannot read happen only when the owner has granted that class beforehand: by typing `/edge allow git.publish` (or another class) in the session, or by listing the class under `edge.thirdPartyAllow` in `~/.pi/agent/settings.json` or the directory overlay (a project's `.pi/settings.json` does not count). Without that grant the action is held, not run: it is kept as a draft and the owner's next turn shows `Held, not run: <action> (<classes>), asked by a peer agent on pi-chat. It runs if you ask for it yourself; /edge allow <class> lets such runs do it.` The owner releases it by asking for it in their own turn, which runs it under their own authority. Other state changes through the harness's own tools (goal and routine changes among them) and handing recorded knowledge to another agent are refused in such a run. See [Third-party words](proactivity.md#third-party-words).

## Limits

Payloads are not encrypted; do not send secrets. Workers never receive these tools (`WORKER_FORBIDDEN_TOOLS`) and never join the mesh: the extension is inert in a worker session. The broker owns peer identity: it refuses a second connection that claims a live peer's id, keeps the id a connection first claimed, assigns the address itself, and drops peers whose id, name or address is empty, longer than 256 characters or holds control characters. Peer text reaches the model inside the nonce-fenced untrusted-content boundary, and the sender name and id are JSON-quoted. Each session holds a credential for its id, created once and kept in `sessions/local/credentials/` (mode 0600, one file per id): the session presents it in its first `hello`, the broker binds it to the peer id (adopting it for an id it does not know, which is how a resumed session re-claims its id after the broker restarted), returns it in a `registered` frame, and requires it on every later frame (`hello`, `send`, `delivery_ack`) and to re-claim the id after a disconnect. It reaches pi's own child processes through `PI_CHAT_CREDENTIAL` and is never given to tool commands, logs, transcripts or tool arguments. `session.key` (mode 0600, created by the first session) lets a session prove it is a pi session; the broker marks such a peer `verified`, and receivers show the peer id and that standing, never the self-declared name as identity. The broker also owns the reply-chain bound (8 hops, 10-minute window) for every message and receivers deliver a retried `messageId` once. A same-user process that can read `session.key` or the socket can still join as a new peer under its own id; lean, minimal and chat capability classes do not receive the chat tools. TCP/LAN, pairing, relay and daemon modes of the user-level extension are not part of the package.
