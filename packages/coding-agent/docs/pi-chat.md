# pi-chat

pi-chat is the packaged peer-agent message mesh. Agents running on the same machine discover each other and exchange short text messages while they work. It ships as the bundled extension `pi-chat` and is active whenever the active resource profile allows it (`all-active` does).

## Tools and command

- `list_peers` lists connected peers (`includeSelf` adds this agent).
- `agent_send` sends one message to one or more peer ids, names or addresses. `expectReply` waits for the peer's acknowledgement up to `timeoutMs` (default 15 s, maximum 120 s). `to: "*"` broadcasts only when `broadcastEnabled` is true in `config.json`.
- `/pi-chat status | setup | peers | help`. `setup` writes `config.json`, `identity.json` and `peers.json` after confirmation, so the agent keeps one persistent name. Every session still joins the mesh under its own id, so sessions sharing a name stay separate peers; a name or address shared by two peers is refused as ambiguous and the call must use the id.

## Transport

One Unix socket per user, `~/.pi/pi-chat/sessions/local/broker.sock` (override the root with `PI_CHAT_STATE_ROOT`). The first process that finds no broker becomes it; every other process is a client. The wire protocol is newline-delimited JSON (`hello`, `registered`, `peers`, `send`, `incoming`, `delivery_ack`, `send_result`, `error`) and extends the user-level pi-chat extension's protocol with the credential fields. A `hello` that announces `protocol: 2` takes part in the credential handshake, and such a peer that does not echo its credential is refused on its first `send` or `delivery_ack`. A `hello` without it (the user-level extension and older sessions) is a legacy peer: it is registered with no credential, is never marked `verified`, and its messages reach receivers as `UNVERIFIED peer`; a legacy peer cannot take an id that is bound to a credential. Older sessions share one stored id, so when a legacy peer announces an id a live peer holds, or an id bound to a credential whose holder is disconnected, the broker routes it under `<id>~2`, `<id>~3`, ... instead of refusing it. Frames are shape-checked and bounded (128 KiB envelope, 32 KiB message, 16 KiB metadata). Native Windows has no transport yet; the extension then registers `/pi-chat` only.

`list_peers` shows a peer as busy while its own turn runs. A process only takes over the socket path after the file is proven dead (nothing answers, same inode), never from a broker that answers or is slow to answer.

## Receiving

An incoming message shows a compact card (Ctrl+O expands it), notifies the UI, and is queued as a steering turn framed as untrusted peer text. It never authorizes credential use, commands, edits or privilege changes. Replies are bounded: every message carries a `hops` count in its metadata, one past the freshest message from the peer it answers, and `agent_send` refuses past 8 hops (10-minute window) so two agents cannot answer each other without the owner. The audit log (`sessions/local/audit.jsonl`) holds metadata only, never message bodies.

## Limits

Payloads are not encrypted; do not send secrets. Workers never receive these tools (`WORKER_FORBIDDEN_TOOLS`) and never join the mesh: the extension is inert in a worker session. The broker owns peer identity: it refuses a second connection that claims a live peer's id, keeps the id a connection first claimed, assigns the address itself, and drops peers whose id, name or address is empty, longer than 256 characters or holds control characters. Peer text reaches the model inside the nonce-fenced untrusted-content boundary, and the sender name and id are JSON-quoted. Each session holds a broker-issued credential: the broker returns it in a `registered` frame after the first `hello`, binds it to the peer id, and requires it on every later frame (`hello`, `send`, `delivery_ack`) and to re-claim the id after a disconnect. It reaches pi's own child processes through `PI_CHAT_CREDENTIAL` and is never given to tool commands, logs, transcripts or tool arguments. `session.key` (mode 0600, created by the first session) lets a session prove it is a pi session; the broker marks such a peer `verified`, and receivers show the peer id and that standing, never the self-declared name as identity. The broker also owns the reply-chain bound (8 hops, 10-minute window) for every message and receivers deliver a retried `messageId` once. A same-user process that can read `session.key` or the socket can still join as a new peer under its own id; lean, minimal and chat capability classes do not receive the chat tools. TCP/LAN, pairing, relay and daemon modes of the user-level extension are not part of the package.
