## CONFIRMED-001 — Orchestration profile falsely becomes a one-model custom router pool
- Category: router pool provenance
- Severity: blocker
- Evidence: `src/core/model-router/candidate-pool.ts` returns `customized: true` on the sole condition `scopedModels.length > 0`; `src/core/agent-session.ts` constructor assigns `_scopedModels = [{ model: this.agent.state.model, ... }]` whenever `config.orchestrationProfile` is set; `src/main.ts` orchestration branch overwrites `sessionOptions.scopedModels` with the single root model even when `enabledModels` was configured.
- Reproduction: start with an orchestration profile and `modelRouter.selectionMode = "auto"`; `getRouterCandidatePool()` reports `1 selected model` and every AUTO tier resolves to the root model.
- Expected: the profile owns the root model only; the router pool is the Models configuration (enabled models / `--models` / live Models selector) or every authed model.
- Observed: hard pool of one; AUTO/HYBRID and H-MoE cannot route.
- Root cause: pool customization inferred from list length; no provenance.
- Authoritative owner: `candidate-pool.ts`, `AgentSession` pool state, `main.ts` scope wiring.
- Fix: `RouterPoolState { source, models }` held by `AgentSession` separately from `_scopedModels`; `resolveRouterCandidatePool(pool, registry)` is a pure projection (`all_enabled` when no state); `main.ts` records the configured scope as the pool (`cli_models` / `enabled_models`) before the orchestration override, which no longer narrows it; the SDK derives `sdk_models` from a caller's scope only when no profile is set (and, after review, before its own orchestration override); the Models selector seeds from the pool and writes `models_selector` on edit, clearing to `all_enabled` when all/none are enabled. Diagnostics and the preview name a manual pin outside a customized pool (FC-016).
- Verification: `test/model-router-selection-modes.test.ts`, `test/agent-session-model-router.test.ts` (orchestration profile + AUTO + multi-model pool routes off-root; explicit selection is a hard pool; live edit refreshes; outside-pool pin diagnostic); Jev confirmed provenance init, main.ts ordering and selector wiring (confidence 1.0).
- Status: fixed (WO-A)

## CONFIRMED-002 — Subscription preference outranks known fitness evidence
- Category: router selection policy
- Severity: high
- Evidence: `auto-selection.ts` `compareCandidates` compares `subscription` before the probed-fit comparison; `admit()` pushes `fitness_gate` only when `deps.fitnessGate` is true, so a known-unfit candidate stays admitted with the gate off; `expert-routing/ranking.ts` comparator returns the `subscriptionPreferred` class delta before `totalScore` and reads no adequacy signal.
- Reproduction: pool = {subscription model with a failed `worker` lane, metered model with a passing `worker` lane}, `fitnessGate=false`, AUTO medium tier: the subscription model wins.
- Expected: known-fit metered beats known-unfit subscription; subscription preferred only among adequate candidates; hard admission unchanged.
- Root cause: preference applied as the outermost class ordering.
- Authoritative owner: `auto-selection.ts`, `expert-routing/features.ts` + `ranking.ts`.
- Fix: `evidenceClassOf(verdict)` and `EVIDENCE_RANK` order `compareCandidates` before the subscription comparison; `subscriptionPreferred` only counts a same-class metered loser; H-MoE `ExpertFeatureVector.adequacyClass` is derived from the same lane as `roleProbeFitness` via `laneMeetsFitnessBar` and `ExpertRankingPolicy` (v1.2) orders adequacy → subscription class → `totalScore`. Hard admission unchanged.
- Verification: `test/model-router-selection-modes.test.ts`, `test/expert-routing/expert-routing.test.ts` (unfit subscription vs fit metered → metered; fit vs fit → subscription; unprobed ordering; exhausted subscription falls through); Jev confirmed both comparator orders and the class derivation (0.97–1.0).
