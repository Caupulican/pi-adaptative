# Proactivity

Pi can review an idle conversation for unfinished requests, risks, useful suggestions and reminders. The review is enabled by default, uses the session's model unless configured otherwise, and reads the recent conversation, current accepted owner knowledge, standing preferences and the goal's status and open requirements. Owner knowledge uses the same current records as ordinary requests and continuous chat, within a 2,000-character allowance. Internal and peer inputs are labeled separately from owner instructions.

The review's only write is `raise_note`. Before deciding, it may make up to three bounded, read-only evidence requests (current files, repository history or memory, limited to what its foreground session and policy already permit); each result carries a host-issued evidence ID that a later note must cite. It cannot run commands, modify files or memory, or contact anyone. The repository's proactive reviews guide describes the read allowances. Ordinary review text stays private to the review. The host drops empty or repeated notes and limits how many notes can be delivered.

By default, an accepted note starts a parent turn without waiting for another owner message. The parent handles it under the session's existing authority and budgets. Set `proactivity.delivery` to `"note"` to carry it with the owner's next turn instead. An explicit delivery choice is preserved. Scheduled routines and goal continuation are separate features.

Acceptance saves the note and its delivery mode in the session before reporting it as raised. Pending notes survive restart. Automatic delivery resumes through the parent-input ledger and does not inherit an unrelated active goal. Note-only delivery waits for an authenticated owner input; startup, internal turns and automatic work cannot consume it. A note is consumed only after its exact content reaches the selected request and that request receives a successful final provider response. Sending a request, a tool call or a failed response leaves it pending. This also applies to continuous chat.

Continuous chat records consumed background inputs as work history. On opening an older store, it hides obsolete background projections, verifies their original session evidence and rebuilds affected summaries. Original records keep their IDs and timestamps. Missing source evidence leaves the affected background record unavailable and reported for retry; ordinary history remains usable. Only proven consumption is restored, and excluded or forgotten sessions are not imported again.

A review retains the conversation branch, settings, goal and memory revision it started with. Foreground work, navigation, relevant settings changes or changed knowledge invalidate its result. Delivery checks those inputs again before entering the session. Each started review announces a raised, quiet or failed outcome. Cancellation or provider failure before acceptance discards captured notes; cancellation after a physical receipt does not undo that saved acceptance.

## Owner controls

- `/proactivity status` shows the resolved settings, the last rolling-day measurement, the last reason a review did not start, and how the last accepted notes were delivered.
- `/proactivity off` disables idle reviews; `/proactivity on` enables them.
- `/proactivity prefs <text>` replaces the standing preferences.
- `/proactivity prefs clear` removes the standing preferences.
- `/proactivity review` requests a review immediately, subject to the remaining admission gates.

The owner does not need `/proactivity status` to learn that reviews stopped for a reason they can change. When a review is refused because the rolling-day spend reached `maxUsdPerDay`, because a configured `proactivity.model` does not resolve to an available model, or because the review model's capability tier allows no background lanes, the harness saves one notice to the conversation. It is shown with the owner's next turn and names the setting that lifts it. It never starts a turn and calls no model. Repeated refusals for the same reason add nothing; a new notice for that reason needs a review to have started (or a different reason to have applied) in between and the earlier notice to have been shown. The notice reports the state as it was first seen, and a bound that lifts before the owner's next turn does not retract it. A state seen before a new session saved its first entry is saved with that entry; until then it is kept only in memory, so it is lost if Pi exits first. The off switch, the turn and run counts and a busy foreground are normal flow and produce no notice. CI results follow the same rule. When results could not be delivered because the session stayed closed for more than 7 days, or its place was given to live sessions, the owner is told once how many results were missed and why. When CI results stop being followed (the `gh` command is missing, the repository cannot be read, or reconciliation failed three times in a row), the owner is told once per cause; recovery clears it without another notice, and retries continue at least every 30 minutes. Past `maxTurnWakesPerDay`, the held note itself reaches the owner and no separate notice is added. In-memory sessions and workers get no notice.

The root agent also has a `proactivity` tool with `view`, `set_preferences`, `clear_preferences`, `turn_on` and `turn_off` actions. It can use this when the owner asks to change the tone or frequency of what gets raised. A request to be told when something happens, or to have something checked on a schedule, is a routine (see below). Each change displays the exact proposal and requires owner confirmation in the host UI. Without a UI, on cancellation or after a conflicting edit during confirmation, it changes nothing. An unrelated setting changed during confirmation is preserved. Workers cannot receive this tool, including through explicit grants.

Preferences are a whole document, limited to 2000 characters. The agent reads the existing document before proposing a replacement. An example is: `Raise unfinished work I asked for; avoid repeated reminders.`

## Scheduled work

The root agent's `routine` tool saves work for its owning session. It supports `create`, `list`, `get`, `update`, `pause`, `resume`, `delete` and `run`. A schedule is one absolute UTC instant in epoch milliseconds (`{ "kind": "once", "at": ... }`), an elapsed interval of at least ten seconds (`{ "kind": "interval", "intervalMs": ... }`), or a calendar rule (`{ "kind": "calendar", "cron": "0 9 * * 1-5", "timeZone": "Europe/Lisbon" }`). A calendar rule has five fields (minute, hour, day of month, month, day of week with 0 or 7 for Sunday) using numbers, `*`, ranges, steps and comma lists; month and weekday names, seconds and nonstandard extensions are rejected. As in classic cron, a day field whose text starts with `*` is unrestricted, including a stepped `*/n`; only when neither day field starts with `*` does a day matching either one run. So `0 0 */2 * 1` runs on odd days that are Mondays, and `0 0 1-31/2 * 1` on odd days and on Mondays. The time zone is an IANA name; a new routine without one takes the authoring host's zone, and an update without one keeps the saved zone. A runtime whose time zone data lacks a saved zone cannot place that routine's slots: `list` and `get` show the reason as `unschedulable`, the owner's next turn carries one harness notice naming the zone (when the routine is saved or its session opens on such a runtime), the first due slot is reported to the session once as a cancelled run, and the routine runs again on a runtime with the zone or after an update to a supported one. A wall time repeated when clocks fall back runs once, at its first occurrence; a wall time skipped when clocks spring forward runs at the transition. A rule that never matches a date, such as 31 February, is refused. Missed slots of an interval or calendar schedule coalesce into one run, and its delivered result states how many earlier slots it covers; a calendar count is kept up to 1,000 and stated as "at least" that many beyond it. Condition triggers are not supported yet.

An event schedule runs on CI results instead of a clock: `{ "kind": "event", "source": "ci", "conclusions": ["failure"], "workflowPath": ".github/workflows/ci.yml" }`. `conclusions` defaults to `["failure"]`; `workflowPath` is optional and must match exactly. It considers terminal attempts of the revision this session has checked out, under the same rule as the session's CI failure note: the CI source has reconciled in this running session and the attempt is the current completed result of its revision. Each new matching attempt runs the routine once; its facts (run, attempt, conclusion, workflow, URL) are appended to the saved prompt as untrusted data, and a later attempt of the same run is a new occurrence. Nothing accepted before the routine was saved, or before its filter last changed, starts it, and a replayed or re-sealed attempt never runs twice. Several new attempts decided together run once, and an attempt superseded before it could run (for example a failure followed by a passing re-run) does not run; both are counted in the next run's missed count. When the CI source reports that it missed history while the session was closed, the next run says so. The event grants nothing: each run uses the saved worker authority and is admitted like any other run. Event routines belong to their session only and need it running; the CI failure note is delivered independently of them.

An event schedule can also run on GitHub pull request and issue activity of the checked-out repository: `{ "kind": "event", "source": "github", "kinds": ["pull-request-comment"], "ownPullRequests": true }`. `kinds` lists `pull-request-comment`, `review-comment`, `review-submitted`, `review-requested`, `issue-assigned`, `pull-request-merged` and `pull-request-closed` (review requests and assignments are those naming the signed-in login). `pullRequest`, `branch`, `ownPullRequests` (pull requests the signed-in login opened, among the repository's 100 most recently updated, at most 50) and `authors` (up to 50 logins) narrow it; comments, review comments, merges and closes without any of them, and reviews without a pull request, branch or `ownPullRequests`, are refused when saved, and a session holds at most 16 GitHub routines. Collection rides on the CI source, so it needs `gh` and the repository's `.github/workflows/ci.yml`; nothing from before the save or the last filter change starts a run. One run carries up to 25 new matching occurrences, oldest first, and counts the rest; an occurrence never runs twice, in the same or another run. Each occurrence's facts (kind, author, thread, branch, time, URL) are given to the worker as host data and each comment or review body as fenced untrusted text. A run that carries anything a third party wrote (a comment, review comment or review) is that party's: its worker cannot push, publish or write to GitHub without a standing grant of the owner, and the parent turn that reads its result keeps such actions as drafts until the owner asks in their own turn. Once a run's result is delivered, its stored occurrences keep only their bodies' lengths. Hands-off intake (below) also reads GitHub watches; it takes a pull request, branch or author only from a typed `#12`, `PR 12`, branch name or `@login`, and reads "my PR" as the owner's own pull requests.

Start windows bound late work. A one-time schedule may set `notAfter`, a UTC deadline at least one minute after `at`: if the routine has not started by then, because its session was closed or no worker was free, it is not run, and its cancellation is reported to the session once. A calendar schedule may set `maxLatenessMs` (one minute to 366 days): a slot that cannot start within that bound is passed over and counted in the next run's missed count, and the first slot passed over since the last run is also reported to the session once as a cancelled run, and an admitted slot still waiting for a worker past the bound is cancelled and reported. A window that has already closed is refused when saved. Changing only a window keeps the routine's slots and progress.

An interval, calendar or event routine may set `expiresAt`, a UTC end in epoch milliseconds that must lie in the future when saved. No new slot or CI attempt is taken at or after it; work already admitted (a run waiting for a worker, or a manual `run`) still runs. Once it passes and every run of the routine is finished and delivered, the routine is removed, including while paused, and the session receives one notice with the owner's next turn, without starting a parent turn. Saving a later `expiresAt` extends the routine in place, keeping its slots and progress. An event routine may set `stopAfterFirstRun: true` for a one-time "tell me when CI finishes": its next matching attempt runs it once, no later attempt does, and the routine is removed quietly once that run's result is delivered. Changing `stopAfterFirstRun` changes the filter, so the routine starts again from the next attempt. Every run's brief ends with the same fixed line: the run is unattended, and when it finds nothing new or nothing the owner needs it reports no owner update.

Scheduling survives faults without dropping work silently. A slot's alarm rechecks the clock at least every 20 seconds, so a slot due while the machine slept runs within that time of waking. A routine never runs while the clock reads earlier than its last edit; a manual `run` is refused with that reason, and scheduled runs wait for the clock. If the clock was once ahead and the routine's next slot was computed from that wrong time, the schedule restarts from the current time; a slot that already has its run is never run again. The sessions of one agent directory share a journal of at most 256 runs. A run leaves it, oldest first and only when room is needed, once everything it owes was delivered and it is finished, or once it stayed uncertain for seven days after its uncertainty was delivered: until then its exact worker is still looked for and a confirmed outcome is still delivered; after it, the run is no longer reconciled. While the journal is full, due slots stay due (a start window still applies), the session is warned once, and they run as results settle and free room. One routine holds at most 32 runs that are unfinished, undelivered or still uncertain within those seven days; a routine at that share starts no further run (its due slot or event attempt stays due as for a full journal, a manual `run` is refused with the reason, and the session is warned once), so no routine can take the journal from the others. Delivered results are sent before new runs are claimed, and a step that fails for one run (its dispatch, its result delivery) is reported once and retried without stopping the session's other routines.

Each routine retains its instructions, admitted worker profile and exact knowledge references. Later execution rechecks current authority and memory validity; saving a routine does not grant permanent access. It runs in an isolated worker and returns the result to the same parent session. Workers cannot create routines. The root may create, update, resume or run a routine only in a turn the owner spoke in; a turn started by a routine result, a CI event or other host input can still list, read, pause and delete routines, but cannot extend or re-trigger the automation that woke it. Scheduled work does not acquire an unrelated goal that happens to be active later.

`list` and `get` report the last run's time and status: `running` from its claim until its result, then `succeeded`, `failed`, `cancelled` or `uncertain`, and `pausedAfterFailures` while the host keeps the routine paused after failed runs. `get` also shows that finished run's summary, including a quiet result that was not delivered. Updates require the current revision from `get` or `list`. Deleting and recreating a name never makes an old revision valid again. An occurrence already admitted retains its original instructions. A manual `run` has its own occurrence and leaves the scheduled slot intact, including when the schedule is paused. A later pause or deletion cancels occurrences that have not reached dispatch; work already dispatched retains its original intent and reports its outcome.

A worker's report can state that its result needs no owner update now (`ownerUpdate: "none"`). The host honors this only for a successful run whose report it accepted against its receipts, with no blockers, inconclusive findings or review requirement. Such a run is recorded and carried with the owner's next turn without starting a parent turn; while one quiet result of a routine is waiting for that turn, later quiet runs of the same routine are recorded but not delivered. A run recovered after restart has no accepted report check and starts a parent turn. Failed, cancelled and uncertain runs, runs whose report omits the statement, and confirmed outcomes of an earlier uncertain run start a parent turn, within the routine-result wake bound (see Limits). "Tell me when X" is therefore a routine whose saved prompt checks X and reports no owner update when nothing changed; "tell me when CI fails" is an event routine.

A routine whose runs keep failing pauses itself. Three failed results in a row (the worker reported failure or a blocker, or the host could not start the run) pause it in the same store write as the third result, also for a run taken away; a succeeded result, quiet or not, starts the count again, and cancelled or uncertain results leave it unchanged (a confirmed outcome of an uncertain run counts as that outcome). The pause cancels the routine's runs that have not reached dispatch and keeps its revision, so `resume` takes the revision `list` or `get` showed. The owner's next turn carries one harness notice naming the routine, the count and the last run's first line of report; a routine paused while its session was closed is announced when the session opens. The routine stays paused until the owner resumes it: resuming needs a turn the owner spoke in, as any resume does, and starts the count again; a manual `run` still runs it while paused.

Routines are also created without the tool. Once an owner turn settles and the session has been idle for two seconds, the host reads the owner's new messages once. When a message explicitly asks for work on a recurring schedule, at a stated time, or when a CI attempt ends, the host creates a read-only routine through the same routine owner as the tool: the same parent check, worker authority capture and store limits, without write authority: its worker cannot edit existing files, create files outside its scratch area or use the network. The routine's instruction is the owner's own words copied from the message. A request found only in pasted or quoted text, a question, a hypothetical or work for now is not scheduled; text pasted into the interactive editor counts as pasted whatever its delimiters, except a part the owner edited. A message with no timing words at all is skipped without any request, and pasted text is never sent to the model that reads the messages. The host builds the schedule by reading the owner's words for the timing itself (English, Portuguese and Spanish): the schedule, how long it lasts, which CI results it watches and its zone come from those words alone, and every word of the quoted timing must be one the host reads. A request is dropped, with a notice naming the words (`Could not schedule what reads as a request: <reason> - "<instruction>"`), when the model's reading differs, when the quoted timing holds a word the host does not read, when timing words of the same sentences lie outside the quoted timing and instruction (or inside the instruction as a schedule: "summarize last week's PRs" is fine, "summarize at 9" is not), when another sentence only adds timing ("At 9pm.", "Not on Fridays."), or when the words say something the host cannot schedule exactly: "first Monday", "next Friday", "the last day of the month", "every other day", "except Fridays", "not on weekends", "between 9 and 5", "9-17", "for two weeks", "in 10 minutes", "starting Monday", "during business hours", "at lunch", "EOD", "until 5pm", "half past 9", "twice a day", "in May", "5/11", "EST", "UTC+3", "Pacific time", "Mon-Fri", or an interval of seconds, months or years. "Every day at 9" is a daily request. An hour without am or pm reads through a stated part of the day ("every evening at 7" runs at 19:00, "às 8h da noite" at 20:00); otherwise it runs on a 24-hour clock ("at 9" is 09:00) and the notice says so. When the owner names only a part of the day, it runs at a fixed hour (morning 09:00, noon 12:00, afternoon 15:00, evening 18:00, night 21:00); with no time at all it runs at 09:00. These host-chosen hours get a 30-minute start window, after which a slot is skipped instead of run late. A monthly request on day 29, 30 or 31 runs on that day, and its cadence names the months that have no such day. A daily request, or a recurring part of the day, that names no days runs on all seven days; named days ("every day on Mondays and Fridays", "weekdays") narrow it to them. The routine runs in the zone the owner's timing words name (UTC, "Lisbon time", "hora de Lisboa", or a city), otherwise this host's zone. A standing request ("every time", "whenever", "every morning") has no end. A request meant only until something happens ("until the release ships") keeps the end the owner stated: every run's worker is told it and is asked to report truthfully whether its run found that end reached. When a run that completed cleanly reports it reached, the host starts no further run (also while the session is closed), removes the routine once its runs are delivered and tells the owner once, with the next turn (a closed session's routine is removed when the session next runs, and nothing repeats after a restart); the host does not check the end itself, so the routine still ends 14 days after the request at the latest; a one-time "tell me when CI finishes" or "the next time CI fails" runs for the next matching attempt only and stops watching after 14 days if none comes. The notice states that end. A CI request must say every time or the next time ("if CI fails" is dropped), watches every outcome its words name ("finishes" names all of them), and may name one workflow file ("every time ci.yml fails"): the host watches exactly that workflow when the session has received a CI attempt of it from a ready CI source, and drops the request when it names a file the session does not watch (the CI source watches `ci.yml`), more than one file, or when no CI attempt has been seen yet. At most two requests are taken from one message. When System One is bound it judges each request, otherwise the session model does, and both answers must find the request explicit and the proposed schedule faithful to the owner's words. The owner's next turn carries a notice, `Scheduled (read-only): <cadence> - "<instruction>"` with the cadence in plain words and the routine's zone, followed by each part the host chose, or `Not scheduled: <reason>` when the request would run more often than every 15 minutes or more than 96 times a day, or names a time already passed. Changing, widening or removing the routine goes through the `routine` tool. Each notice is saved once, also after a restart or a refused delivery, and a request whose message the owner navigates away from (`/tree`) while it is judged creates nothing. A `routine` save marks every owner message its context held, steering sent before the save included, and intake does not read those again; a message from an earlier turn that nothing answered is still read. A marked message is skipped whole, also a part the model left unanswered. A request decided once is never scheduled again, also after its routine was deleted. When intake is inactive for a reason the owner can act on (no model, an unpriced model, no bounded judge, a spent allowance) while the newest message states timing, when a message that states timing is not read because it holds a secret or is too long, or when the owner's latest messages could not be read after repeated failures or a spent allowance, the owner is told once with the next turn. Intake spending is accounted to the session (`routine_intake`): at most $0.03 per message read and $0.30 per session, within the session's estimated-cost bound. A model without declared prices, an unsaved session or `routines.automaticIntake: false` starts no intake requests. `/proactivity status` shows whether intake is on, its judge, its spending and its last pass.

Occurrence claims and results are durable. Restart recovery reconciles the exact worker execution, and a dispatch whose outcome cannot be established is reported as uncertain instead of being repeated. If the exact worker later finishes, its confirmed outcome is delivered separately while the earlier uncertainty receipt is retained. A result is acknowledged only after the parent has durably accepted it. The parent's response is tracked separately, so a restart can resume an unhandled result without appending it twice.

A routine whose session is closed runs away, in the background bot daemon. Nothing has to be started: a session starts the daemon when it starts while any enabled routine is saved, and whenever a routine is saved and no daemon holds its lease. Only one daemon runs per agent directory. It keeps running after every session closes, and the next session start or routine save starts it again after it stopped. The daemon takes a due clock or manual run of a session that no live process holds open, opens that session read-only and runs the occurrence through the same worker lifecycle. It never writes the session's transcript: the run's claims and its result wait in the routine store and the run's own records, and the session receives them when it opens, each claim before the result it explains, delivered once. A session that is open while another host records writes for one of its runs lands them on the next routine store change. Stopping the daemon suspends a run in progress; it resumes when the daemon or the session holds that session again.

Only read-only runs go away. The saved worker profile may hold the read capabilities (files, worktrees, the repository, sources and settings), use the network, and, when the profile is read-only, run the shell commands the deterministic read-only line admits. A run that needs any other capability, write paths, saved knowledge, a goal binding or host-event subscriptions waits for its session. `routines.away` bounds the spend (see [settings](settings.md#routines)). A run is charged its full `maxUsdPerRun` from the moment the daemon admits it, however long it waits or runs, until it finishes; a finished run is then charged what its attempts measured (its worker, retries and verifier, read from the ledger when it ends and saved on the run, so a daemon restart keeps it) for 24 hours after it finished, or its full `maxUsdPerRun` when that could not be read. An uncertain run stays charged in full until it is resolved, at most until a day after the routine journal's week of uncertain retention. A run that never started is charged nothing. A run is admitted only while the charges across the agent directory plus another `maxUsdPerRun` stay within `maxUsdPerDay`, compared exactly in whole micro-dollars. At most `maxParentHosts` sessions are held open away at once, and one run away per routine waits for its session at a time: while a routine's run away is unfinished or its result is not yet delivered, its later slots stay due and the session's next run counts them as missed. A due run the daemon does not take (no room in the day, an earlier run away not yet delivered, a capability it cannot grant, a pinned model without declared prices, a saved origin that is no longer on the session's branch, a session with no saved run or file, a lease registry it cannot read) claims nothing and stays due. Its reason is recorded on the routine once, and when the session opens it runs the slot itself and reports once why it did not run away. A run the daemon claimed but could not hand to its worker (the session opened, the specialist was busy, the session file is gone) returns to the session's queue unclaimed and uncharged, and the session runs it when it opens.

An event routine of a closed session is followed away too, when its run could go away and `proactivity.ciEvents` is not off in the owner's global settings. The daemon follows the session's CI for the session's own working directory, with one CI check loop per session (not one per routine) on the session's own CI position: it catches up on the CI results and reconciles them before it decides anything, as the session does, and decides each attempt by the same rule. A decided attempt becomes a run the daemon takes under the rules of any run away (the day's spend bound, one run away per routine waiting for its session), and its result is delivered when the session opens. The session's own CI source then continues from the saved position, so no result is lost or decided twice. A session that opens while the daemon still follows its CI takes it back at once, and the daemon stops following it. The daemon stops following a session's CI when the session opens, its file is gone, no event routine of it may run away, routines away are turned off or the daemon stops; each stop is in the daemon's reports. When the daemon cannot follow the CI (the `gh` command is missing or not signed in for it, GitHub cannot be reached, checks keep failing, or the project has no CI workflow), the reason is recorded once on the session's event routines as why they wait for the session, and the session reports it when it opens; following again clears it. When the session opens while the daemon still cannot follow its CI, the session also gets one notice with the owner's next turn saying since when its CI was not followed. A gap in the CI history found away, and a CI journal replaced while the session is closed, are told when the session opens. Following a session's CI does not count toward `maxParentHosts`.

A run away is held to its `maxUsdPerRun` while it runs. Before each provider request of the run (its worker, retries and verifier share the bound), the host prices the request's input at the model's declared rates and caps the request's output tokens to what the rest of the run's bound pays for. A request whose input alone exceeds what is left, and any request on a model without declared prices, is refused and ends the run failed (`worker_run_cost_budget_exhausted`, `worker_run_model_unpriced`); a run whose pinned worker or verifier model has no declared prices is not admitted away in the first place. The run's worker reads only the session's working directory, its own scratch directory and the workspace its profile names: its file tools and its read-only shell refuse every other path, also one that a link inside the directory points to. A read-only worker without a network grant runs git with lazy fetch, credential prompts, the pager and the filesystem monitor turned off. A turn the session itself queued on a specialist stays the session's: the daemon does not run it, deliver it or route the replies to it, and a run that would queue behind it is deferred.

The daemon starts in the agent directory with a reduced environment: platform, locale and temp variables (PATH without entries inside the project that started it), `PI_*` settings without the starting session's identity, provider credential variables, the variables the global `auth.json` and `models.json` reference as `$NAME`, the secret-manager session, proxy and certificate settings, and gh's configuration directory and host (`GH_CONFIG_DIR`, `GH_HOST`). gh's tokens (`GH_TOKEN`, `GITHUB_TOKEN`, `GH_ENTERPRISE_TOKEN`, `GITHUB_ENTERPRISE_TOKEN`) are not in its environment, unless the global `auth.json` or `models.json` references one as `$NAME`: the session that starts the daemon writes them once to its input, and only the `gh` commands of its CI checks receive them, never a command a run starts. A token changed later reaches the daemon when it next starts. A gh sign-in kept only in a desktop keyring reached over the session bus is not available to the daemon. It holds one credential store for all its runs and reloads it when `auth.json` or `models.json` changes on disk. Stopping the daemon waits for a settings reload in progress.

`/bot daemon status` shows whether the daemon runs, each routine it did not run away with the reason, how it last ended (released by `/bot daemon stop`, stopped by a signal, or the error that ended it) and its most recent reports (at most 20 are kept). When a daemon ended on an error, the session that starts the next one reports it once. A worker process never starts the daemon, and the daemon and every run away apply only the owner's global settings: no project's settings, trusted or not, change what an unattended run may do, and a run away installs no package and reads no project instruction file.

## Third-party words

Every message that can open or steer a turn carries its origin, recorded where it is created and saved with it: the owner's typed or pasted words, the owner's own automation (routines, CI events, proactive notes, goal continuation, worker results, harness notices, installed extensions), or a third party's words: those an extension delivers with an origin (a peer agent on pi-chat, verified or not, or another channel), host events of a kind whose content someone else writes (CI results are the owner's own systems), the result of a routine run such words decided, and the report of a worker that carries such words. Only the owner's typed words and a third party's words decide a run's authority. Every run, however it starts (a typed prompt, a queued message, a goal continuation, a routine or worker wake, a replayed input or a retry), takes the authority of the latest deciding message on the session branch, and each message the run takes in later decides again. So a continuation or wake after a peer's run stays the peer's until the owner types. Compaction keeps the deciding messages, and resuming, forking or moving in the tree reads them from the branch again. A saved message whose origin cannot be read counts as a third party's; a message without any identity decides nothing and is never the owner's.

A third party's message never joins a run the owner's words decide: it waits in the queue and opens its own run when the owner's run ends. An extension that delivers a message with an origin it cannot state (a channel that is not 1 to 128 characters, a sender, verified flag or text of the wrong type) is refused, and the extension is told the message was not accepted.

A run that carries a third party's words cannot act for the owner on its own:

- `git push` and `git send-email`, package publishing (also with options such as `npm --registry ... publish`), every `gh` command outside a read-only set (`pr view`, `issue list`, `run watch`, `api` reads and the like; a `gh` alias counts as outside it), and starting or messaging other agents (`delegate` launches and messages, `pi_collaboration` launches and follow-ups, a goal's `dispatch_worker`) run only under a standing grant of the owner. Their classes are `git.publish`, `package.publish`, `forge.write` and `agent.delegate`.
- Writing harness files (settings, models, memory and state under the agent directory, a project's `.pi/extensions`, `.pi/SYSTEM.md`, git hooks and git config) with the `write` or `edit` tools, a shell redirection, `tee`, a `cp`, `mv`, `install` or `ln` destination, `sed -i` or `dd of=` is `settings.authority`. Writing the session store is never granted to such a run.
- Running code the gate cannot read is `operation.irreversible`: the `python` tool, program text given on the command line (`python -c`, `node -e`, `perl -e` and the like), `eval`, a shell or interpreter reading commands from its input (`curl ... | sh`, a here-document), a program named by a variable, and a line the gate cannot parse.
- A standing grant is `/edge allow <class>` typed by the owner, or a class listed in `edge.thirdPartyAllow` in the global settings or the directory overlay (a project's `.pi/settings.json` does not count) that `edge.allow` also grants. `edge.thirdPartyAllow` defaults to none. The owner's `edge.allow`, a grant given at an edge prompt, one System One reads from the owner's words, a `goal grant_edge` and YOLO mode cover only the owner's own runs. A standing grant stays standing when a later, weaker record of the same class is added, and a fork keeps it.
- Without such a grant the action is prepared instead of run. It is kept as a draft, identified by the third party's message and the action. The tool result says it is held, who asked for it and how the owner can release it, and the owner's next turn carries one notice: `Held, not run: <action> (<classes>), asked by <origin>. It runs if you ask for it yourself; /edge allow <class> lets such runs do it.` The same request asking the same action again keeps the same draft and adds no notice. When the owner's own run performs the same action, the draft is recorded as released; once the owner has typed after it and that run ended without it, it counts as dismissed. A branch keeps at most 64 pending drafts; past that, one notice says the later ones are not recorded. Where no notice can be saved (an unsaved session, print or RPC mode without a session file, a child session), the tool result says so instead of saying the owner is told.
- Actions of the harness's own tools that change state are refused outright with the reason, except the delegation launches above. A closed table lists the actions that only read (for example `goal get`, `routine list` and `get`, `delegate status` and `wait`, `task_steps list`); every other action of these tools, and any action of a tool not in the table, is refused. The owner's records and replies are refused for every action, reads included: `knowledge`, `memory` (its history reads too) and `channel_reply`. Handing recorded knowledge to another agent (the `knowledge` parameter of `delegate` and `pi_collaboration`) is refused as well.
- The run's system prompt leaves out the owner's memory block (in OKF: `MEMORY.md`, the project's `MEMORY.md`, the `USER.md` preferences and memory extensions' blocks). The run reads one line saying the memory is withheld, and the owner's next run sends the block again. Each variant keeps its own cached prompt prefix, so switching between them reports no prefix change. ICM's prompt block holds no owner records and is the same for both. A worker that carries such words gets no owner working preferences in its system prompt.
- A worker that carries such words follows the same classes and the same standing grants, also under YOLO. Such a worker is one a routine run a third-party event started, one such a run starts (a background worker or a managed lane), every worker it reaches through a start or a message, and a running worker from the moment it takes in a message that carries such words; its later turns and retries carry them too. It keeps no drafts: an uncovered action is refused, the result says how the owner releases it, and the worker reports it in its result so the parent can tell the owner. It reads none of the owner's memory. Its report opens a run that carries a third party's words. The closed table of reading actions applies to the parent session only. System One judges such a worker's calls as it judges such a run's (next point), whatever the parent's current run.
- System One, when it judges such a run's tool calls, is given no owner request: the owner's earlier words never approve them, a call is judged on its effects alone, its verdicts are cached apart from the owner's, and only a standing `operation.irreversible` grant lets an irreversible call run. YOLO mode does not skip that check.
- A goal's owner evidence skips messages from a third party, so a peer's words never satisfy a goal's owner requirement.

The rule reads the command line, not the files it runs: a script the run executes (`./deploy.sh`, `bash script.sh`, `npm run release`) is not read, so what it does is not classified, and a git alias from a git config file is not resolved. Extension and MCP tools are not classified unless they take an `action` argument (which is then refused), and `package.install`, `agent_send` (which sends text to another session) and a worker's `bot_message` send (which reaches only this session's workers, and carries the sender's words to them) are not classified; and the release of a held action goes through the model, which must perform it again in the owner's run. A managed lane's child process is not told that its task carries a third party's words. A message delivered to a worker's saved conversation while no attempt of it runs does not mark that conversation. Sending mail, spending money and handling credentials stay with the edge policy and System One. Runs the owner's words decide are unchanged.

## Limits

The defaults allow one review after two idle minutes, require three new owner turns between reviews, permit four reviews per running session and allow two notes per review. The review uses at most two provider requests. See the [settings reference](settings.md#proactivity) for all fields.

Two bounds hold across sessions and restarts over the last rolling 24 hours. They count every session stored with the current one: all projects under the agent directory, or only the custom session directory when one is configured. They are measured from recorded usage when a review is admitted, so they survive a restart and opening more sessions.

- `maxUsdPerDay` (default `$0.25`) bounds review spend. Once the recorded review spend reaches it, no review starts and the gate reads `max_usd_per_day_reached`. Below it, a review's bound is the smaller of `maxUsd` and what remains of the day.
- `maxTurnWakesPerDay` (default `3`) bounds parent turns that proactive note deliveries and CI events delivered to the main session start without an owner message; the two count together. Past it, the review still runs, but its accepted notes wait for the owner's next turn, and a CI event is likewise saved to the conversation and carried with the owner's next turn. The status reads `max_turn_wakes_per_day_reached` on the `Last note delivery` or `Last CI event delivery` line. Nothing is dropped, with one exception: a held CI result that a later attempt of the same run replaces before the owner's next turn is skipped, with a record in the conversation, and the later attempt's result is delivered instead. Held notes carried with the owner's turn state when they were first held. A delivery interrupted after it was saved keeps the mode it was saved with. CI events a subscribed worker receives start no parent turn and are not counted. Routine results have their own bound, below, and do not count here.
- `routines.maxResultWakesPerDay` (default `10`) bounds parent turns that routine results start, including those of event routines and of runs taken away (counted when their session receives them). Quiet results and end notices ride with the owner's next turn and never count. Past it, a result is saved to the conversation and carried with the owner's next turn instead of starting one; while one such result of a routine waits for that turn, later results of the same routine are recorded on the routine (`get` shows the latest) and in its run history but not delivered again. The first result held this way adds one harness notice for the owner's next turn naming the setting; the notice can recur only after a routine result started a turn again. Nothing is dropped, and a delivery interrupted after it was saved keeps the mode it was saved with.

`0` is a valid value for each bound; `enabled` remains the off switch for reviews. Sessions that admit reviews or deliver events or results at the same moment can each pass the same measurement, so concurrent sessions can exceed a bound by one review or one wake each.

Before each review provider request, the host estimates the complete request cost, including tools and long-context pricing, and reduces the output allowance to fit the review's remaining bound. If even one output token cannot fit, it sends no request and the started review ends as failed. This is an estimate, not a guarantee of the provider's eventual bill; measured overspend stops further review requests and note delivery. These bounds cover the isolated review. A parent turn uses normal session accounting and budgets and can incur additional inference cost; `maxTurnWakesPerDay` and `routines.maxResultWakesPerDay` bound how many such turns start without an owner message.

Custom models need declared prices for these background reviews. An explicitly configured zero price is valid; omitted prices are unknown and prevent a review request. Tiered prices use the same rate selection as measured usage.

The review reserves usage-journal capacity before starting. Each dispatched request retains its original accounting identity until the provider reports usage, including after cancellation. Cancellation can finish the review immediately while the provider request remains in flight; it does not release that request's accounting or admission capacity. Unresolved requests stay visible in the session journal with unknown usage, without an invented charge or automatic replay. Measured responses replace those entries and remain attributed to the starting session. Missing usage or failed receipt retention stops further spending. A restarted session starts a new per-session review count; the rolling-day bounds read recorded session usage and do not reset. Receipts a closed session could not record in its session file are not visible to other sessions' measurement.
