# Proactivity

Pi can review an idle conversation for unfinished requests, risks, useful suggestions and reminders. The review is enabled by default, uses the session's model unless configured otherwise, and reads the recent conversation, current accepted owner knowledge, standing preferences and the goal's status and open requirements. Owner knowledge uses the same current records as ordinary requests and continuous chat, within a 2,000-character allowance. Internal and peer inputs are labeled separately from owner instructions.

The review's only write is `raise_note`. Before deciding, it may make up to three bounded, read-only evidence requests (current files, repository history or memory, limited to what its foreground session and policy already permit); each result carries a host-issued evidence ID that a later note must cite. It cannot run commands, modify files or memory, or contact anyone. The repository's proactive reviews guide describes the read allowances. Ordinary review text stays private to the review. The host drops empty or repeated notes and limits how many notes can be delivered.

By default, an accepted note starts a parent turn without waiting for another owner message. The parent handles it under the session's existing authority and budgets. Set `proactivity.delivery` to `"note"` to carry it with the owner's next turn instead. An explicit delivery choice is preserved. Scheduled routines and goal continuation are separate features.

Acceptance saves the note and its delivery mode in the session before reporting it as raised. Pending notes survive restart. Automatic delivery resumes through the parent-input ledger and does not inherit an unrelated active goal. Note-only delivery waits for an authenticated owner input; startup, internal turns and automatic work cannot consume it. A note is consumed only after its exact content reaches the selected request and that request receives a successful final provider response. Sending a request, a tool call or a failed response leaves it pending. This also applies to continuous chat.

Continuous chat records consumed background inputs as work history. On opening an older store, it hides obsolete background projections, verifies their original session evidence and rebuilds affected summaries. Original records keep their IDs and timestamps. Missing source evidence leaves the affected background record unavailable and reported for retry; ordinary history remains usable. Only proven consumption is restored, and excluded or forgotten sessions are not imported again.

A review retains the conversation branch, settings, goal and memory revision it started with. Foreground work, navigation, relevant settings changes or changed knowledge invalidate its result. Delivery checks those inputs again before entering the session. Each started review announces a raised, quiet or failed outcome. Cancellation or provider failure before acceptance discards captured notes; cancellation after a physical receipt does not undo that saved acceptance.

## Owner controls

- `/proactivity status` shows the resolved settings, the last rolling-day measurement, the last reason a review did not start, and how the last accepted notes were delivered.
- `/proactivity off` disables idle reviews; `/proactivity on` enables them.
- `/proactivity prefs <text>` replaces the standing preferences.
- `/proactivity prefs clear` removes the standing preferences.
- `/proactivity review` requests a review immediately, subject to the remaining admission gates.

The root agent also has a `proactivity` tool with `view`, `set_preferences`, `clear_preferences`, `turn_on` and `turn_off` actions. It can use this when the owner asks to change the tone or frequency of what gets raised. A request to be told when something happens, or to have something checked on a schedule, is a routine (see below). Each change displays the exact proposal and requires owner confirmation in the host UI. Without a UI, on cancellation or after a conflicting edit during confirmation, it changes nothing. An unrelated setting changed during confirmation is preserved. Workers cannot receive this tool, including through explicit grants.

Preferences are a whole document, limited to 2000 characters. The agent reads the existing document before proposing a replacement. An example is: `Raise unfinished work I asked for; avoid repeated reminders.`

## Scheduled work

The root agent's `routine` tool saves work for its owning session. It supports `create`, `list`, `get`, `update`, `pause`, `resume`, `delete` and `run`. A schedule is one absolute UTC instant in epoch milliseconds (`{ "kind": "once", "at": ... }`), an elapsed interval of at least ten seconds (`{ "kind": "interval", "intervalMs": ... }`), or a calendar rule (`{ "kind": "calendar", "cron": "0 9 * * 1-5", "timeZone": "Europe/Lisbon" }`). A calendar rule has five fields (minute, hour, day of month, month, day of week with 0 or 7 for Sunday) using numbers, `*`, ranges, steps and comma lists; month and weekday names, seconds and nonstandard extensions are rejected. When both day fields are restricted, a day matching either runs. The time zone is an IANA name and defaults to the zone of the authoring host. A wall time repeated when clocks fall back runs once, at its first occurrence; a wall time skipped when clocks spring forward runs at the transition. A rule that never matches a date, such as 31 February, is refused. Missed slots of an interval or calendar schedule coalesce into one run, and its delivered result states how many earlier slots it covers. Condition triggers are not supported yet.

Start windows bound late work. A one-time schedule may set `notAfter`, a UTC deadline at least one minute after `at`: if the routine has not started by then, because its session was closed or no worker was free, it is not run, and its cancellation is reported to the session once. A calendar schedule may set `maxLatenessMs` (one minute to 366 days): a slot that cannot start within that bound is passed over and counted in the next run's missed count, and an admitted slot still waiting for a worker past the bound is cancelled and reported. A window that has already closed is refused when saved. Changing only a window keeps the routine's slots and progress.

Each routine retains its instructions, admitted worker profile and exact knowledge references. Later execution rechecks current authority and memory validity; saving a routine does not grant permanent access. It runs in an isolated worker and returns the result to the same parent session. Workers cannot create routines. Scheduled work does not acquire an unrelated goal that happens to be active later.

`list` and `get` report the last run's time and status: `running` from its claim until its result, then `succeeded`, `failed`, `cancelled` or `uncertain`. Updates require the current revision from `get` or `list`. Deleting and recreating a name never makes an old revision valid again. An occurrence already admitted retains its original instructions. A manual `run` has its own occurrence and leaves the scheduled slot intact, including when the schedule is paused. A later pause or deletion cancels occurrences that have not reached dispatch; work already dispatched retains its original intent and reports its outcome.

A worker's report can state that its result needs no owner update now (`ownerUpdate: "none"`). The host honors this only for a successful run whose report it accepted against its receipts, with no blockers, inconclusive findings or review requirement. Such a run is recorded and carried with the owner's next turn without starting a parent turn; while one quiet result of a routine is waiting for that turn, later quiet runs of the same routine are recorded but not delivered. A run recovered after restart has no accepted report check and starts a parent turn. Failed, cancelled and uncertain runs, runs whose report omits the statement, and confirmed outcomes of an earlier uncertain run start a parent turn. "Tell me when X" is therefore a routine whose saved prompt checks X and reports no owner update when nothing changed.

Occurrence claims and results are durable. Restart recovery reconciles the exact worker execution, and a dispatch whose outcome cannot be established is reported as uncertain instead of being repeated. If the exact worker later finishes, its confirmed outcome is delivered separately while the earlier uncertainty receipt is retained. A result is acknowledged only after the parent has durably accepted it. The parent's response is tracked separately, so a restart can resume an unhandled result without appending it twice.

The owning session must currently be running for execution. The bot daemon records due work but does not advance the schedule or execute a parent session in the background. Headless execution remains a separate missing capability.

## Limits

The defaults allow one review after two idle minutes, require three new owner turns between reviews, permit four reviews per running session and allow two notes per review. The review uses at most two provider requests. See the [settings reference](settings.md#proactivity) for all fields.

Two bounds hold across sessions and restarts over the last rolling 24 hours. They count every session stored with the current one: all projects under the agent directory, or only the custom session directory when one is configured. They are measured from recorded usage when a review is admitted, so they survive a restart and opening more sessions.

- `maxUsdPerDay` (default `$0.25`) bounds review spend. Once the recorded review spend reaches it, no review starts and the gate reads `max_usd_per_day_reached`. Below it, a review's bound is the smaller of `maxUsd` and what remains of the day.
- `maxTurnWakesPerDay` (default `3`) bounds note deliveries that start a parent turn. Past it, the review still runs, but its accepted notes wait for the owner's next turn, and the status reads `max_turn_wakes_per_day_reached`. No accepted note is dropped.

`0` is a valid value for either bound; `enabled` remains the off switch. Sessions that admit reviews at the same moment can each pass the same measurement, so concurrent sessions can exceed a bound by one review or one wake each. Only proactive notes count toward the wake bound; CI event deliveries are separate.

Before each review provider request, the host estimates the complete request cost, including tools and long-context pricing, and reduces the output allowance to fit the review's remaining bound. If even one output token cannot fit, it sends no request and the started review ends as failed. This is an estimate, not a guarantee of the provider's eventual bill; measured overspend stops further review requests and note delivery. These bounds cover the isolated review. A parent turn uses normal session accounting and budgets and can incur additional inference cost; `maxTurnWakesPerDay` bounds how many such turns start without an owner message.

Custom models need declared prices for these background reviews. An explicitly configured zero price is valid; omitted prices are unknown and prevent a review request. Tiered prices use the same rate selection as measured usage.

The review reserves usage-journal capacity before starting. Each dispatched request retains its original accounting identity until the provider reports usage, including after cancellation. Cancellation can finish the review immediately while the provider request remains in flight; it does not release that request's accounting or admission capacity. Unresolved requests stay visible in the session journal with unknown usage, without an invented charge or automatic replay. Measured responses replace those entries and remain attributed to the starting session. Missing usage or failed receipt retention stops further spending. A restarted session starts a new per-session review count; the rolling-day bounds read recorded session usage and do not reset. Receipts a closed session could not record in its session file are not visible to other sessions' measurement.
