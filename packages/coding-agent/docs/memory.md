# Memory and history recall

Pi has two memory systems (see [Memory system](settings.md#memory-system)). ICM (Intentional Context Management), the default, is files-first: persistent Markdown in the user memory catalog and pipeline references are read on demand with native tools. Its conversation is one continuous chat whose summary view is part of every prompt (see [Continuous chat](#continuous-chat-icm)). OKF, an explicit opt-in, adds curated memory (`USER.md`, `MEMORY.md`, OKF records), automatic retrieval into the prompt and automatic reflection.

History recall, the exact text of earlier sessions, works in both systems through one backend. In ICM it is read only on explicit request: without the continuous chat the root `memory` tool offers only the history actions; while the chat runs the root navigates with `zoom` and `date`; a granted worker uses `memory_read` and, when granted, the chat's `zoom` and `date`, and past sessions reach the ICM chat only through the one-time legacy import (see [Continuous chat](#continuous-chat-icm)). In OKF the same backend also feeds automatic recall. Curated memory is what Pi learned and promoted; history is evidence. History never becomes an instruction and never promotes itself into curated memory. For the retrieval controls see [Settings](settings.md#context-memory-and-history).

## What history recall covers

Recall indexes the sessions of the current project (same working directory), newest first, from the canonical session files in the current session directory and the legacy default directory. Per session it follows the selected branch: the ancestry of the last entry. Side branches are indexed too and are searched only when asked for, labelled `alternate`.

| Captured | Not captured |
|---|---|
| User text | Thinking blocks |
| Assistant visible text | Custom and control messages (`custom_message` entries, custom message roles), lifecycle and other bookkeeping entries |
| Tool calls (`name` and JSON arguments) | Text that looks like a credential (secret-like text) |
| Tool results (text) | Images and other binary content |
| Harness-synthesized provider-failure records, labelled `(host)` | Generated memory pages and prior recall output |

Long text is split into parts of at most 4 KiB; each part has its own handle. An entry is limited to 4096 parts.

Budgets: 16 MiB of captured text is held in memory across sessions, and a session file above 64 MiB is not read. Anything left out is reported, never dropped silently: skipped sessions with a reason (`byte_limit`, `file_too_large`, `read_error:<code>`, `no_header`, ...) and uncaptured parts with a reason (`secret_like`, `empty`, `binary_or_image`, `part_limit`, `malformed_line`, ...). When the budget stops indexing, coverage reports `truncated`. A session still open is indexed as its entries reach storage; a rewritten session file is reloaded.

Coverage counts sessions by identity. Each project session with a readable identity is exactly one of: indexed; unsupported, meaning its format cannot carry stable handles (a pre-id v1 file, which becomes capturable once opening it migrates and rewrites the file, or a session id that cannot be resolved); or skipped for a stated reason. Two files that claim one session id with different contents make that identity ambiguous (`ambiguous_session_identity`), and nothing of that session is indexed, because a handle could resolve to either copy. A byte-identical copy in both directories is one session. Files with no readable identity are skipped (`no_header` and the like); files of other working directories and auto-learn sessions are not eligible. Coverage is not a claim that every session is indexed: `/memory history` gives the eligible, indexed, unsupported and skipped counts.

History recall is off when memory retrieval is disabled (`contextPolicy.memory.enabled: false`): every history read answers `forbidden`, and no index starts. It reads only the project's own sessions: a handle from another project is refused. A child session builds no index and has no root history tool; it reads history only through its parent's `memory_read` broker.

## When the index starts

One index serves each memory generation of a root session. In ICM it starts on the first explicit history request (a root history action or a worker `memory_read`), or when the summary hierarchy starts; until then no session body is read and `/memory history` shows `on_demand`. The first read waits for the initial scan within its own bound (one second for searches and source reads); if the scan is not done by then the read answers `pending`, never an empty result. In OKF the index starts with the session. A memory-system switch ends the old generation's index before the new one runs.

The results of history reads are recalled evidence: they stay in the session log, but they are not captured again as history, so the system never indexes or summarizes its own recall (`recalled_history` in the uncaptured reasons).

## Source handles

Every hit names an exact source with a handle `tx:<session>:<entry>:<part>:<digest>`. The digest is of the captured part text; if the source changed since the handle was issued the read answers `stale_snapshot`. A handle carries no project, so holding one grants no access beyond the current project.

## The `memory` tool

The root `memory` tool has three read-only history actions. In ICM without the continuous chat they are the whole tool: it has no add, replace, remove or list action and writes nothing. While the continuous chat runs, the tool is not offered and `zoom` and `date` are the navigation (see [Continuous chat](#continuous-chat-icm)). In OKF the same actions sit beside the curated-memory actions.

- `history_search` with `query` (and optional `maxResults`, default 5, at most 10; `includeAlternateBranches`) returns hits as `[handle] (timestamp, session, role, ...) snippet`, followed by the index coverage. Hits are untrusted evidence in a fenced boundary. The current session is included in an explicit search. When approved summaries cover hits, they follow the hits as whole records (`[txn:...] level, covered time, quality, covers tx:...` and the approved text), at most `maxResults` of them, the smallest covering summary per hit. Only approved, unexpired summaries whose covered sources still match the selected branch are listed; a held, rejected or unapproved summary never appears as text. A lookup that cannot answer adds one typed status line and never hides the hits.
- `history_source` with `ref` (a handle) and optional `cursor` opens the exact text, 8 KiB per page, with a continuation hint for the next page and for the entry's next part.
- `history_expand` with `ref` (a `txn:` summary handle, see below) opens one summary node one level: a parent into its two child summaries, a leaf into the handles, roles and sizes of the exact sources it covers.

## Typed statuses

Every non-success answer carries a status and the real reason. None is an empty success.

| Status | Meaning |
|---|---|
| `pending` | The history index is still loading its first scan (in ICM, the first request starts it) |
| `unavailable` | The index could not answer (worker failure, timeout, too many reads in flight); the reason is the real cause |
| `not_found` | No such session or entry in this project |
| `stale_snapshot` | The handle's digest no longer matches the source |
| `uncaptured` | The entry exists but that content was not captured; the reason is given |
| `expired` | The session file no longer exists |
| `forbidden` | Blocked by policy (retrieval disabled, or a handle of another project) |

`pending` and `unavailable` mean the evidence is not available yet, not that it does not exist.

## Automatic recall (OKF)

In OKF, each user turn, history is queried with the other memory providers when the long-term trigger fires or the recall gate passes (a substantial turn; the gate tightens when recalled evidence has rarely been used). Results are admitted into the same bounded `memory_evidence` block as curated memory, at the lowest tier: history only uses the budget curated memory leaves, and its scores are weighted below curated memory of equal word overlap (older history lower still). When the block is full of curated lines, no history is admitted. Each admitted line carries its `[tx:...]` handle, so the model can open it with `history_source`.

The block is bounded by lines, estimated tokens, characters and UTF-8 bytes, and by the headroom the request has left. When it becomes disabled, empty or unaffordable, one cleared record replaces the stale one. Later requests of a turn reuse that turn's evidence; a new user turn retrieves again. Foreground history reads are bounded to one second.

Extension memory providers that implement a lifecycle `prefetch` still contribute a pre-turn recall page; history recall does not.

## Delegated workers

A worker with `memory_read` gets read-only access, in both memory systems: a query or a `ref`. In ICM a worker granted `zoom` and `date` holds them as read-only tools through the same broker, by message id only; private worker logs stay root-readable (see [Continuous chat](#continuous-chat-icm)). A result may cite `tx:` source handles and `txn:` summary handles; the worker passes one back as `ref` to read that source or expand that summary, but only a handle an earlier `memory_read` of the same lane returned (or one returned by an admitted expansion), in the same memory generation (otherwise `memory_source_forbidden`). Workers cannot write memory or read arbitrary history. See [Task worker presets](worker-profiles.md).

A `memory_read` result is sized against the receiving lane, never the root model. The lane's own model window, its last accepted request (system prompt, tool schemas and messages), the reply room it keeps free and the tokens its grant and tree still allow are measured from the lane itself. A lane that has sent no request, or whose model declares no window, has unknown capacity. After the wrapper, status and omission lines, standing memory takes at most half of what remains, and the history frontier at most half of what is left after that. Open Knowledge Format documents, extension recall and history hits then compete for the rest. Each is admitted as a whole source-labelled record, so a `tx:` or `txn:` handle is never cut. An Open Knowledge Format document that does not fit appears as its title and summary only, and the omission is stated. When capacity is unknown or exhausted the result says `Memory is constrained`, gives the reason, and attaches no memory. A frontier in a lane snapshot names `memory_read` rather than the history tools. Each lane attempt builds its own memory port, so a retry queries again and holds only the handles its own new reads return.

In ICM a `memory_read` result holds only the explicit history query: its hits and the approved summaries that cover them, sized against the lane in the same way. There is no standing memory, persona, extension recall or frontier. A memory-generation or retrieval-policy change while a read is in flight rejects that read with `memory_snapshot_stale` instead of delivering it; the worker reads again. Disabled retrieval answers with the policy reason.

## Diagnostics

- `/memory history` shows the history recall state: availability (disabled, unavailable, on_demand, loading, active), sessions and spans indexed and skipped, top skip and uncaptured reasons, truncation, the last indexing error with its time and detail, the latest retrieval (status, result count, source refs) and how many items the prompt block admitted.
- `context_audit` shows the same without error text or paths, plus each memory provider's retrieval status (`queried`, `blocked`, `failed` with the failure class).
- History transport. A failed post to the index worker, or a reply outside the protocol, ends that worker once with its cause; reads then answer `unavailable` with that cause until the memory generation restarts the worker. A read that exceeds its bound answers `unavailable` and is counted. Reads made for a history tool call (queries, source reads, and the lineage listings and range checks of summary reads) have one second each and all share the call's deadline; background session and lineage listings for summary construction have 30 seconds. A stopped worker (`stoppedAt`) and a slow one (`readTimeouts`) are reported separately. In coverage, `lastError` is historical; `activeFailures` counts the sources failing now, and when it is zero the error is labelled historical.

`failed` and `blocked` stay distinct from a query that ran and found nothing.

## Continuous chat (ICM)

In ICM (Pi-adaptative-memory) the conversation is one permanent chat per project. Every message is logged word for word and is never edited or deleted. A cheap model compresses the log in the background into a binary tree of one-line summaries, and every user turn sees the view of that tree: summary lines covering the whole chat, recent lines fine and older lines coarse.

**Storage.** `<agentDir>/state/continuous-chat/<project>/` holds `main/<day>.jsonl` (messages), `tree/<day>.jsonl` (summary nodes), `messages.idx`, `keys.idx` and `nodes/<level>.idx` (fixed-width lookup indexes), `view.json` (the saved view, loaded at start and never rebuilt from the log), `queue.json` (pending compactions), `migration.json` (see Migration), `sessions.json` (attached ICM session recovery ledger) and `images/` (image bytes, by digest). Lines are appended and flushed, never rewritten.

**Messages.** `user` (the user's words), `pi` (the agent's replies), `tool` (tool calls: name and JSON input), `echo` (tool results, clipped to their head and tail at 30,000 characters), `work` (a subagent's report, starting `[Name]`) and `note` (memories imported from before the chat). Thinking is not logged.

**Tree and view.** A node covers 2^level consecutive messages and is named `id+n`, its first message and its count. Its summary targets 512 UTF-8 bytes and may be at most 16 bytes over, 528 bytes in all. A line that fits the target is its own node with no model call. The turn view is merged in one batch once it passes 128,000 bytes, down to 64,000. A compaction reads a causal view of 16,000 bytes, merged down once it passes 32,000, that stops before the first line not yet built. The view is a list of summary lines only; `zoom` opens a line when its words are not enough.

**Compactions.** Compactions run on the configured `summaryModel`, at most 8 at once. A reply over the 512-byte target is corrected in the same conversation, up to five attempts in all, and the shortest reply is kept. If the shortest reply is still over 528 bytes, the node fails and is retried after the next arrival.

**Tools.** The root has `zoom` and `date`. A worker granted them, by name in its profile or authority and never by inheritance, has `zoom` and `date` read-only through its memory broker, by message id only; a worker's pages are 4 KiB rather than 32 KiB. Private worker logs stay root-readable.

- `zoom` with a message `id` and `n` opens the line `id+n` into the two lines it was made from. `n` is a power of 2 and `id` a multiple of `n`. `zoom` with `n` equal to 1 returns one message in pages of 32 KiB (4 KiB for a worker). Its images are paged as well, at most four per result and within the 25 MiB per-image storage bound, so every retained image remains reachable.
- `zoom` with an agent's name streams that agent's durable chat log in pages of 32 KiB. Only the root has this form: a worker takes message ids only. Pagination stops after it establishes whether another page exists, so an early page does not load or traverse the complete log and a large message remains readable across pages.
- `date` with a message `id` returns the message's exact stored RFC 3339 occurrence time, with its time and offset. Storage segments remain append-monotone and do not rewrite that occurrence time.

Refusals (for example `not-summarized`, `misaligned` or `not-found`) are typed outcomes of the call: the model reads the reason and the call is not retried unchanged. Every navigation result carries `TRANSCRIPT_RECALL_RESULT_MARKER` so legacy OKF transcript-history capture skips recall output, while ICM continuous-chat ingestion logs each `zoom` or `date` call and result once (`tool` and `echo`) under its own source key.

**Settings.** The view sizes, the compaction concurrency and the tree are intrinsic to ICM and have no setting. `contextPolicy.memory.history.summaryModel` names the cheap model. It must be set and resolve to a configured, authenticated model supporting `xhigh` thinking, and a model that is not local (a local runtime provider or a loopback endpoint) also needs `contextPolicy.memory.history.allowExternalSummaryEgress: true`. When `summaryModel` is unset, unknown, lacks external summary egress permission, or does not support `xhigh` thinking, the chat reports the setting to change and does not substitute another model; when a valid configured catalog model's stored credential becomes unusable at runtime (refused OAuth refresh, account refusal, or quota exhaustion), the lane model resolver fails over to a healthy authenticated model that satisfies the same local/egress and `xhigh` requirements. The summary tree is part of ICM and is always built; `contextPolicy.memory.history.hierarchy` is not read by the chat.

**Migration.** The first ICM start after the upgrade imports up to the 8 most recent eligible earlier sessions' exact text (up to the last 32 non-echo parts per session) as `note` records, in session start order, once; older eligible sessions are recorded as `superseded_by_recent_history`. Earlier sessions are those in this project's default session directories (the current directory encoding, then the legacy one); the running session is excluded because its entries are logged as they happen. Valid copies of the same session identity are deduplicated with the current directory taking precedence. Session bodies stream one at a time in bounded append batches. Source keys are the durable progress checkpoint: after interruption, already appended entries deduplicate while the import resumes. A file that cannot be inspected or read now blocks completion with its real reason and is retried on the next start; it is never converted into a completed skip. A file that holds a session's body without its header line (every non-empty line a session entry, and a `<start time>_<session id>.jsonl` name whose id passes the session-id rule and whose time is a real time) is repaired in memory: its header is reconstructed from the file name, the file itself is never rewritten, and it is imported like any other session; an intact file with the same session id wins over the repaired copy. A file whose content can never be read as a session (a header with an invalid id or time, a header-less file that cannot be repaired from its name or holds a line that is not a session entry, or a repaired copy of a session already listed) is recorded in `migration.json` as skipped with its real reason, and the import completes. A session in the import window whose body holds a line that is not a session entry is detected before any of it is imported and recorded the same way, leaving its place to an older session. Each repaired source and each skipped malformed source is reported once as a warning, when the marker first records it. Empty files are ignored. Sessions the owner forgot in the legacy store are intentional skips and are recorded as forgotten. `migration.json` is written only after all selected sources settle. Its original `completedAt` stays fixed; new sessions are handled by canonical recovery rather than another legacy import. An older marker that incorrectly finalized a failure retries only its recorded failed sources, using the remaining allowance under the original eight-session limit and the same source keys and 32-part bound. Intentional forgotten, unsupported-date and older-history exclusions stay excluded. A known session forgotten since the failure needs no readable source. Filename-only failures must resolve to one session identity, which may be one repaired from the file name; ambiguous or still-unreadable sources block repair, a source that is still malformed is recorded as skipped with its current reason and checked again on later starts, and a source that is no longer listed blocks. Attached sessions recover through the host's canonical path, with legacy repair deferred: a repaired source recovers through its repaired reader, while an attached session whose file is unreadable or malformed blocks the start with its cause, because its live chat entries must never be dropped silently. A repaired marker is saved only after the selected imports settle, preserving the old marker across interruption. The legacy transcript-summary store under `<agentDir>/state/transcript-memory/` is left in place: the migration never deletes or rewrites it, and its derived summaries are never imported as text. When its forget state is unknown or unavailable, the import is blocked, nothing new is imported, and the reason is reported; the next start tries again. A damaged `migration.json` is an error and is never rebuilt.

**Failure states.** A turn whose earlier messages are not all summarized waits for the compactions it needs; if they cannot finish, the turn fails with the real reasons rather than sending with incomplete coverage. A scheduler or lease failure stops the chat, wakes outstanding waits and leaves ICM explicitly blocked; the session never silently falls back to ordinary durable history. A damaged log, queue, view or migration marker is an explicit error, never a silent rebuild. Tree indexes are recovered from the authoritative append-only node journals before they are served. Active ICM sessions are tracked in `sessions.json` so persisted entries (including worker terminal reports) from an interrupted session are recovered with their canonical kinds even when a new session is started next, and worker-name `zoom` resolves durable worker transcripts across parent sessions in the project. `zoom` and `date` report `continuous_chat_unavailable` while the chat is not running in the session. A setting that fails validation is reported with the setting's name; the chat only fails over when a valid configured catalog model's credential or quota fails at runtime.

The system block and the tool definitions carry no dates or live state. A batch rewrites the view once.

**Host compaction.** The chat is the memory structure; host compaction only frees the model's context and never touches the chat log, the tree or the view. Because a turn's requests carry the view, the turn state and the turn's own messages, host compaction under ICM is scoped to the running turn: it summarizes the turn's own messages when a request needs room, the view and state stay fixed envelope, and the next turn is rebuilt from the view. The chat log is fed by persisted session entries, so a compacted turn loses nothing from the log. A continuation turn that resumes at an earlier turn's compaction summary does not own that summary: it is pre-turn history the view already carries, so it is never sent and the turn's scope starts at its first own message. Child sessions (workers) have no project chat and compact session-wide. `context_audit` on an ICM root reports the running turn's request frame and its own rows, not the rebuilt session. A `self_compact` note is released by the end of the turn, with no compaction, and opens the next turn verbatim. See [ICM and host compaction](compaction.md#icm-and-host-compaction).

## Summary hierarchy

An opt-in layer of durable summaries over captured history, controlled by `contextPolicy.memory.history.*` (see [Settings](settings.md#context-memory-and-history)). Exact history recall above does not depend on it; turning the hierarchy off stops summary generation and the frontier, never recall. In ICM the continuous chat is the one summary tree of the root session, so background transcript-hierarchy construction runs only in OKF.

Background construction runs in OKF for a root (non-child) session with memory retrieval enabled, and only when `summaryModel` resolves to a configured, authenticated model. A model that is not local (a local runtime provider or a loopback endpoint) is external egress and needs `allowExternalSummaryEgress`; otherwise construction stays stopped and `/memory history` says why. A memory-system switch does not turn summary or admission egress on.

Reading what was already approved does not need construction. With the hierarchy off, no summary model, or construction stopped, `history_search` discovery and `history_expand` read the stored summaries through a read-only view of the store: it makes no model, admission or egress call, writes nothing, applies the same approval, expiry and branch checks, and follows the store when its root changes: it compares the old and new page trees of the accepted-node table (equal pages prune whole subtrees), reads only the node files of the keys that changed and applies them to the same mirror, without the writer lock and without reading an unchanged table. It reloads the whole store only when it cannot follow safely: a legacy or damaged root, pages the writer already cleaned up, a changed forget state, a damaged node file, or more changes than a reload would read. Every summary read, through the view or the running hierarchy, checks the exact history range the summary depends on (its covered sources and the context entries its leaves were built with) in one batched index request, so a parent zoom never reads its descendants' sources. The index builds its range sums lazily: the first check that reaches a position hashes every position up to it, and later checks inside that prefix are constant-time. A source's identity binds its text and the metadata summaries depend on (role, tool name and call, error status, timestamp, origin), so a change to any of them makes summaries built on it stale. The identity is a 64-bit digest: an accidental miss of one changed part has a chance of about 2^-64, and it is a staleness check, not protection against crafted input. At delivery, after the read's last wait, the store revision, retention, approval and the index state the check observed are confirmed together. Freshness is against what the index has been notified of and ingested: a file change it has not seen yet is not detected. A summary that fails any check is refused with the exact `tx:` sources to open instead; one whose history or store changed while the read was in flight, including while the current session is being written, answers `stale_snapshot` with a retry hint. All reads of one history tool call share one deadline, and an unreadable or busy summary store gives a typed status beside the exact hits instead of failing the search.

- **Nodes.** Leaves summarize up to 8 consecutive captured spans or 8 KiB of one session's selected branch. A leaf whose text fits 512 UTF-8 bytes is an exact copy with no model call. Two aligned sibling nodes merge into a parent. A parent stores no copy of the source handles it covers: its coverage is its two children's, read through them, so a node file and the in-memory mirror stay bounded however much history a parent covers (a parent file written before this still parses, and its copy is dropped). Each leaf keeps the exact source handles it covers separately from the earlier turns it only used as context (at most two spans, 2 KiB), and is accepted only after deterministic checks: non-empty, at most 1,024 bytes (never clipped), no handle outside its inputs, not refusal-shaped. A model reply that fails one of those shape checks is sampled again only within the job's existing three-attempt budget; exhaustion remains terminal and later summaries continue past its explicit gap.
- **Admission.** The deterministic checks prove shape, not fidelity, so a model summary is accepted only after a second gate. Exact copies are never judged. System One, the session's recording semantic engine, judges the exact input the summary covers, with the earlier context kept apart (it only resolves references). Each judgment is a separate yes/no question:
  - `support` (always): every statement is supported by the input.
  - `constraints` (when the input has an owner entry or an earlier summary): owner corrections and constraints are stated with their force intact.
  - `status` (when it has tool traffic, a host-written record or an earlier summary): failed, pending and completed steps are reported as the input shows them.

  A judgment passes only as a decisive yes: P(holds) of at least 0.90, and in the engine's hard-pass band (0.93 by default, which binds). A decisive no (P at or below 0.20) ends the job `failed` as `admission_rejected`; any other answer ends it as `admission_uncertain`. Neither is sampled again. An evaluator that did not answer (outage, timeout) is transient: the job retries within its attempts, and its validated reply is kept on the job, so the summarizer is not paid again. A paid answer that breaks the evaluator's contract (any asked question is left unanswered, or it returns no usable probability) is evidence of nothing: it ends the job `failed` as `admission_invalid_output` after that one request, is never reused and is not retried as an outage. The kept reply is reused across restarts while its input and recipe still match and it still passes the deterministic checks. An evaluator that refuses the exact input (a credential in it, or more than 128 KiB, never truncated) is terminal. A call refused before any provider request keeps the provider-request, transport-attempt and receipt counters at zero, but the logical claim attempt is consumed (a conservative policy). Usage is charged to the session's System One receipts and shows as `summary admission` on the semantic ledger. Each paid response has one receipt, written to the session ledger as a `semantic_usage` row and confirmed by reading it back. A receipt that cannot be confirmed yet (the session file has no first reply, or a write failed) keeps the verdict on the job under the `usage_receipt` hold: the answer is not bought again, and the receipt is recorded on the bounded retry once the session file has its first reply, or once a new session manager reads the file after a failed write. A session that never gets a first reply has no file to record into. An automatic rollback (or any replacement that fails before it commits) that discards a session it created removes the session file, unless the file holds paid usage rows that no other session records: then the file is kept as recovery evidence and the notice names its path and row count. A branch's copied rows are its source's, so they never keep a file. An import copies its file, and the copy is the file the rule above decides, with the source file's rows as its evidence baseline. A switch or resume target is never removed. A replacement whose runtime fails after its session exists disposes that session in full (its extensions, shell and usage owner) before the file is decided, and the owner's warnings still reach the surviving session. Its usage-journal sidecar is kept as unmatched recovery evidence, and the discarded session's owner handoff names the sidecar path and the number of reports it holds; that handoff is delivered on the session that survives: the restored session, or, when the restore itself fails, the replacement error the host shows. Warnings the discarded session held are delivered there too, none is dropped. Deleting a session from the session picker is the user's own delete: it removes the sidecar with the session file (moved to the trash when a trash is available, unlinked otherwise). The sidecar is named by the session id, which must satisfy the kernel's session id rule: letters, digits, '.', '_' and '-', starting and ending with a letter or digit, and no longer than the 64 KiB session header that carries it. A session file whose header id breaks the rule is refused when it is opened. A job that ends while a receipt is still owed hands it to a durable owed-receipt queue (`owed-receipts.json`, at most 256 entries; past that the oldest entry is dropped from the queue and counted as lost, though the usage journal may still hold its receipt) that the owning session records. Receipts the owner hands back join the end of that queue, so an overflow drops the oldest queued entries first. An accepted judgment is kept with the reply: a retry after it (an index that did not answer at publication, or a restart after the job list was saved) publishes that verdict without asking the evaluator again, while the reply, the admission input and the contract are unchanged.

  A model summary is **held** before any model call, with the cause shown and the attempt returned, while exact copies keep flowing. Held when the summarizer is missing or its egress is not allowed; when `allowExternalAdmissionEgress` is off (see [Settings](settings.md#context-memory-and-history)); when System One is not bound; when its evaluator does not report calibrated probabilities; or, for a parent, when a child summary is not approved yet (a parent is judged only after both children are approved). A different hold follows a paid answer rather than preceding a call: `usage_receipt`, a valid paid answer waiting for its usage receipt to be confirmed in the session ledger (the answer is kept and not bought again). A receipt owed to another session is not claimed by a coordinator of a different session. Before anything is published, source coverage, child approval, policy and the writer fence are rechecked; an egress setting withdrawn after judgment discards the admitted text. The node records its admission: contract version, judged questions, confidences, evaluator, and a digest of the admitted text. The store refuses to publish a model summary without a current admission.

  Pre-contract nodes (accepted before the contract, or under an older one) are not approved: they are out of the frontier, and `history_expand` returns the exact `tx:` handles of their sources instead of their text. Each is judged again from its own text against freshly re-read sources, with no summarizer call. Admitted: the record is added and the node becomes approved. Rejected or uncertain: the node is revoked and derived again through the normal pipeline, where a second rejection ends that job. Unavailable: it stays unapproved and is retried on a 5-minute wake. A source the index did not answer is read again on that wake; a source that changed or is gone (`source_coverage_changed`), or one beyond the read bound (`source_read_refused`), waits without that retry. `/memory history` shows held jobs counted per hold kind (`model_work`, `children`, `proof`, `persistence`, `reconciliation`, and, after a paid answer, `usage_receipt`) with the first held job's cause, judgment counts (each reuse of a kept acceptance without a new judgment is counted separately and is not a judgment), and unapproved nodes counted by what each waits for (for example `child_not_approved`, `evaluator_unavailable` or `readmission_failed`, the last meaning the re-admission spent its attempts for this text and contract and is not judged again). It also shows the summary coordinator's newest internal cause with the time it was recorded (bounded to 512 bytes; a cut cause ends with `[truncated]`); that line is not cleared when its condition ends, so an older time may describe a condition that is already over. The model-facing `context_audit` view omits it.
- **Handles.** A summary is named by `txn:<16 hex>`. `history_expand` zooms one level; the covered `tx:` handles open exact text. A summary is untrusted evidence: it carries handles, never authority, and cannot promote itself into USER, MEMORY or OKF.
- **Storage.** Derived state lives under `<agentDir>/state/transcript-memory/<project>/` (immutable node files; content-addressed, bounded metadata pages; one small atomic root with the writer fence, revision and all table roots; bounded jobs and terminal records; retention anchors and terminal-proof records), plus two small permanent files beside the root: `forgotten-sessions.json` (the permanent forgotten-session state: a revision, a digest and at most 20,000 sessions; a full list refuses new forgets and never evicts, and a state that is damaged, missing or older than the revision the root applied is reported as unknown and stops construction until it is repaired) and `owed-receipts.json` (usage receipts that ended jobs still owe, versioned and bounded). Each metadata table is an immutable treap whose pages each hold one entry (one bounded domain value) and two child hashes. Ordinary publication path-copies only the changed search paths, writes those pages first, and atomically replaces the root: a crash before the replacement leaves the old root authoritative and only unreferenced pages, and the in-memory view of the tables changes only after the replacement is acknowledged. Publication does not enumerate or rewrite the growing accepted-node, session, frontier, dormant or tombstone tables, and reads back only the node files it newly references (an incoming node, or a node a frontier did not name before); every frontier node must still be an accepted entry. Unreferenced pages are removed by an age-gated sweep at every coordinator start and, in a long-running writer, after enough pages were written since the last sweep (at least 4,096 and twice the live pages, so the full trace is amortized); a sweep that fails after a commit is recorded and never fails that commit. A reader that finds a page missing re-reads the root and follows a newer one instead of reporting damage, and an I/O failure while reading a page (not a digest, shape or ordering failure) is reported as the store being unavailable, never as damage that recovery would act on. The page cache is bounded to 32 MiB of page text. A legacy full manifest remains readable and migrates under the writer lock (pages first, root last, so an interrupted migration leaves the legacy file authoritative). The first load of a read-only view, and any change it cannot follow, take the full load under the writer lock. Metadata binds each accepted or dormant node to the SHA-256 digest of its exact summary text and committed admission marker; legacy entries without the text binding are refused and rebuilt from canonical history. Writes are atomic by rename and are never fsynced. A process crash leaves the old root or the new one, never a torn one; power-loss durability is not established, so after one a file can be missing or empty. Every file and content-addressed page is verified on load. A damaged file or metadata page is kept beside itself as `*.corrupt.<time>` (the newest five per file; recovery also keeps the replaced root), reported as a recovery issue, and its derived content is rebuilt from the canonical sessions. Parent node files contain only child identities; covered source handles remain in leaves, so node size stays bounded as parents cover more history.
- **Work.** Summaries run in the background at most `maxConcurrentSummaries` at a time, start from committed-input events (no polling), wait while the foreground is busy, and retry only transient failures (three attempts). A summary call is made only after the job list that counts its attempt has been saved: when that save fails, the job is held with the cause `persistence_unacknowledged` and the save's real error, its attempt is returned, and the save is retried with backoff (1 s doubling to 60 s); a superseded writer or a corrupt manifest stops the hierarchy. At every start, no new summary work is admitted until the run's first job-list save succeeds, so earlier attempts, including those recorded under an earlier source identity, are never reset. Leaf jobs recovered from an earlier run are held (`reconciliation`) until their earlier spending is merged, and a summary call is made only while its claim is still current, so a budget raised by that merge is never overspent. Usage is charged to the session's usage record on the `history_summary` route (see **Spend** below).
- **Spend.** A summary call's paid spend is retained in the session's usage journal before its row is appended, on the `history_summary` route: the canonical row is a `semantic_usage` row whose `route` is `history_summary`. It counts once in CURRENT by report id, and as background (spawned) spend in the cost guard and `/context`, as it did before the route. A report the journal retained that is not yet recorded (a failed or fenced append) stays in the sidecar, and the next session manager that reads the file records it exactly once; a summary retry never buys the same reply again. History summary spend holds at most half of the journal's record bound. A report past that share, or past the journal's combined bound, is kept in a bounded live total: it counts in this session's CURRENT and background spend, is warned once, and is not durable, so it is absent after reopen. An unretained report is the same: counted live, absent after reopen. A rejected replacement's session file is removed only when it is readable and holds no paid row appended after its copy was made (a copied row is recorded by its source); otherwise it stays as recovery evidence with a notice, and a file that cannot be read back is always kept. Bound: a fork whose branch file was not yet written when it was made counts from byte 0, so if the discarded candidate later writes a reply, the rows copied from its source count as kept, and the notice says the source may also record them. Warnings a session still holds when it ends are not dropped. A session under a runtime hands them on quit to the runtime's terminal sink (`onTerminalWarnings` of `createAgentSessionRuntime`) and, on a replacement, to the session that replaces it. A bare session (`createAgentSession`) hands them to `onClosingWarnings` when `disposeAndWait()` closes it. The default sink is stderr, one line per warning, with every control character shown as a visible `\xNN` escape; the sinks themselves receive the raw text. The interactive host holds them until the terminal is restored, and RPC sends them as warning events while the stream is open. A session that closes with paid usage it has not recorded therefore shows its handoff, and a discarded replacement's handoff goes to the session that survives.
- **Frontier (OKF).** In OKF, the current session's frontier (an ordered history view made of accepted nodes, explicit unsummarized gaps, recent history in detail and older history merged) is shown as a `transcript_frontier` record, and only for history that was compacted away on the live branch. What the live context still shows after the latest compaction (the kept tail, the original user message and restored gap entries under `original-user` retention, carried-forward records) is read from the session's retention owner and is not re-sent. A node that also covers visible spans is expanded to its two children; a leaf that mixes both is withheld and replaced by a pointer that keeps its compacted-away source handles reachable. The persisted frontier is never changed by this view. After a branch switch (`/tree`) a frontier whose entries are off the live branch is not shown (`lineage_mismatch` in `/memory history`), and a plan prepared before a branch switch or a new compaction is planned again. The record lives inside the memory allowance: at most half of it, in bytes and in estimated tokens, and at most `frontierMaxBytes`, and the evidence block composes within the remainder. The summary catalog incrementally owns approved-node ordering, parent-pair lookup and approval invalidation, so ordinary publication extends the bounded frontier without scanning or sorting the session's history. It grows by append, skips a failed or still-pending range only by rendering that range as an explicit gap (a summary that lands in such a gap later is spliced in by resuming after the last record before it, so every earlier record keeps its bytes), merges oldest aligned pairs toward half the allowance, and replaces the oldest run by an explicit pointer when merging cannot fit. A selection also remembers the position it was first built from; an accepted leaf that later appears before it (a summary that finished after later ones) makes the next planning rebuild once from that leaf, while a reduction that drops the oldest records does not. Its opening boundary and untrusted-content nonce stay stable for the controller lifetime, so an append preserves the provider-visible prefix through the retained records; mutable coverage status follows the records. A frontier that changes after a request was planned enters the next request only. ICM never projects this frontier into the prompt; legacy summaries reach an ICM session only through `history_search` and `history_expand`. The continuous chat's view is a separate memory (see [Continuous chat](#continuous-chat-icm)).
- **Retention.** `retentionDays` ages out derived summaries only. It never erases or hides a canonical transcript and never limits exact history search or source reads. A source's age is its entry's event time; without one, the canonical session timestamp; without one, the moment it was first captured (`event_time_unknown` in `/memory history`). That anchor is persisted per source, so invalidation and rebuilds never reset it, and up to 20,000 anchors are kept; past that, the affected work is held and reported. A node that depends on a source past the window is revoked with every ancestor and frontier built on it. Expiry is enforced when a summary is read, when it is expanded, and before a late result is published; the frontier is withheld while it names an expired node. A source with no age yet does not feed a new summary. One lifecycle wake covers the earlier of the next retry and the next expiry, and a restart recomputes it from persisted state. A job whose attempts are spent ends `failed` with `attempts_exhausted`, and identical work found again gets no fresh budget.
- **Terminal proof.** Each admitted summary job identity reserves one durable record before its first chargeable summary or admission call; when the job fails, the record keeps its spent attempts in the same slot. At most 20,000 records are kept. At that bound new identities are held with the cause `capacity` and existing jobs keep their own budgets; a failed job is never pruned before its record is durable. A ledger written before records were reserved that is already at the bound, or damaged proof, may have lost records, so it sets a durable `possibly_lost_proof` hold: sessions started before the hold get no new summary identities until their records are forgotten through the canonical forgetting path (`/memory history forget <session> <session>`, which records the forget permanently whether or not construction is running: without a coordinator every reader denies the session at once and the derived data is removed the next time one starts; an unknown session id writes nothing), and one reclaimed record does not lift it. Reservations and holds persist across restarts. Exact history reads are never held. `/memory history` shows the records and reservations against the bound, and the hold with its cause and time.
- **Forget repair.** When the permanent forget state is unknown (damaged, missing, or older than the revision the root applied; from the first lease on the forget file always exists and the root always records an applied revision, so a file that disappears is never read as "nothing was forgotten"), construction stops with that cause and never reads the state as "nothing was forgotten". `/memory history repair-forget I-accept-lost-forgets` is the explicit operator repair: it keeps the damaged file beside the new one, carries over what is still readable, and accepts that sessions forgotten only in lost records can be summarized again, then restarts the hierarchy. The acknowledgement word is required, and a known, intact state is never replaced (the command reports that nothing was repaired).
- **Reconciliation.** Revoked nodes are derived again after an invalidation (a source changed) or after an admission verdict of `rejected` or `uncertain` on that node. A retention or forgetting revocation is permanent: its identity is never admitted again, and a late result for it is refused. A parent whose two children survive is derived again from them, and until it is published its range is covered at child level. `/memory history` reports how many parents are being derived again.
- **Work counters.** The structured hierarchy status (`admission.work`; the `/memory history` text does not print it) keeps unlike units apart: logical attempts, semantic requests, transport attempts, receipts recorded, pending and lost, and reused verdicts. A semantic request counts an admission call that sent at least one provider request; a transport attempt counts the provider responses behind it (at least one per counted request). Neither claims a charge: spend is the receipts.
- **Handoff.** Each finished batch leaves a bounded terminal record (counts and causes). Failures and self-stops are shown through the session warning path; a success is diagnostics only and never starts a chat turn.

`/memory history` and `context_audit` add a hierarchy section: state, jobs by state, accepted nodes, oldest backlog, the frontier revision and size, recent failure classes and the last batch. `/memory history` also prints the real stop reason, failure causes and recovery findings; `context_audit` shows failure classes only.
